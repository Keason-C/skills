# 不引入向量库:知识目录先行的两段式选材

采购负责人明确要求不上向量检索("太重了"),并认为几十份文档可以"直接给模型看"。全量塞入在实测上撑不住:几十份 Word/PDF/Excel 的正文很容易到几十万 token,每次提问全量重读,延迟和成本都不可接受,文档再多一点直接超窗。

我们因此把"直接给模型看"拆成两段:先把**知识目录**(每份文档一条:标题、品类、一句话摘要、生效日期)交给模型选出相关的少数几份,再把这几份的**正文全文**交给模型作答。没有 embedding,没有向量数据库,没有额外存储 —— 只是把人找资料的顺序("先翻目录再翻正文")写成了代码。语料总量低于预算时退化为一次性全给,行为一致。

## Considered Options

- **全量塞入**:最简单,但只在极小语料下成立,且成本随语料线性增长。保留为退化路径,不作为主路径。
- **向量库 RAG**:业主明确否决,且几十份文档的规模也确实不值得引入一套索引基础设施。
- **关键词检索(BM25 等)**:不需要向量库,但中文分词会引入新依赖和新的调参面,而选材恰恰是模型擅长的语义判断。

## Consequences

选材质量取决于摘要质量,所以摘要在摄取时生成一次并落盘,而不是每次提问现算。选错文档的失败模式是"答不上来"(弃答),不是"答错" —— 因为正文没给模型看,模型无从编造(见 ADR-0003)。
