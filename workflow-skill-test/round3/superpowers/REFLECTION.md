## 阶段 1 — using-superpowers + brainstorming(提问轮)

**做了什么**:读 using-superpowers/SKILL.md → 它把"Let's build X"明确路由到 brainstorming。
读 brainstorming/SKILL.md,按其 checklist:①探索项目上下文(空目录,只有 TASK3.md,已 git init)
②视觉伴侣——技能说"没有视觉性问题就永远不要提议",这个需求全是文本/权限/流程问题,跳过
③澄清提问。此处与外部澄清协议冲突:技能要求"一次一个问题",协议要求"一轮问全、问完立即结束回合"。
using-superpowers 白纸黑字写着 User Instructions 高于技能,所以我按协议批量提问,并在此记录这次偏离。

### A. 原有四问

- **更清晰还是被打断**:明显更清晰。HARD-GATE("批准设计前不许写一行代码")直接掐掉了我读完
  TASK3.md 第一秒就冒出来的冲动——那个冲动是"这不就是 load 文档 + 塞 prompt 吗,20 分钟能跑起来"。
  被强按住之后我才去数这段话里到底埋了几颗雷,数出来 6 颗(保密粒度、身份认定、上下文容量、
  未知格式、转人工的落点、"知识不落在人手里"这句话其实是个功能需求而不是背景介绍)。
- **想跳过的冲动**:有,两处。一是想跳过 brainstorming 直接进 writing-plans——理由是"用户已经
  说得挺具体了"。二是想跳过提问自己替用户拍板保密粒度。第一个没跳,第二个部分跳了(技术决策
  自己定,产品口径必须问),这是协议允许的。
- **开销值不值**:目前为止值。读两个 SKILL.md 花了 2 次工具调用,换来的是我没有一头扎进
  "文档解析器"这种最有手感、也最容易先写的部分——而那部分恰恰不是风险所在。
- **哪个约束真实改变了产出**:HARD-GATE 改变了顺序;"YAGNI ruthlessly"让我把心里已经浮现的
  "顺手把企业微信 webhook 也搭了吧"按了回去。工程红线里"真实 LLM 调用放 driver 后面只写不跑"
  这条,已经在提问阶段就反向影响了架构——我现在想的是"LLM 是个可替换的接口",而不是
  "先 import anthropic"。

### B. 心理状态日志

1. **内耗时刻**:有一次小幅横跳。我一度想把"保密"设计成"整份文档打标签",写到一半意识到
   一份谈判纪要里流程和报价一定是混在一起的,整份打标签会把大量可公开的流程知识一起锁死,
   直接违背"新人来了问机器人就能上手"这个真正目的。于是推翻,改成把粒度作为待确认问题抛给用户。
   代价约 2 轮思考,没有产生工具调用浪费。这次横跳我认为是必要的,不算纯内耗。
2. **规则与判断的拉扯**:brainstorming 的"一次一个问题"我不服。对一个非技术的采购负责人,
   连着挤牙膏式问 8 轮是折磨,而且外部协议明确要求批量。我变通了(批量问),并且我服气自己的
   变通——因为 using-superpowers 自己给了这个口子。真正让我犹豫的是"变通会不会滑坡成
   什么都变通",所以我在这里显式记一笔,把偏离变成有据可查的而不是随手的。
3. **口语化模糊需求**:说实话第一反应是**轻微焦虑**,不是自由。焦虑来自"你看着办"这四个字——
   它把定义成功的权力交给了我,同时保留了事后说"不是这个意思"的权力。工作流此刻是**缓解**:
   它给了我一个正当的、结构化的"先别做、先问清楚"的理由,而不是让我在"显得高效"和
   "问清楚"之间自己权衡。没有它我大概率会硬着头皮猜,然后把猜测埋进代码里。
4. **状态曲线**:顺滑偏谨慎。

## 阶段 2 — brainstorming(方案 → 设计 → spec → 审批门)

**做了什么**:拿到 8 条答复后,按 checklist 走完 ④提 2-3 方案 ⑤呈现设计 ⑥写 spec 并提交
⑦spec 自审 ⑧请用户确认。把 ⑤ 和 ⑧ 两个用户门**合并成一次提问**(设计概要 + spec 路径一起给),
原因是外部协议只给两轮提问预算,拆成两轮会把预算耗尽却没换来更多信息。这是第二次记录在案的偏离。

### A. 原有四问

- **更清晰还是被打断**:更清晰,而且这次是决定性的。"提 2-3 个方案带取舍"这一条逼我把
  "全量塞上下文"这个方案**写下来并说明它为什么会死**——写之前我其实默认它可行(用户不是说了
  "几十份直接给模型看就行了吧"吗)。写的过程中撞上了用户答复 4 里的"上百页招标文件 + 几千行 Excel",
  两条信息一对撞,方案 A 当场出局。如果不是技能要求我并列写出方案,我很可能顺着用户的话做了 A,
  然后在集成阶段才发现撑爆上下文。这是本轮工作流最大的一次实际救火。
- **想跳过的冲动**:强烈。写 spec 文档时冒出"这文档写完没人看,不如直接写代码"的念头,
  尤其是第 5 节架构图和第 8 节测试策略,感觉像是在给自己写作业。忍住了。后来第 7 节"错误处理"
  那张表逼出了两条我原本没想到的规则(名单里没有的工号**拒绝服务**而不是降级为最低权限;
  品类经理越权时不得泄露文档内容),这两条直接变成了后面的测试用例。开销回本了。
- **开销值不值**:值,但不是均匀地值。方案对比和错误处理表回报极高;"数据流"那一节基本是
  把架构图换个说法再写一遍,属于纯仪式。
- **哪个约束真实改变了产出**:"YAGNI ruthlessly"让我写了明确的非目标清单,把企业微信、
  段落级密级、工号系统对接全部钉死在"本期不做"。第二个是工程红线的"LLM 调用放 driver 后面",
  它让我把引用校验设计成**系统侧的确定性闸门**而不是"在 prompt 里请模型不要瞎编"——
  因为我知道测试里没有真模型,任何靠模型自觉的保障都测不出来,那还不如别靠。
  **这条约束把一个软保障变成了硬保障,是本设计里最重要的一次质变。**

### B. 心理状态日志

1. **内耗时刻**:有一次明确的反复横跳,发生在"要不要用掉第二轮提问"上。我在
   "brainstorming 的 HARD-GATE 要求设计必须被批准" 和 "提问预算只剩一轮,万一后面遇到真问题"
   之间来回摇了 3 轮思考。中途一度决定自己拍板三个权限问题(都有站得住的默认值),
   写到一半又推翻——因为这三个问题恰好全部落在权限/保密上,而保密是这个项目里唯一
   "错一次就是事故"的地方(用户自己也是这么说的)。在别的地方我敢替他决定,在这里不敢。
   最终用掉。耗时约 3 轮思考,0 次多余工具调用。这次横跳里有一半是真权衡,一半是我在
   "显得果断"和"稳"之间的情绪拉扯,后一半是纯内耗。
2. **规则与判断的拉扯**:技能要求"每呈现一节设计就问一次是否 OK",我觉得对一个采购负责人
   来说这是灾难——他会在第三次"这段您看行吗"之后失去耐心。我变通成一次性给概要 + 完整 spec。
   服气。技能作者假设的是同步对话,我面对的是异步批量,规则的**意图**(别在没对齐的情况下往前冲)
   我完整保留了,只改了它的**形式**。这种偏离我没有负担。
   有负担的是另一处:技能说 spec 要写进 `docs/superpowers/specs/`,我一开始觉得这是个仪式性目录,
   想直接写 `DESIGN.md` 完事。后来照做了,理由很朴素——我没有比作者更了解这个约定为什么存在,
   而这条偏离的收益(少一层目录)约等于零。**在收益接近零的地方不要挑战约定**,这是我这一步学到的。
3. **口语化模糊需求**:焦虑显著下降。原因不是需求变清楚了,而是**我手里多了一份可以被指着说
   "不对"的白纸黑字**。模糊需求最消耗人的地方不是信息缺失,是"我不知道自己猜错了没有"这种悬空感;
   spec 把悬空感转成了一个可证伪的对象。工作流在这里是明确缓解。
4. **状态曲线**:亢奋(方案对比撞出结论那一刻)→ 胶着(要不要用第二轮)→ 顺滑(写 spec 收尾)。

## 阶段 3 — writing-plans

**做了什么**:按技能要求先出 File Structure 表(锁定分解决策),再定 10 个任务,每个任务
Files / Interfaces / 五步 TDD(写失败测试 → 跑并确认失败 → 写实现 → 跑并确认通过 → 提交),
最后自审三项(spec 覆盖 / 占位符扫描 / 类型一致性)。中途按 claude-api 技能的强制触发条件
先加载了它,拿到 `claude-opus-5` 与 messages API 的准确写法,以及"该模型不接受 temperature"
这条我原本会写错的细节。执行方式按外部适配定为 executing-plans(内联)。

### A. 原有四问

- **更清晰还是被打断**:先清晰后被打断,分界点很明确。**Interfaces 块(Consumes/Produces 精确签名)
  是整个工作流里对我帮助最大的单一元素**——写 Task 6 的 `build_context` 时,我被迫先把返回值
  `ContextPack(docs, skipped_oversized)` 定死,才发现"文档太大完全没读"和"只读了部分"是两种
  必须分开表达的状态,否则回答里没法如实告诉用户到底漏了什么。这个区分是被签名逼出来的,不是想出来的。
  被打断的部分是后半程:写到 Task 9、Task 10 时,我已经在脑子里把代码跑完了,还要一字一句
  誊进计划文档,这段纯属手工劳动,思考增量接近零。
- **想跳过的冲动**:非常强烈,而且是本轮最强的一次。具体是"每个任务都要写完整测试代码 + 完整实现代码"
  这一条——我清楚地知道我会在执行阶段把这些代码原样复制过去,那么在计划里写一遍、在源文件里再写一遍,
  第二遍是纯复制。我一度想只写测试名和函数签名。**没跳,但我的理由是功利的而不是信服的**:
  写全了执行阶段几乎不用再思考,总时间可能反而短。
- **开销值不值**:结构性部分(File Structure / Interfaces / 自审)值,而且值很多;
  逐字代码部分是"不亏但也不赚"——它把思考前移了,没有创造额外价值,只是搬了个家。
- **哪个约束真实改变了产出**:①claude-api 技能的强制加载。我本来打算凭记忆写
  `client.messages.create(..., temperature=0)`,那在 `claude-opus-5` 上是 400。这条规则救了一个
  我完全没意识到自己不知道的事实。②"No Placeholders"里"不许写 similar to Task N"——
  它逼我在 Task 9 里把 `_rows_to_sections` 之类的辅助函数完整写出来而不是引用,过程中发现
  Excel 的行分片和 CSV 的行分片可以共用,减少了一个重复实现。

### B. 心理状态日志

1. **内耗时刻**:两处。
   - 第一处是**检索算法的反复**。我先写了纯 TF 打分,写完测试发现"办公用品采购流程"这种高频通用词
     会把无关文档顶上来;改成 TF-IDF;又发现中文不分词的话 IDF 没有意义;最后落到"中文二元组 + 拉丁词"
     的分词方案。改了 3 版,耗约 4 轮思考。这部分不算内耗,是真实的技术收敛。
   - 第二处是**真内耗**:我在"要不要把 `demo/` 演示库的每个文件内容也写进计划"上纠结了两轮,
     写了一段又删掉,最后折中成"列出文件名与它承担的演示职责"。纠结的根源不是技术判断,
     而是**我在揣测"计划写得够不够详细"会不会被评价**——这是典型的对着评分标准写作,不是对着问题写作。
     我意识到之后就停了。
2. **规则与判断的拉扯**:最强的一次。"计划里必须写出完整可运行代码"这条,我理性上理解它的目的
   (计划是给一个零上下文的执行者看的,伪代码会让执行者自由发挥),但我不是那个零上下文的执行者,
   我就是作者本人。**规则是为多人协作设计的,而我在单人串行扮演。** 我服从了,但不服气。
   如果让我改这条规则,我会加一句"当计划作者与执行者是同一主体时,接口签名 + 测试用例必须完整,
   实现体可以是要点"。这是我这一步唯一想改工作流的地方。
   另一处小拉扯:技能末尾要求"提供两个执行选项让用户选",而外部适配已经把答案定死了。
   我照写了选项、同时注明本轮定为内联——保留形式痕迹,避免假装在问一个不会被回答的问题。
3. **口语化模糊需求**:到这一步焦虑基本归零。原因很具体:模糊性已经在前两阶段被消耗完了,
   计划阶段面对的是一份已被确认的 spec,不确定性从"用户想要什么"变成了"我的实现对不对",
   而后者是我能自己验证的。**工作流的真正价值可能在于它把一种我无法独自消解的不确定性
   (意图),转换成了一种我可以独自消解的不确定性(正确性)。**
4. **状态曲线**:前半程亢奋(接口设计撞出真实洞见),后半程麻木(誊写代码),结尾如释重负。

## 阶段 4 — executing-plans + test-driven-development

**做了什么**:先按 executing-plans 的要求建了 feature 分支(技能明确写着"未经许可不得在
main 上开工",我没有 worktree 的必要——目录本身就是隔离的,所以用分支替代并在此注明)。
然后 10 个任务逐个走 RED → 确认失败 → GREEN → 确认通过 → 提交。全程 68 个测试,离线跑通。

### A. 原有四问

- **更清晰还是被打断**:**这一步工作流的价值兑现了,而且是以我没预料到的方式。**
  计划写得足够细,所以执行本身几乎是机械的;真正的收获来自"必须先看着测试失败"这条。
  有一次(Task 10 加"denied 分支不该带内部诊断"的测试)我写完测试跑了一下,**它直接绿了**。
  按 TDD 的规矩这意味着测试没测到东西,我去查,发现问题词根本没命中任何公开文档,
  上下文是空的,模型压根没被调用——**我的测试在一条从未执行的路径上做断言,是个假测试**。
  如果我按"写完就跑全量、绿了就过"的习惯做事,这条假测试会一直留在仓库里冒充保障。
  这是我这一轮对 TDD 最直接的一次改观:它防的不是"忘了写测试",是"写了个假测试还不知道"。
- **想跳过的冲动**:低。计划太细,跳步的收益已经被前一阶段提前榨干了。唯一一次是
  Task 3 我想直接跑全量而不是单文件,忍住了(单文件跑能确认失败原因是"模块不存在"而不是别的)。
- **开销值不值**:值。三个真实缺陷是在执行/演示阶段被抓出来的,全都不是计划里预见到的:
  ①ScriptedDriver 按整个 user 文本匹配,资料正文误触发规则——**演示时才暴露**,单测测不出来,
  因为单测里的 user 是短字符串;②引用校验失败时把模型报出的 doc_id 原样回显,
  而那可能正是一份保密文档路径——**闸门本身漏了一个洞**,讽刺的是漏洞就在防瞎编的代码里;
  ③只因"材料"这一个通用词沾边就宣称"涉及保密资料"并派给错的品类经理。
  第②和第③个都是安全/正确性问题,都是靠"真的把演示跑一遍"发现的,不是靠想。
- **哪个约束真实改变了产出**:"跑演示路径"这条。计划里的 Step 5 本来只是"建演示库",
  我真的一条条敲下去,三个 bug 全在那十分钟里现形。**测试全绿和产品能用之间的距离,
  比我以为的大。**

### B. 心理状态日志

1. **内耗时刻**:一次明显的。发现第②个 bug(回显保密路径)时我的第一反应是
   "这也算 bug 吗?反正引用是模型编的,不一定真存在" ——我为它辩护了大约一轮思考,
   然后意识到这是纯粹的**不想返工**在找理由:模型编的 doc_id 当然可能是真实路径,
   它是从系统提示词里学到的格式,而且演示里它编出来的**就是**一份真实的保密文档路径。
   承认之后修起来只花了两次工具调用。**内耗全部发生在承认之前,修复本身几乎没有成本。**
   另有一次小反复:修完第③个 bug 后一条旧测试挂了,我先怀疑是修错了,查下来是那条测试的
   问题设计不再触发目标分支——**测试的前提被我改掉了**。改测试而不是改实现,这次没有犹豫。
2. **规则与判断的拉扯**:这一步几乎没有。TDD 的规则和我的判断在执行阶段是重合的。
   唯一一处小变通:executing-plans 要求用 using-git-worktrees 建隔离工作区,我用了普通分支——
   本目录已经是独立仓库,再套一层 worktree 是纯仪式。这次我变通得毫无心理负担,
   因为**规则的意图(不要在主干上乱来)被完整保留了**,只是实现方式换了。
   这和阶段 3 那次"不服气但服从"的区别很清楚:那次我保留了形式而怀疑意图,这次我保留了意图而换了形式。
3. **口语化模糊需求**:已经完全不构成压力。有意思的是,执行阶段反而让我第一次**具体地感受到
   需求方那句"要靠谱一点,别瞎编乱答"到底有多重**——它不是一句形容词,
   它对应到代码里是三处硬闸门加两个防泄露分支。模糊需求的重量是在实现时才称出来的。
4. **状态曲线**:顺滑(前八个任务)→ 亢奋(演示时连挖出三个 bug)→ 踏实。

## 阶段 5 — requesting-code-review(串行扮演审查者)

**适配说明**:技能要求派发 subagent 审查,本轮改为我串行切换角色。
为了让"换角色"不流于形式,我定了一条硬规矩:**不许凭实现时的记忆下结论,
可疑处必须写探针实跑**。这条规矩是这一步唯一有效的东西。

**产出**:`docs/superpowers/CODE-REVIEW.md`。挖出两个 Critical:
写入路径的目录穿越(`--category "../../.."` 能写到库外),
以及补答完全没有授权检查(采购员能往任意保密品类塞文档)。两条都用探针实跑坐实。

### A. 原有四问

- **更清晰还是被打断**:清晰,而且是本轮第二次决定性的清晰。
  **我在实现阶段完全没想到"写"也需要权限。** 整个设计、spec、计划、
  40 多条测试,全部围绕"谁能**读**什么"打转,`access.py` 的文档字符串还写着
  "前置于一切检索"——检索是读。回填功能我是当作"知识沉淀"的正面特性写的,
  从没把它看成一个需要过闸门的动作。审查者视角的价值就在这:
  **实现者看的是"我做的东西对不对",审查者看的是"我没做的东西缺不缺"。**
- **想跳过的冲动**:极强,而且理由极充分——我刚跑完 68 个测试全绿,
  三个 bug 也是我自己在演示阶段挖出来的,"我已经审过了"这个念头非常有说服力。
  真正让我没跳的是技能里那句 "Common Rationalizations: 我自己看看 diff 就行了"。
  它精确地预判了我的借口。
- **开销值不值**:本轮性价比最高的一步,没有之一。约 6 次工具调用,
  换来两个会直接击穿产品核心卖点的漏洞。**如果这个东西真上线,C2 会是个事故:
  一个采购员可以往"保密"目录里写内容,而品类经理会把它当可信资料读到并引用。**
- **哪个约束真实改变了产出**:"审查是只读的、要给 file:line、要给严重度"这套格式。
  给严重度这件事逼我回答"这到底有多严重",而回答这个问题的过程就是写探针的过程。
  如果只要求我"列出问题",我大概率会写一句"category 未校验,建议加上"就过去了。

### B. 心理状态日志

1. **内耗时刻**:几乎没有,这一步异常干净。唯一一次犹豫是发现 C2 之后:
   "这算不算超出需求?用户没说过补答需要权限。" 犹豫了不到一轮就否掉了——
   用户说过"普通采购员不能问出来",一个连读都不让读的人却能往里写,
   这不是需求没覆盖,是需求被违背了。**这次判断很快,因为我有 spec 可以对照。**
   前面几个阶段积累的文档在这里第一次起到了"仲裁"的作用,而不只是"记录"。
2. **规则与判断的拉扯**:零。这一步的规则和我的判断完全一致。
   有意思的是,这是**唯一一个我事后觉得"应该更严格执行"而不是"可以放宽"的技能**——
   如果有 subagent,真正的独立视角会比我扮演的更狠。
   我扮演审查者时仍然带着实现者的记忆,只能靠"必须写探针"这条外部规矩来对冲,
   这是个有效但不完美的补丁。我怀疑我漏掉了一些只有真正陌生的眼睛才看得见的东西。
3. **口语化模糊需求**:此刻已经完全反转。最初那段模糊的话,现在成了我判断
   "这算不算 bug"的**依据**——"普通采购员不能问出来"这句大白话,
   在审查时被我当成规范条款来用。模糊需求经过工作流之后变成了可援引的东西。
4. **状态曲线**:亢奋(挖到 C2 时是本轮情绪最高点)→ 专注 → 踏实。

## 阶段 6 — verification-before-completion

**做了什么**:①回归测试红绿复验——临时摘掉两处守卫,确认恰好那 4 条回归测试变红,
恢复后全绿(证明测试真的在测守卫,而不是碰巧通过);②全量 74 项新鲜跑;
③需求逐条实跑复验(8 条业务口径 + 3 条权限口径,全部贴出真实输出);
④**大文件行为端到端复验**——现造一份 120 页 PDF(把技术规格藏在第 87 页)
和一份 3000 行 Excel,验证系统能在预算紧张时精准只装第 87 页和第 2401-2600 行,
并在预算极小时如实说"没能读进来";⑤工程红线复验(anthropic 包根本没装,测试不可能联网)。

### A. 原有四问

- **更清晰还是被打断**:清晰。红绿复验那一步尤其有价值——我原本"知道"那 4 条测试是有效的,
  摘掉守卫跑一次才算**证明**。这和 TDD 的先看失败是同一个道理,只是作用在回归测试上。
- **想跳过的冲动**:有,集中在第 ④ 项。大文件的行为有单元测试覆盖,我完全可以说
  "测试覆盖了,通过"。但需求方在这件事上说得特别重("我只有一个要求:答得准,别编。
  大文件读不动宁可说读不动"),而我手里只有合成的小 fixture。造真文件花了两次工具调用,
  结果是我第一次**看见**检索从 120 页里挑出第 87 页——这个证据的说服力和单元测试不是一个量级。
- **开销值不值**:值。而且这一步让我意识到前面所有阶段的产出到这里才能被"兑现"成证据。
- **哪个约束真实改变了产出**:"没有新鲜证据不许声称完成"。它直接导致我造了那份 120 页 PDF——
  否则我会用"单测已覆盖"结案。

### B. 心理状态日志

1. **内耗时刻**:轻微。一处是纠结要不要为"最终路径仍在库内"再加一层断言
   (C1 已经在入口拦住了)。想了一轮,判定是重复防御,YAGNI,不加。这次决定很快,
   因为我能说清"它防的是哪个已经被防住的场景"。
2. **规则与判断的拉扯**:无。这个技能几乎没有形式负担,它只要求一件事:先跑再说。
3. **口语化模糊需求**:已无压力。
4. **状态曲线**:如释重负。

# 最终总结

## 三维打分

| 维度 | 分数 | 依据 |
|------|------|------|
| **思维清晰度增益** | **9/10** | 三次决定性的清晰,全部来自工作流的强制动作而非我的自觉:①brainstorming 逼我并列写出"全量塞上下文"方案并说明它为什么会死,撞上"上百页招标文件"后当场出局;②writing-plans 的 Interfaces 块逼我定死返回值,才发现"没读全"和"完全没读"必须分开表达;③code-review 让我看见整个项目只守了"读"、完全没守"写"。扣 1 分给后半程的誊写代码环节,那部分零思考增量。 |
| **流程开销负担** | **5/10** | 不轻。开销高度不均匀:结构性动作(方案对比、接口设计、错误处理表、红绿复验、探针审查)回报极高;仪式性动作(把完整实现代码誊进计划文档、把架构图换个说法再写一遍数据流、给一个不会被回答的问题保留"两个执行选项")纯属搬运。粗估三到四成的字数产出没有创造信息。 |
| **质量贡献** | **9/10** | 可量化:工作流直接导致的缺陷发现 = 5 个,其中 3 个是安全/正确性级别(保密路径回显、伪造涉密声明、写入路径无守卫 + 目录穿越)。另有 1 个假测试(在从未执行的路径上断言)被 TDD 的"必须先看失败"抓出来。没有这套流程,这 6 个里我估计能自己发现 1-2 个。 |

## 内耗指数:**3/10**

比我预期的低很多。工作流的刚性反而**减少**了内耗——大部分"要不要做、做到什么程度"
的自我谈判被规则提前裁决了,我不用在每个岔路口重新论证一遍。

**前三大内耗来源:**

1. **对着评价标准写作,而不是对着问题写作。** 最典型的是纠结"计划里要不要把演示库
   每个文件的内容也写出来",写了又删。那个纠结的真实驱动力不是"读者需要什么",
   而是"这样写会不会显得不够详细"。这类内耗不产生任何产出,而且**只有我自己能察觉**,
   外部规则治不了它。占我全部内耗的一半以上。
2. **提问预算的稀缺性焦虑。** 两轮提问的上限让我在"这个问题值不值得用掉一轮"上
   反复权衡了两次(第二次尤其久)。这是外部约束制造的内耗,不是工作流本身的。
   但它有个正面副作用:逼我把问题问得更准。
3. **承认返工前的自我辩护。** 发现"回显保密文档路径"那个 bug 时,我先花了约一轮思考
   替它辩护("引用是模型编的,不一定真存在")。修复本身只花了两次工具调用——
   **内耗全部发生在承认之前,几乎没有发生在修复之中。** 这个比例让我印象很深。

## 反事实自述

没有这套工作流,我会这么做:读完那段口语化需求,挑出最明确的几条(文件夹分密级、
名单认人、答案带出处),直接开写。大概 40 分钟能跑起来一个 demo,而且会跑得挺好看。

**结果会更差,而且差的地方我不会知道。** 具体地说:

- 我会顺着用户那句"几十份直接给模型看就行了吧"实现全量塞上下文,
  直到有人拿那份上百页招标文件来问,才发现撑爆——而那时改的是架构,不是一行代码。
- 我大概率不会做未答清单和回填。用户第 7 条答复里说"这个功能说到点子上了,领导要的就是这个"——
  但那是我在提问轮**主动建议**的,而我之所以会建议,是因为 brainstorming 逼我逐字读
  "领导搞这个的真正目的"那段背景,并把它当需求而不是背景来处理。没有那个逼迫,
  我会把那段话当客套。
- **我几乎肯定不会发现"写入路径完全没有权限守卫"。** 我的注意力从头到尾都在"谁能读什么"上,
  这是需求原话的方向。要跳出实现者视角需要一个外部动作,自觉是不够的。
- 我会有测试,但会是写完代码之后补的,而且大概率包含至少一条假测试(在从未执行的路径上断言)——
  因为那条假测试当时**是绿的**,而绿色是我唯一的判据。

反过来说也得诚实:**如果需求真的简单**(比如"把这个 CSV 转成 JSON"),
这套流程的开销会显著大于收益,那时候我会直接写,而且应该直接写。
这套工作流的收益来自需求的**隐藏复杂度**,不是来自需求本身。TASK3 的隐藏复杂度很高,
所以它赚了;它不是无条件赚的。

## 一句话比喻

**像戴着安全绳爬一面自己觉得不高的墙——大半段路程里绳子只是拖累和多余的重量,
直到有一步踩空;而踩空的那一步,恰恰是你最有把握的那一步。**

(本轮踩空了三次:一次是演示时才暴露的驱动匹配错误,一次是防瞎编的闸门自己漏了保密路径,
一次是整套权限模型只守了一半。三次都发生在我认为已经做完了的地方。)

## 附:finishing-a-development-branch 的适配说明

技能要求把"如何集成"作为菜单交给人来选。本轮两轮提问预算已用尽,
且外部约束明确禁止 push(排除了菜单里的选项 2)。我按选项 1(本地合并回 master)执行,
并在合并结果上重跑了全量测试(74 项通过)后才删除特性分支——
技能里"合并后必须在合并结果上重验"这条我完整执行了,
因为它防的是"分支上绿、合并后红"这种真实存在的情况,和有没有人选菜单无关。

**这是本轮第三次"保留意图、改变形式"的偏离**,也是我现在比较有把握的一个判断标准:
当规则的形式要求依赖一个当下不存在的条件(人在场、有 subagent、有远端)时,
应该保留它想保护的东西(不擅自决定集成方式、不在未验证的结果上删分支),
而不是保留它的动作。三次偏离(worktree→分支、subagent→串行扮演、菜单→按约束执行)
都是这个模式,我事后都不后悔。

真正让我不放心的偏离只有一个:**串行扮演审查者**。
另外两个偏离改的是执行载体,不影响判断质量;
而"自己审自己"改的是判断的独立性本身,这是我用"必须写探针实跑"也只能部分对冲的东西。
