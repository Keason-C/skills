# 采购品类知识问答机器人 — 设计文档(spec)

日期:2026-07-31
需求方:采购部负责人(非技术背景)
状态:待需求方确认

---

## 1. 要解决的问题

采购员日常要问五类问题:某品类归谁管、有哪些供应商、以前怎么谈的、规格要求是什么、走什么流程。
答案散落在同事上传的杂格式文档里(Word/PDF/Excel/Markdown/以及打不开的怪格式)。

领导的真实目标不是"做个聊天机器人",而是:**知识落在库里,不落在人手里**。
这句话在本设计中被当作功能需求,而不是背景说明,它直接产出两个必须做的特性:

- 每条回答必须给出**出处**(哪份文档),否则同事无法把机器人当作可信的交接材料。
- 系统必须**看得见知识缺口**:答不上来的问题要沉淀成清单,人工补答后能**回填成新文档**进库,
  从而让库随使用自动变厚。

## 2. 明确的非目标(YAGNI)

- 不做向量库 / embedding / RAG 基础设施(需求方明确否决,文档量也不需要)。
- 本期不接企业微信。但对话入口与问答内核分层,以后加一层壳即可。
- 不做段落级密级标注(需求方明确否决:没人有空一段段标)。
- 不做权限系统对接工号系统(本期用管理员维护的名单文件)。
- 不让机器人自己判断"哪句话是报价、哪句是成本"(猜错一次就是事故)。

## 4. 备选方案与选型

**方案 A(否决)——全量塞进上下文。**
每次提问把所有文档全文拼进 prompt。实现最简单,但一份上百页招标文件 + 几千行 Excel 就会撑爆
上下文,且会出现"文档 A 的内容污染文档 B 的答案"。与"答得准"直接冲突。

**方案 B(否决)——向量检索。** 需求方明确否决,且几十份文档上做 embedding 属于杀鸡用牛刀,
还引入了一个需要维护的索引状态。

**方案 C(采用)——确定性检索 + 上下文预算 + 引用校验。**
不引入任何模型来做检索:用**关键词打分**(词频/BM25-lite,纯 Python,可完整单测)对文档排序,
在 token 预算内装载全文;装不下的大文档退化为**按小节装载**(按标题/页/工作表切片),
仍装不下就明确标记"这份文档太大,只读了一部分/没读",并在回答中如实告知。
模型只负责"读给定材料、组织语言、给出引用",不负责"决定读哪份"。

**为什么这个方案能压住瞎编**:模型被要求输出结构化结果(答案 + 引用的文档编号),
系统在返回给用户之前**校验引用是否指向本次真实装载的文档**。引用编造 / 引用了没装载的文档 /
返回格式不合法 —— 一律降级为"答不上来",转人工。这条校验是确定性的,不依赖模型自觉。

## 5. 架构

```
CLI (pkbot)
  │
  ├─ identity     名单文件 → 当前用户(工号/姓名/角色/负责品类)
  ├─ library      文件夹扫描 → 文档清单(含密级 = 所在文件夹)
  │    └─ ingest  按扩展名分派解析器;不认识的格式 → 记为"读不了"并说明原因
  ├─ access       按身份过滤可见文档(唯一的权限闸门,前置于一切检索)
  ├─ retrieval    关键词打分排序 → 上下文预算装载(整篇 / 节选 / 放弃)
  ├─ llm driver   接口:complete(system, messages) -> str
  │    ├─ AnthropicDriver  真实调用(只写不跑,测试从不触发)
  │    └─ MockDriver / ScriptedDriver  确定性,供测试与演示
  ├─ answering    组 prompt → 解析结构化输出 → 引用校验 → 答案 / 无答案
  └─ gaps         无答案 → 待人工清单;周报;人工补答 → 回填为新文档
```

### 5.1 磁盘布局(需求方唯一需要理解的部分)

```
library/
  public/            ← 公开文档,谁都能问
  confidential/      ← 保密文档,只有对应品类经理能问
  registry/          ← 品类-负责人对照表(Excel/CSV)
  roster.csv         ← 人员名单(管理员维护)
  faq/               ← 人工补答回填生成的新文档(自动写入)
state/
  unanswered.jsonl   ← 待人工清单
```

`roster.csv` 字段:`工号,姓名,角色,负责品类`。角色取值 `采购员` / `品类经理` / `管理员`。
负责品类多个用 `;` 分隔。Excel 可直接另存为 CSV,填写门槛低。

### 5.2 各单元职责与边界

| 单元 | 做什么 | 依赖 | 可独立测试 |
|------|--------|------|-----------|
| `identity` | 读名单,解析当前用户 | 文件系统 | 是 |
| `ingest` | 单个文件 → 纯文本 + 结构(节/页/表) | 解析库 | 是,给定 fixture 文件 |
| `library` | 扫目录 → 文档集合 + 读不了清单 | ingest | 是 |
| `access` | (用户, 文档集合) → 可见子集 | 无 | 是,纯函数 |
| `retrieval` | (问题, 可见文档, 预算) → 装载包 | 无 | 是,纯函数 |
| `driver` | 文本进文本出 | 网络(仅真实实现) | 是,用 mock |
| `answering` | 装载包 + 问题 → 结构化答案 | driver | 是,用 mock |
| `gaps` | 记录 / 出周报 / 回填文档 | 文件系统 | 是 |

每个单元一个文件,不超过几百行,边界即函数签名。

## 6. 数据流(一次提问)

1. `pkbot ask "不锈钢紧固件归谁管" --user G0042`
2. identity:G0042 = 李四 / 采购员 / 负责品类 无
3. library:扫描 → 12 份可读文档,2 份读不了
4. **access:采购员 → 只保留 public/ 与 registry/,confidential/ 全部剔除**
5. retrieval:关键词打分 → 对照表命中最高,装载全文;招标文件超大 → 只装匹配小节
6. answering:组 prompt(系统提示强制"只能用给定材料,必须给引用,不确定输出 no_answer")
7. driver 返回 JSON → 解析 → 校验引用 doc_id ∈ 本次装载集合
8. 输出:答案 + `依据:《品类负责人对照表》第 3 行` + (若有)`注意:《XX招标文件》太大,仅阅读了部分章节`
9. 若 no_answer:屏幕提示"这个问题已记录,会有人跟进",写入 `state/unanswered.jsonl`

## 7. 错误处理

| 情况 | 行为 |
|------|------|
| 文件格式不认识 / 加密 PDF / 扫描件 | 不猜内容;记入"读不了"清单;`pkbot library status` 可查 |
| 文档太大装不下 | 按小节装载;仍不行则跳过,并在回答中明确告知"这份没读全" |
| 模型返回不合法 JSON | 视为答不上来,转人工(绝不把原始文本当答案吐出) |
| 模型给的引用不在装载集合里 | 视为答不上来,转人工(这是防瞎编的硬闸门) |
| 名单里没有这个工号 | 拒绝服务并提示联系管理员(不默认给最低权限,避免身份含糊) |
| 品类经理问不属于自己品类的保密内容 | 按不可见处理,走转人工 |

## 8. 测试策略

- 全部离线。真实 LLM 调用只存在于 `AnthropicDriver`,测试从不实例化它(有一条测试断言"默认
  driver 在测试环境下不是真实 driver")。
- 解析器测试用真实生成的 fixture 文件(用 python-docx / openpyxl / reportlab 在 conftest 里生成
  .docx / .xlsx / .pdf),保证不是拿字符串假装解析。
- 权限测试是重点:采购员看不到保密文档、品类经理只看得到自己品类的保密文档、越权提问必须
  走转人工且**不得泄露"存在这样一份文档"以外的任何内容**。
- 引用校验测试:喂给系统一个"编造引用"的 mock 返回,断言输出降级为无答案。
- 端到端测试用 ScriptedDriver 跑完整 CLI。

## 9. 演示路径

```
uv run pkbot library status --user G0001      # 看库里有什么、哪些读不了
uv run pkbot ask "不锈钢紧固件归谁管" --user G0042    # 采购员,公开问题
uv run pkbot ask "去年和某供应商谈到什么价" --user G0042  # 采购员,保密 → 转人工
uv run pkbot ask "去年和某供应商谈到什么价" --user G0007  # 品类经理,可见
uv run pkbot gaps report                       # 本周问了多少、几个没答上
uv run pkbot gaps answer <id> --text "..."     # 人工补答 → 回填成新文档
```

## 10. 权限口径(需求方已确认)

1. **越权提示可见**:采购员问到保密内容时,明确告知"涉及保密资料,已记录并转给品类经理",
   而不是装作库里没有。理由(需求方原话):同一部门内应让人知道该找谁;装作没有会让同事
   误以为公司没有这块知识,统计也会被弄脏。
   → 实现含义:越权时可以暴露"存在相关保密资料"这一事实**以及该品类的负责人姓名**,
   但不得暴露文档标题、内容或任何正文片段。
2. **品类经理按品类隔离**:只能看自己负责品类的保密文档。管紧固件的经理查不了电子元器件的
   历史报价,必须转给对应品类经理。名单中"负责品类"一栏即为此设计。
   → 实现含义:`access` 的可见性判定是 (角色 == 品类经理) AND (文档品类 ∈ 用户负责品类)。
3. **回填文档默认公开**:人工补答生成的新文档默认写入 `library/public/faq/`;
   补答人可显式标记为保密,则写入 `library/confidential/faq/`。

### 附:保密文档的"品类"从哪来

`library/confidential/` 下按品类建子目录,例如 `library/confidential/紧固件/xxx.docx`。
子目录名即该文档的品类,与名单里"负责品类"一栏的字符串精确匹配。
直接放在 `confidential/` 根目录、不属于任何子目录的文档,视为"未分类保密文档",
仅管理员可见 —— 避免出现"没人管所以谁都能看"的漏洞。
