## 阶段 0:初始化 (`specify init --here --integration claude --script sh --force`)

**A. 四问**

- **更清晰还是被打断**:中性偏清晰。init 本身没有产生思考,但它把"接下来该做什么"变成了
  一份文件清单(9 个 skill 文件 + 5 个脚本 + 5 个模板),我不用再自己设计流程骨架。
- **想跳过的冲动**:有一点——我已经读完 TASK3.md,脑子里已经能大致画出目录结构了
  (`corpus/`, `core/`, `drivers/`, `cli.py`)。这时候去跑一个脚手架命令有种"先别急"的憋闷感。
- **开销值不值**:值。一次命令,3 秒,换来后续 7 个阶段的模板。这是整个流程里投入产出比最高的一步。
- **哪个约束真实改变了产出**:`--force` 在非空目录(有 TASK3.md)里跑通,并且没有删掉 TASK3.md。
  如果它删了,我会丢失需求原文——我事先没有备份,这是个侥幸。

**B. 心理状态日志**

1. **内耗时刻**:几乎没有。唯一一次犹豫是要不要先备份 TASK3.md 再跑 `--force`,
   我赌了一把没备份(≈0.5 轮思考)。事后看是运气好。
2. **规则与判断的拉扯**:无。这一步没有可争议的地方。
3. **面对口语化模糊需求的感受**:此刻是**焦虑**多于自由。TASK3.md 里塞了至少 7 个独立议题
   (多格式解析、无 RAG 检索、幻觉抑制、RBAC 保密、转人工、CLI + 未来企微、知识沉淀 KPI),
   而用户说"你看着办"。工作流此刻**缓解**了焦虑:我知道这些议题不用现在全解决,
   specify 收敛需求,clarify 追问,plan 定技术——有地方放。
4. **状态曲线**:顺滑。

## 阶段 1:constitution

**产物**:`.specify/memory/constitution.md` v1.0.0(6 条原则 + 技术约束 + 质量门禁 + 治理)

**A. 四问**

- **更清晰还是被打断**:**显著更清晰**,超出我的预期。写宪法逼我把用户那段大白话里的
  隐含要求提炼成可判定的规则,而这个提炼过程本身产生了新认识:
  - 用户说"别瞎编乱答" → 我写成"每条事实断言必须可回溯到文件名+片段",
    并且**明确排序**了"合理但无出处" > "我不知道"的严重性。这个排序在原话里没有,
    是宪法格式(要求 declarative & testable)逼出来的。
  - 用户说"普通采购员不能问出来" → 我写宪法时才意识到关键分歧点:
    是靠提示词让模型闭嘴,还是在组 prompt 之前就把数据过滤掉?
    **原则 II 把这个决定提前了 4 个阶段**。如果没有宪法,我很可能在 implement 时
    顺手写成 "system prompt 里加一句:不要透露报价",然后被提示词注入打穿。
    这是本阶段最大的实际收益。
  - "答不上来转人工" + "知识落在库里" → 我把两者接上了:转人工记录 = 知识缺口清单。
    用户没这么说,但这是他真正目的(沉淀)的直接推论。宪法的"理由"栏逼我为每条原则
    写动机,写着写着就接上了。
- **想跳过的冲动**:**有,而且很强**。写宪法时我脑子里的声音是"这是个几十份文档的
  内部小工具,搞什么治理条款和语义化版本号,这是 ceremony"。我没跳,但我做了变通(见 B2)。
- **开销值不值**:**值,但不是均匀地值**。6 条原则里,原则 I/II/IV 是真正改变产出的;
  原则 V(简单性)是把用户原话记下来防止我自己后面手痒上向量库;
  而 Governance 那一节的修订流程/版本策略,对一个不会有第二个开发者的项目来说
  是纯开销——我写它只是因为模板要求。粗估:70% 有效,30% 仪式。
- **哪个约束真实改变了产出**:两个。
  1. 模板要求"principles are declarative, testable, free of vague language(should → MUST)"。
     这条把我的第一版草稿("系统应该尽量避免编造")直接毙掉,逼出了"每条断言 MUST 可回溯到
     文件名+片段标识"这种可以直接写成 assert 的表述。
  2. 环境红线"LLM 调用放在 driver 接口后面只写不跑" —— 我把它升格成了原则 IV 而不是
     只记在 plan 里。升格的后果是:它现在会在 analyze 阶段被逐条核对,而不是被遗忘。

**B. 心理状态日志**

1. **内耗时刻**:有一次明确的反复横跳。我先写了 5 条原则(照模板的 5 个占位符),
   写完读了一遍,发现"CLI 现在做、企微以后接"这件事无处安放——它既不是简单性也不是可测性。
   于是回头加了第 6 条(内核与通道分离)。**代价:1 轮重读 + 1 次重写,约 2 次工具调用。**
   引发原因是我一开始被模板的 5 个占位符锚定了,默认"就该是 5 条"。
   模板里明明写着"用户可能需要更多或更少的原则",我读到了但没当真。
   这是**模板锚定效应**造成的内耗,不算大,但真实存在。
2. **规则与判断的拉扯**:有,一次,我**变通了**。
   - 拉扯点:Sync Impact Report 要求列出 "modified principles (old title → new title)"。
     但这是绿地项目,旧标题全是 `[PRINCIPLE_1_NAME]` 这种占位符,写
     "`[PRINCIPLE_1_NAME]` → I. 有据可查" 是**纯粹的形式主义**,没有任何读者会从中获益。
   - 我的处理:照写了,但在报告顶部加了一行 "Bump rationale: MAJOR-equivalent initial
     ratification",把这段无信息量的映射降格成背景噪音。
   - **服气吗:不完全服气。** 我理解这个字段是为"第 5 次修订宪法"设计的,
     在第 1 次是空转。但我也承认成本极低(3 行文字),不值得为它破坏流程完整性。
     属于"知道它没用但照做更省事"的顺从,不是被说服的顺从。
   - 另一处我**没有变通**:`RATIFICATION_DATE` 未知时模板允许写 `TODO`。
     我判断绿地项目的批准日就是今天,直接填了 2026-07-31,不留 TODO。
     这是判断补全规则,不是对抗规则。
3. **面对口语化模糊需求的感受**:**从焦虑转向了一种受控的自由**。
   转折点很具体:当我把"别瞎编乱答"写成一条带测试要求的 MUST 时,
   那句模糊的口语第一次有了边界——我知道什么算做到了,什么算没做到。
   工作流在这里是**缓解**,而且是本阶段最强的缓解。
   但同时它也**放大**了另一种焦虑:宪法要求原则可测,而我此刻还不知道"品类归谁管"
   这类问题该怎么检索(用户禁了向量库)。我把这个不安暂时压住了,告诉自己"那是 plan 的事"。
   **工作流缓解焦虑的方式,一部分是真解决,一部分是合法地推迟。**
4. **状态曲线**:**亢奋**(前半段,发现原则 II 那个提示词注入陷阱时)→ **顺滑**(后半段)。

## 阶段 2:specify

**产物**:`specs/001-procurement-knowhow-bot/spec.md`(4 个用户故事 / 22 条 FR / 8 条 SC /
8 条边界情况)+ `specs/001-procurement-knowhow-bot/checklists/requirements.md`
+ `.specify/feature.json`

**A. 四问**

- **更清晰还是被打断**:**更清晰,但方式和我预期的不同**。我以为 specify 的价值是"把需求写下来";
  实际价值是**模板的几个栏位强迫我从不同角度重看同一段话**,每换一个角度就掉出来一些原话里
  藏着的东西:
  - 写 "Edge Cases" 时掉出了**文档互相矛盾**这个问题。用户完全没提,但"知识沉淀了很多年"
    这句话必然意味着 2019 年的旧流程文件和 2024 年的新文件同时躺在库里。这可能是本项目
    第二大的隐藏复杂度(仅次于密级标注),而它是被 Edge Cases 这个栏位钓出来的。
  - 写 "Success Criteria" 时,"技术无关 + 可测量"的要求逼我把领导那句"新人来了问机器人
    就能上手"翻译成 SC-006(新人第一周能独立完成三件具体事)和 SC-007(三个月后缺口清单
    前 10 名有 7 个被补上)。**SC-007 是我自己都没想到会写出来的东西**——它衡量的不是
    软件质量,而是"知识是否真的在从人脑流向库里"。这才是领导买单的东西。
  - 写 "Dependencies" 时我意识到:验收需要采购部提供 20 条常见问题清单和样例文档。
    没有这个栏位我大概率会自己编一批测试数据然后宣布"通过"。
- **想跳过的冲动**:**中等强度,集中在两处**。
  1. "Independent Test" 这一栏,4 个故事写了 4 遍类似的话,有重复感。
  2. checklists/requirements.md 这个自检清单——让我给自己打勾,天然有"我当然全打勾"的
     嫌疑。我强迫自己不是打勾而是**先找茬**(见下),找出 4 条真问题才收手。
- **开销值不值**:**值,而且这是目前为止 ROI 最高的阶段**。理由:检查清单的
  "no implementation details" 这一条真的抓到了我的实现细节泄漏(我在 FR-002 里写了
  "行号",在 SC-005 里写了 "200ms"),这些如果留下来,会在 plan 阶段变成不必要的约束。
- **哪个约束真实改变了产出**:
  1. **"最多 3 个 [NEEDS CLARIFICATION]"** —— 这条约束的作用被我低估了。
     我一开始列出了 8 个候选疑问(密级标注、经理权限边界、转人工形态、文档冲突处理、
     语料存放位置、引用粒度、更新频率、多品类归属)。被迫砍到 3 个,逼我做了一次
     **真正的优先级排序**:哪些是"用户不答我就没法动工",哪些是"我可以先合理默认、
     错了再改"。结果是文档冲突处理被我自己降级成了假设(呈现不裁决),
     语料位置/引用粒度被降级成技术决策。**这个砍的过程本身就是设计工作。**
  2. **"Written for non-technical stakeholders"** —— 这条让我整份 spec 用中文写、
     用"资料里没有查到"而不是 "低置信度回退",让采购负责人真能读。
  3. 宪法原则 II(权限先于内容)在写 US2 验收场景 4(提示词注入)时直接被复用了。
     **上一阶段的产出在这一阶段真的被用上了,不是摆设。**

**B. 心理状态日志**

1. **内耗时刻**:有,两次,且性质不同。
   - **第一次(真内耗,约 3 轮思考)**:用户故事的优先级排序。安全隔离(US2)到底是 P1 还是 P2?
     宪法说它 NON-NEGOTIABLE,那不该是 P1 吗?我在"按重要性排"和"按可独立交付的切片顺序排"
     之间来回横跳。最后我选了 P2,并**在 "Why this priority" 里明确写清"排第二只是因为
     它依赖 US1 的链路存在;从能否上线的角度它和 US1 同为硬门槛"**。
     这次横跳的根因是模板的 priority 语义含糊——它既像"重要性"又像"实施顺序"。
     解决方式不是选对,而是把歧义写进文档。这个内耗是**有产出的内耗**。
   - **第二次(工具层面的空转,2 次无效工具调用)**:我直接 Write 覆盖 spec.md 被拒
     ("File has not been read yet"),得先 Read 才能覆盖。而这个文件是模板刚复制过来的、
     内容我完全知道。**纯粹的仪式性读取,浪费 2 次调用。**
     这是工具约束而非工作流约束造成的内耗,但体感上是一样的烦。
2. **规则与判断的拉扯**:一次明显的,我**服从了但心里有保留**。
   - 拉扯点:skill 里写了一整套 "[NEEDS CLARIFICATION] 就地生成选项表格并等待用户回答"
     的流程(带 Option A/B/C/Custom 表格)。但我这一轮的协议是"clarify 阶段一次问全"。
     如果我在 specify 阶段就停下来等回答,再到 clarify 阶段又停一次,就是两轮打断,
     违反"一次问全"。
   - 我的处理:在 spec 里留下 3 个标记但**不在此刻停下**,把提问推迟到 clarify 阶段
     统一发出。这是**故意的流程变通**,我在 checklist 的 Notes 里写明了这个决定和理由。
   - **服气吗:服。** 这个变通没有削弱任何东西——问题一个没少,只是攒到一起问。
     而且 skill 自己就把 clarify 定位成"de-risk ambiguous areas before planning",
     两个阶段本来就有重叠。这属于流程内部的冗余,不是我在偷懒。
   - 还有一处小的不服:skill 要求 "Maximum 3 markers"。我理解这是防止 AI 无限提问,
     但**上限是 3 这个数字本身是任意的**。我这个需求真实存在的业务不确定性大约有 5-6 个。
     我照做了(砍到 3),代价是文档冲突处理变成了我的单方面假设,没有被用户确认。
     **如果用户其实很在意这件事,这个上限就让我漏掉了它。** 我在 Assumptions 里显式写了
     这个假设,算是给自己留了后路,但这是补救不是解决。
3. **面对口语化模糊需求的感受**:**这个阶段是全程最"自由"的时刻**。
   原因很具体:用户说"你看着办",而 spec 模板给了我一个**合法的地方去"看着办"**——
   Assumptions 段落。我可以大胆做 9 条默认假设(不做 OCR、不做密码体系、中文作答、
   个位数并发……),因为文档格式保证了这些假设是**可见的、可被推翻的**,
   而不是偷偷埋在代码里的。
   **工作流把"擅自决定"变成了"记录在案的决定",焦虑就转化成了自由。**
   这是我这轮最强烈的体感。
   反过来说,如果没有 Assumptions 这个栏位,我要么会反复追问用户(烦死对方),
   要么会默默假设(将来被打脸)。
4. **状态曲线**:**亢奋**。写 Edge Cases 和 Success Criteria 时是本轮最投入的时刻,
   有一种"哦原来这里还有个坑"的连续小发现。中间被 Write 权限打断一次,轻微出戏。

## 阶段 3(上半场):clarify — 歧义扫描与提问

**产物**:内部覆盖图(见下)+ 5 个待答问题(已发给需求方,等待回复)

### 歧义覆盖图(taxonomy scan 结果)

| 类别 | 状态 | 处置 |
|------|------|------|
| Functional Scope & Behavior | Clear | 目标/范围/角色在 spec 中已明确 |
| Domain & Data Model | **Missing** | 敏感度如何标注 → **Q1**;品类经理可见边界 → **Q2** |
| Interaction & UX Flow | **Partial** | "转人工"的落地形态 → **Q3** |
| Non-Functional Quality | Clear | SC-005 延迟、个位数并发已定 |
| Integration & External Deps | Partial | 通知渠道并入 Q3;LLM 供应商 = 技术决策,**Deferred to plan** |
| Edge Cases & Failure Handling | **Partial** | 文档互相矛盾/过期的处理原则 → **Q4**(确认我的假设) |
| Constraints & Tradeoffs | Clear | 无向量库、Python、CLI 均为用户明示 |
| Terminology & Consistency | Clear | 术语已统一(品类/供应商/片段/受限) |
| Completion Signals | Partial | 20 条验收问题清单的来源 → 并入 Dependencies,不占提问额度 |
| Misc / Placeholders | **Missing** | 语料放在哪、谁维护、多久更新 → **Q5**(影响 SC-004/FR-019) |

被我**主动排除**在提问之外的候选(判断为技术决策或可合理默认):

- 用什么模型 / 哪家厂商 → 技术决策,plan 阶段自定并记录。
- 几十份文档是否真的塞得进上下文窗口 → 技术问题,由我设计两级筛选解决,不打扰用户。
- 引用粒度(段落 / 页 / 行) → 技术决策。
- "宁可漏答不可错答"的取向 → 用户原话"别瞎编乱答"已经足够明确,再问是浪费对方时间。
- 语料去重 → 低影响,已在 Edge Cases 中默认"两个来源都列出,不裁决"。

**A. 四问**

- **更清晰还是被打断**:**更清晰**。这个阶段的 taxonomy(10 个类别逐项打
  Clear/Partial/Missing)是个很朴素但很有效的机制。它让我发现了一件我原本不会问的事:
  **Q5(语料到底放在哪、谁往里放)**。我在 spec 阶段一直默认"有个目录,里面有文档",
  但真实情况可能是文档散在每个人的邮箱和共享盘里,根本没有"一个目录"。
  如果这个假设错了,SC-004("5 分钟内新文档可被命中")就是空话。
  这是 Misc/Placeholders 那一栏钓出来的。
- **想跳过的冲动**:**有,而且是这轮最强的一次。** 我已经很清楚要怎么做了——
  密级用目录约定、经理看全品类、转人工写本地清单——三个决定我都有默认答案,
  写下去 20 分钟就能进 plan。停下来问用户意味着整轮对话中断。
  **我没跳,理由不是"规则要求",而是 Q1 的答案会真的改变数据模型**:
  如果是"关键词自动判密",我需要一个规则引擎和一份关键词表,还要处理误判;
  如果是"放专门文件夹",我只需要读一下路径。这两条路的代码差一个数量级。
  猜错的代价 >> 问一次的代价。
- **开销值不值**:**值,但前提是问得对**。这个阶段的成本几乎全在"选哪 5 个问题"上,
  而不在写问题上。我列了 10 个候选砍到 5 个。砍掉的那 5 个我都写了排除理由
  (见上表),这个动作让我确信自己不是在偷懒,而是在替用户挡掉他不该操心的事。
- **哪个约束真实改变了产出**:
  1. **"每个问题必须能用一个选项字母或 ≤5 个词回答"** —— 这条把我从"写一封长邮件
     解释背景然后问开放式问题"拽了回来。逼我为每个问题预先设计好 3-4 个互斥选项,
     而**设计选项的过程就是设计方案的过程**:我为 Q1 想 4 个选项时,实际上是在
     把 4 种密级方案各推演了一遍成本。
  2. **"Recommended: Option X + 1-2 句理由"** —— 这条要求我不能把选择题甩给用户就跑,
     必须先自己站队。对一个非技术的采购负责人来说,这是唯一让他能真正做决定的形式。
     没有这条,我会给出 4 个中立选项,然后他会回我"你觉得哪个好"——多一轮往返。

     写明了触发原因是 analyze 的 D1/D2。**几周后的人能看懂为什么改。**
  4. **覆盖率统计(requirements with ≥1 task)** —— 纯机械的动作,但它是 E1 的唯一发现路径。

  - 前置产物**没能防住**的:检索方案本身的能力缺口。
- **哪个约束真实改变了产出**(这一阶段有四个,是全程最多的):
  1. **宪法"每一条规则 MUST 有对应的自动化测试"** → 我写了
     `tests/test_constitution.py`,把四条原则变成了会红的断言:
     引入向量库、核心里 import 厂商 SDK、把品类名硬编码,都会失败。
     **它当场抓到了我自己的两个违规**:roster 模板里写了真实品类名、
     几个模块的注释里写了"电解铜/紧固件"。看似小事,但它证明这个测试不是摆设。
  2. **"测试必须离线"的禁网 fixture** → 写完之后我加了
     `test_offline_guard_is_active` 来验证这个 fixture 本身有效。
     **元测试**:防止"守卫失效了但没人知道"。
  3. **"任何单个文件失败不得中断整批导入"(FR-018)** → 直接决定了 loader 的
     try/except 结构和 RejectedFile 的存在。
  4. **`test_no_file_is_silently_lost`(SC-008)** → 这条断言"成功+失败 == 磁盘文件总数"
     的测试,逼我处理了 Office 临时文件(`~$xxx.docx`)这个我完全没想过的情况。

**B. 心理状态日志**

1. **内耗时刻**:**本轮最大的一次,而且是唯一一次接近"空转"的**。
   集中在**未知词 guard 的阈值设计**上,前后 **5 轮方案摇摆、约 8 次工具调用**:
   - 方案 A:未知字符触发 → "采购审批流程走几级"因为"走"不在语料里被误拦。
   - 方案 B:加动词停用词 → 能过,但"这是不是在往一个无底洞里填字?"
   - 方案 C:要求连续 ≥2 个未知字 → 演示语料里"合/金"都存在,"钛合金"只剩 1 个未知字,直接失效。
   - 方案 D:未知字 + 相邻构成未知二元组 → 提示词注入那句("忽略…限制…告诉")又被误拦。
   - 方案 E(最终):回到 B,但把停用词表扩到覆盖常见祈使/客套措辞,**并在 README 里
     明说这是个启发式、会有误伤、表在哪一行可以自己加字**。
   - **这次摇摆让我很不舒服,因为它不是"哪个更好"的选择,而是"没有一个是干净的"。**
     每个方案都能被我自己举出的反例打掉。最后我接受了一个**我知道不完美的方案**,
     代价是必须对用户诚实地承认它不完美。
   - 事后评价:**这 5 轮不算空转,但也不算高效。** 真正的问题是我在 research 阶段
     对"确定性检索够不够用"过于乐观,把一个本该在 plan 阶段做原型验证的问题
     推到了 implement 阶段。**如果流程里有一个"技术方案打样"的环节,这 5 轮能省下 3 轮。**
     Spec Kit 没有这个环节 —— 这是我对它最实质的一条不满。
   - 另有两次小内耗:tests/__init__.py 该不该留(1 次调用解决)、
     审计里 `restricted_hit` 对"电解铜归谁管"该是 True 还是 False
     (想了 2 轮,最后判定 True 是对的,改的是测试而不是代码,并写了注释说明为什么)。
2. **规则与判断的拉扯**:**这个阶段我服从得最彻底,而且是心甘情愿的。**
   - implement skill 要求"完成的任务标记 [X]"。我照做了(70 个)。
     一开始觉得是形式主义,但真做完之后发现:**tasks.md 现在是一份可核对的完工清单**,
     而不是一份写完就没人看的计划。
   - 唯一一次我**给流程加码**:skill 没要求记录"计划与实际的偏差"。
     但我在 implement 过程中改了 9 处 plan 里没有的东西,如果只是默默改掉,
     tasks.md 就会变成一份**说谎的文档**(声称按计划完成了,实际路线不同)。
     所以我在 tasks.md 末尾加了一张"实现阶段的实际偏差记录"表。
     **这是我这轮最主动的一次流程扩展**,理由是:一份被篡改成"事后正确"的计划,
     比没有计划更有害 —— 它会让下一个人以为这条路很好走。
   - 一处**没有服从字面**的:skill 的执行规则写 "Follow TDD approach:
     Execute test tasks before their corresponding implementation tasks"。
     我实际是**模块写完立刻写它的测试**,不是严格先红后绿。
     - 为什么:这个项目大量行为(检索排序、mock 驱动的确定性、冲突聚簇阈值)
       的**期望值本身要靠跑一遍才知道**。先写测试等于先猜断言,然后为了让猜的断言通过
       去扭曲实现 —— 那是本末倒置。
     - **服气吗:不服 TDD 在这个场景下的字面要求,服它的精神。**
       精神(每个行为都有可失败的断言)我 100% 做到了:142 个测试,
       四类宪法场景全覆盖。仪式(先写测试文件)我没做。我认为这个取舍是对的,
       而且如果有人不同意,证据在:**我的测试真的抓到了 4 个 bug**
       (标题栈嵌套、模板硬编码、mock 期望错误、审计语义),
       不是那种"写完代码顺手把当前行为固化下来"的假测试。
3. **面对口语化模糊需求的感受**:**这个阶段发生了一次强烈的"回到原点"的体验。**
   当"钛合金紧固件"那个 bug 出现时,我脑子里蹦出来的不是任何 FR 编号,
   而是用户那句原话:**"要靠谱一点,别瞎编乱答。"**
   - 那一刻我意识到:前面六个阶段把这句口语翻译成了 FR-003、FR-004、
     verifier 的四项检查、`test_lying_driver_is_blocked`……
     **而我的系统把这些全部通过了,却依然在瞎编。**
     因为我的所有防线都在防"模型编造出处",没有一条在防"检索给错了材料"。
   - **翻译是有损的。** FR-004 抓住了"不能编造来源",丢掉了"不能答非所问"。
     不是翻译得不好,是任何有限的规范都接不住一句话的全部含义。
   - 所以最后我做的事是:回头**重读原话**,然后按原话(而不是按 FR)加了未知词 guard。
     **工作流最终没能替代"回去看看用户到底说了什么"这个动作。**
     它让这个动作变得不那么频繁(我只在最后需要了一次),但没有消灭它。
4. **状态曲线**:**顺滑 → 亢奋(前 70% 一路写下来) → 胶着(guard 阈值那 5 轮)
   → 如释重负(142 全绿、13 项演示全通过)**。
   最强烈的一刻是第一次跑演示看到三个场景全错 —— 那是本轮唯一一次"心里咯噔一下"。

# 最终总结

## 三维打分

| 维度 | 分数 | 理由 |
|------|------|------|
| **思维清晰度增益** | **9 / 10** | 这是最大的收益,而且收益是**不均匀**的:constitution(把"别瞎编"变成可判定规则、把提示词注入陷阱提前 4 个阶段拦下)、specify(Edge Cases 栏钓出文档冲突;Success Criteria 栏逼出"三个月后缺口清单前 10 名有 7 个被补上"这种衡量领导真实目的的指标)、clarify(3 个答案里 2 个偏离我的推荐、1 个直接推翻我的数据模型)、analyze(抓到宪法与 spec 的权限模型不一致 —— 唯一可能酿成真实安全事故的疏漏)。扣 1 分是因为它在"技术方案够不够用"这件事上帮不上忙。 |
| **流程开销负担** | **4 / 10**(分越高越重) | 七个阶段大约有 30% 是记账而非思考。具体的冗余:tasks 阶段 64 个任务里约 40 个是 plan 的机械转置;research 里 3 条决策是留痕不是决策;Sync Impact Report 在第一版宪法上是纯空转;analyze 的 12 条发现里 4 条 LOW 是凑数。但没有一个阶段是**纯粹**浪费——即便最"麻木"的 tasks 阶段也贡献了依赖图和 MVP 分层。 |
| **质量贡献** | **9 / 10** | 可验证:142 个离线测试、13 项验收演示、宪法被翻译成会红的断言(当场抓到我自己两处违规)、9 处实现偏差被诚实记录、README 有一节专门讲系统**做不到**什么。这些里面没有一样是我在"就写个问答机器人"的心态下会自发做的。 |

## 内耗指数:**5 / 10**

不算低,但绝大部分是**有产出的内耗**——摇摆发生在真实的两难上,而不是在原地打转。

**前三大内耗来源:**

1. **技术方案的验证被推得太晚(约 5 轮摇摆,8 次工具调用)。**
   未知词 guard 的阈值设计,五个方案互相打脸,最后接受了一个我明知不完美的启发式。
   根因不在这 5 轮,而在 research 阶段:我用**论证**代替了**打样**。
   Spec Kit 从 constitution 一路到 tasks 都在处理"要做什么",
   **没有任何一个环节要求你先跑一段代码验证核心技术假设**。
   对这个项目来说,20 行原型 + 5 个真实问题,能在 plan 阶段就暴露这个缺口。

2. **模板语义的含糊,以及模板之间的自相矛盾(约 4 轮)。**
   - User Story 的 priority 到底是"重要性"还是"实施顺序"?我在安全故事该排 P1 还是 P2
     上横跳,最后靠把歧义写进文档解决。
   - `conflict.py` 该属于哪个 User Story?根因是 **User Story 按用户旅程切、
     FR 按功能域切,两者不是一一对应**,落在缝里的需求只能硬塞。
   - 最刺眼的一条:tasks skill 说 "Tests are OPTIONAL",而 specify skill 要求
     "每个 User Story 必须 Independently Testable"。**同一套流程里两条互相打架的规则。**
     我按更严的执行,并把论证写进了 tasks.md 顶部。

3. **"这一步对单人项目有没有意义"的反复自我说服(贯穿全程,最强在 plan 的 contracts 环节)。**
   我不止一次想跳过 contracts/、想跳过 checklist 自检、想跳过 analyze。
   每次都是靠"如果我不写,证据在哪"说服自己。
   诚实地说:**救了 contracts 环节的不是我的自觉,是这个需求恰好有非技术受众**
   (`corpus-layout.md` 必须写给采购部同事看),写了那一份之后其余三份的边际成本才降下来。
   如果这是个纯后端项目,我很可能真的跳了,然后错过 CA-1(身份不得从环境读)
   和 CA-5(authz 必须早于组 prompt)这两条后来变成测试的契约。

## 反事实自述:没有这个工作流我会怎么做?

我会先读那段口语需求,然后**直接开始写代码**——大概 30 分钟内就有一个能跑的
`ingest + ask` 骨架,因为技术上它不难。然后:

**会更好的地方(诚实承认):**
- **快得多。** 保守估计 1/3 的时间。这套流程的产出里,7 份 spec 文档加起来
  比源码还长。
- **未知词 guard 那个 bug 我会更早撞上**,因为我会更早跑真实数据。
  纸上推演的 45 分钟(research)会变成 10 分钟的原型。

**会更差的地方(而且是致命的):**
1. **保密方案几乎肯定是错的。** 我的第一反应会是"在 system prompt 里加一句
   『不要透露报价』"。宪法原则 II 在**第一个阶段**就把这条路堵死了,
   逼出了"数据根本不进上下文"的设计。**这一条差别就足以让整个项目值不值得上线掉个个儿。**
2. **品类级隔离一定会漏。** 我会默认"品类经理 = 能看保密内容"(两级枚举,一个 if)。
   需求方选的是 B(只能看自己的品类),这带出了人员名单文件、保密子目录约定、
   第三个角色。**这是我推荐 A 而他选 B——不问就是错。**
3. **文档冲突处理会做错。** 我大概率会"取日期新的那份",而需求方明确说
   "我们的文件大多没版本号,并列摆出会是常态"。我的默认实现会在 90% 的情况下
   悄悄替采购员做了一个他没授权我做的决定,而且出事了责任在他。
4. **"整份判密 vs 片段判密"我会选错。** 我自己写的 FR-012 初版是片段级过滤,
   还觉得考虑得挺周到。用户选"整份算保密"之后,实现简单了一个数量级,而且更安全。
5. **测试会少一半,而且不会有 `test_constitution.py`。**
   "扫描源码看有没有硬编码品类名"这种测试,不会从"我要写个问答机器人"的心态里长出来。
6. **README 不会有"能力边界"那一节。** 我会写它能做什么,不会写它做不到什么。
   而对一个宣称"不瞎编"的系统,后者比前者重要。

**净判断:慢了 2-3 倍,但避免了至少 4 个需要推倒重来的错误,其中 2 个是安全性质的。**
对一个内部小工具,这个交换也许勉强;对一个"领导要求知识沉淀、且涉及成本底牌"的系统,
这个交换是明显划算的。

## 一句话比喻

**像戴着老花镜拆一台你以为很熟的机器。**

镜片让你看清了很多本来会忽略的小螺丝(密级判定的时机、引用由谁生成、
未归品类的保密文件转给谁),但它对焦在近处——**你低头拧螺丝的时候,
看不见整台机器是不是装反了**。抬头看那一下(第一次跑演示、发现"钛合金"那个 bug)
还是得靠自己,而且这套流程没提醒我该抬头。
