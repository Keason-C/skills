**Feature**: 001-procurement-knowhow-bot | **Date**: 2026-07-31

本文件记录**技术决策**。业务决策见 `spec.md` 的 `## Clarifications`。
按澄清协议,技术决策由实现方自行决定并在此记录,不打扰需求方。

## D-01 检索方式:确定性词元打分,不用向量

**Decision**: 自实现一个确定性检索器 `retrieval.py`。中文按**字符二元组(bigram)**切分,
英文/数字按单词切分,大小写归一。打分 = Σ(命中词元的 IDF) × 位置权重
(标题/表头命中加权 2.0,正文 1.0),再按片段长度做轻度归一。全部为整数/浮点算术,
无随机性,同一输入永远同一输出。

**Rationale**:

- 用户明确否决向量库("太重了"),宪法原则 V 将其固化为禁令。
- 中文没有空格分词。可选方案是引入 `jieba`,但那是一个 ~40MB 带词典的运行时依赖,
  为几十份文档引入不划算,且分词错误会静默降低召回。**字符 bigram 不需要词典**,
  对"电解铜"这类专有名词的匹配效果反而更稳定(它会同时命中"电解""解铜")。
- IDF 可从语料本身现算(几十份文档,毫秒级),不需要预训练资源。
- 可解释:每次命中都能报告"命中了哪几个词元、各贡献多少分",符合宪法原则 V
  "结果 MUST 可被人复现和解释"。

**Alternatives considered**:

| 方案 | 否决理由 |
|------|----------|
| 向量库 + embedding | 用户明确否决;宪法原则 V 禁止 |
| jieba 分词 + BM25 | 依赖过重(词典),分词错误不可见;bigram 已够用 |
| 全文一次性喂给模型 | 几十份 Word/Excel 展开后远超上下文窗口;且成本与延迟不可控 |
| SQLite FTS5 | 需要建库与维护,且中文分词仍需 tokenizer;标准库方案已够 |

**已知代价**:问法与文档用词差异大时会漏召回(问"铜" vs 文档写"Cu-CATH-1")。
按"宁可漏答不可错答"处理为诚实的"不知道"。已写入 spec 的 Assumptions 与 Edge Cases。

## D-02 "不搞 RAG"与"塞不下上下文"的调和:两级筛选

**Decision**: 采用 **粗筛(全部片段打分)→ 取 Top-K(默认 K=12,可配置)→ 组 prompt** 的两级流程。
当候选片段数 > K 时,在答案中置 `partial_context=True` 并显式声明"本次只参考了资料的部分内容"。

**Rationale**: 用户理解的"直接给模型看"指的是**不建向量索引**,而不是"字节级全量投喂"。
两级筛选对用户是透明的(效果相同、更快更省),且 FR-006 要求截断必须被声明,
不会让用户误以为通盘查阅过。此决策已在澄清回合中主动告知需求方并获认可。

**Alternatives considered**: 全量投喂(超窗、昂贵);map-reduce 多轮总结(多次 LLM 调用,
延迟与幻觉风险都上升,违背简单性原则)。

## D-03 文档解析:三个运行时依赖及其正当性

宪法原则 V 要求"新增运行时依赖 MUST 有书面理由"。三个依赖及理由:

| 依赖 | 版本(实测) | 为什么不能用标准库 |
|------|------|------------------|
| `python-docx` | 1.2.0 | `.docx` 是 ZIP+XML,手写解析需处理段落/表格/样式,代码量远超依赖成本 |
| `pypdf` | 6.14.2 | PDF 文本抽取涉及字体编码与内容流解析,自实现不现实 |
| `openpyxl` | 3.1.5 | `.xlsx` 同为 ZIP+XML,且需处理共享字符串表与多工作表 |

`.md` / `.txt` 用标准库直接读,不引入 markdown 解析器(我们只要纯文本 + 标题层级,
用正则识别 `#` 标题即可)。

**测试夹具的生成**:`.docx` / `.xlsx` 用上述库在构建脚本中生成;`.pdf` 用一个**约 30 行的
自写最小 PDF 生成器**(手工组装 xref 表 + Helvetica base14 字体),已实测 `pypdf` 可正确回读。
因此**不引入 reportlab** 这个只为造测试数据而存在的依赖。
副作用:PDF 样例只能是英文(base14 字体不含 CJK)——这恰好满足需求方"中英混着"的要求。

## D-04 LLM 驱动边界与离线测试

**Decision**: 定义 `LLMDriver` 协议(`generate(LLMRequest) -> LLMResponse`)。
提供三个实现:

1. `KeywordMockDriver` — 确定性、纯本地。从提供的片段中抽取与问题词元重合度最高的句子作答,
   无重合时返回 `sufficient=False`。**用于离线演示与端到端测试。**
2. `ScriptedDriver` — 测试专用,按预设脚本返回指定响应,**包括故意伪造引用的"说谎驱动"**,
   用来验证防幻觉校验器真的拦得住。
3. `AnthropicDriver` — 真实厂商驱动,**只写不跑**。不在测试中导入执行,SDK 为可选依赖。

**Rationale**: 宪法原则 IV。业务逻辑只依赖协议,不 import 任何厂商 SDK。

**离线保障(硬措施)**:`tests/conftest.py` 中放一个 autouse fixture,
把 `socket.socket.connect` 替换为抛异常的实现。**任何测试一旦尝试联网就会立刻失败**,
而不是悄悄依赖网络。这把"测试必须离线可跑"从一句约定变成了一条会红的断言。

**Alternatives considered**: 用 `unittest.mock.patch` 逐个测试打桩(容易漏);
用 `pytest-socket` 插件(多一个依赖,自己写 6 行就够)。

## D-05 防幻觉:结构化响应 + 确定性校验器(不依赖模型自觉)

**Decision**: 驱动返回结构化响应 `{answer_text, cited_passage_ids, sufficient}`。
在驱动之外、由**确定性代码**执行以下校验(`answer.py::_verify`):

1. `sufficient == False` → 直接判定为"不知道",丢弃 `answer_text`(**即使模型写了正文也不采用**)。
2. `cited_passage_ids` 为空 → 判定为"不知道"。
3. 任一引用 ID 不在本次提供给模型的片段集合内 → **判定为幻觉**,丢弃整个答案,
   记为"不知道",并在审计中标记 `fabrication_blocked=True`。
4. 通过校验后,答案末尾由**代码**拼接引用清单(文档名 + 位置),而不是让模型自己写出处。

**Rationale**: 宪法原则 I 要求"每条断言可回溯"。让模型自己保证这一点是不可靠的;
让代码验证"你引用的东西存在吗"是可靠的、可测的。第 4 条尤其重要——
**出处由代码生成,模型无法伪造一个好看的假引用。**

**已知边界(诚实记录)**:本机制能拦住"引用不存在的来源",但**拦不住"引用了真实来源却
曲解其内容"**。真正的缓解手段是提示词约束 + 引用与原文并排展示,让人一眼可核。
这个残余风险已写入 README 的"能力边界"一节,不假装解决了。

## D-06 权限判定的执行位置

**Decision**: 顺序为 `加载全部片段 → authz 过滤 → 检索打分 → 组 prompt`。
受限片段在过滤阶段被剔除,**绝不进入 prompt、审计日志或任何输出**。

**一个需要明确的例外及其边界**:为了实现 FR-010(命中受限材料时要明确告知"权限不足",
而不是假装无此资料),系统需要知道"这个问题是否命中了受限内容"。
做法:对受限片段**单独打分**,只保留**分数与所属品类**两个数字/标签,
文本立即丢弃,不进入任何后续环节。

- 这不违反宪法原则 II——原则禁止的是受限内容进入**生成上下文**,打分不是生成。
- 强制约束:由测试 `test_authz.py::test_restricted_text_never_leaves_authz` 断言
  受限文档的特征字符串(如具体价格数字)不出现在 prompt、审计记录、CLI 输出的任何位置。
- 拒答提示为**统一文案**,不随命中内容变化,避免通过提示差异侧信道推断内容。

**Alternatives considered**: 完全不告知(回答"没查到")——会让采购员误以为公司没有这份资料,
反复追问,且与 FR-010 冲突;直接报"存在 X 文档但你不能看"——泄露文档名,已否决。

## D-07 版本/生效日期识别(支撑 FR-005a)

**Decision**: 用一组正则从文档正文前 N 行中抽取:

- 日期:`生效日期[::]\s*(...)`、`发布日期`、`Effective Date`、`Version Date`,
  支持 `2024-03-01` / `2024/3/1` / `2024年3月1日` 三种写法。
- 版本:`版本[::]\s*V?(\d+(\.\d+)*)`、`Version: v1.2`、`Rev. 3`。

抽不到就是 `None`,**不猜、不用文件修改时间兜底**。

**Rationale**: 用文件系统 mtime 兜底看似聪明,实则危险——共享盘上一次复制粘贴就会
把 2019 年的老文件变成"最新",从而在 FR-005a 下**压制掉真正的新版本**。
需求方明确说"大多数文件没版本号",意味着 FR-005b(并列展示)是常态,
这正是安全的那条路径。**宁可退化到并列展示,不可错误地裁决。**

**Alternatives considered**: 文件 mtime(上述风险);文件名中的年份(如"2019旧版")——
作为**辅助**信号保留:仅当正文抽不到日期、且文件名中存在 4 位年份时,记为
`date_confidence="filename"`,并在冲突比较中**只在双方都来自文件名时**才参与排序。

## D-08 冲突检测的判定方法

**Decision**: 两份文档构成"竞争来源"的判定:
(a) 二者都进入了本次检索的 Top-K,且 (b) 二者的**标题词元集合**在剥离版本噪声词
(`旧版/新版/old/new/v1/2019/final/最终`等)后 Jaccard 相似度 ≥ 0.6。

对每个竞争组:全部成员都有可比日期/版本 → FR-005a(取最新 + 注明旧版);
否则 → FR-005b(并列 + 提示不一致)。

**Rationale**: "语义上矛盾"无法用确定性代码可靠判定,而**"同一主题的多个版本"可以**,
且后者覆盖了需求方举的实际例子(2019 版 vs 2024 版流程文件)。
不假装能检测任意语义矛盾——这一能力边界写入 README。

**Alternatives considered**: 让 LLM 判断是否矛盾(不确定、不可测、且会把幻觉引入
一个本该是确定性的环节);比较片段文本相似度(噪声大,表格类文档误报严重)。

## D-09 存储与状态

**Decision**: 无数据库。语料目录只读;运行状态写在 `--state` 指定的目录(默认 `./.pbot/`):

- `index.json` — 导入产物(片段、元数据、被拒文件清单)
- `escalations.jsonl` — 转人工记录(追加写)
- `audit.jsonl` — 审计日志(追加写)

JSONL 追加写在单机个位数并发下足够,且人可以直接用文本编辑器看。

**Rationale**: 宪法原则 V。SQLite 也可以,但会引入 schema 迁移问题,而我们的
"表"只有三张且从不 UPDATE。

## D-10 人员名单格式

**Decision**: `roster.csv`,UTF-8 with BOM(**关键:让 Excel 双击打开中文不乱码**),四列:

```csv
工号,姓名,角色,负责品类
P1001,李明,采购员,
P1002,张伟,品类经理,电解铜
P1003,王芳,品类经理,紧固件
P1005,赵强,品类经理,电解铜;铝锭
P9000,陈国华,采购负责人,*
```

- `负责品类` 多值用 `;` 分隔;`*` 表示全部(仅 `采购负责人` 使用)。
- `采购员` 的该列留空。
- 解析失败(缺列、角色非法)→ 明确报错并指出行号,**不静默降级为最小权限**
  (静默降级会让权限问题变成"某人突然查不到东西"的玄学故障)。

**Rationale**: 需求方原话"你给我个格式我填",且明确表示自己维护。CSV 是他能用 Excel
直接编辑的最简格式。BOM 这个细节是给非技术用户的实质关照。

## D-11 转人工路由:问题 → 品类 → 联系人

**Decision**: 从问题文本中识别品类:把语料中出现过的品类名(来自保密子目录名 + roster 的
`负责品类` 列的并集)作为词表,在问题中做最长匹配。命中 → 该品类的品类经理;
未命中或该品类无人认领 → 采购负责人(`*` 角色)。多人负责同一品类时,全部列出。

**Rationale**: 品类词表来自数据而非硬编码,满足宪法原则 III(领域知识不入代码)。

## D-12 项目布局与打包

**Decision**: 单包 `src/procurement_bot/`,`pyproject.toml` + `uv`,
控制台入口 `pbot`。测试在 `tests/`,演示语料在 `demo/corpus/`(由
`scripts/build_demo_corpus.py` 生成二进制格式文件,文本格式文件直接入库)。

**Rationale**: 宪法原则 VI 要求内核与通道分离——`core.py` 暴露
`AskService.ask(question, employee_id) -> Answer` 这一纯函数式入口,
`cli.py` 只做参数解析与渲染。未来企业微信适配器直接调 `AskService` 即可。
