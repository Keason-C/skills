## Iris 的需求描述(原文)

我们组和运营那边天天用 sqlite-utils 把各种乱七八糟的 CSV、接口导出灌进 SQLite。灌完之后最常被问的一句话是:"这表里的数据到底干不干净?"现在没人答得上来,只能肉眼抽查。

我想要的东西说白了就是:**我给一份"这张表应该长什么样"的约束描述,工具告诉我哪些行不合格,并且给我一份能直接转发给运营看的报告页面**。具体一点:

1. 约束描述用 JSON Schema 就行,我们内部已经在用了(别自己发明一套 DSL)。
2. 命令行能跑:给它数据库、表名、schema 文件,它告诉我结果。脚本里要能用,所以"有没有问题"得从退出码上看得出来。
3. 报告要两种:给机器的(JSON,我们要进流水线)和给人的(**HTML,发给运营点开就能看**)。人看的那份不能是一堵文字墙——要能按列筛、按错误类型筛、能搜、能排序、点开一条能看到"期望是什么/实际是什么"。运营的电脑没网络限制但很怕装东西,所以**一个 HTML 文件拖进浏览器就得能用,不许依赖外网**。
4. 数据量:我们最大的表百万行级别,但报告主要看头部问题,你们定个合理的策略,别把浏览器搞死。

哪些细节我没想清楚的,来问我,别自己猜我的业务。

## 老周的技术要求(原文)

补几条技术边界,都是我们吃过亏的地方:

1. **前端一律 TypeScript + 正经构建管线**(vite 或 esbuild 都行你们定)。我不接受在 Python 里拼 HTML/JS 字符串——上次那个内嵌 3000 行字符串模板的报告页没人敢改。报告页面要做成"数据进、DOM 出"的组件,逻辑可以被 vitest 在 DOM 环境里测到,`tsc --noEmit` 干净。Python 只负责把构建产物和数据打包成单文件 HTML。
2. **Python 侧新代码全部带类型注解,过 mypy**(仓库自己就有 mypy 配置,别降标准)。库 API 和 CLI 分层要跟仓库现状一致——先去读 `db.py` 和 `cli.py` 是怎么组织的,照着来,包括测试和文档的写法(tests/ 和 docs/ 都有现成模式)。
3. **老测试一个不能挂**。这是给上游开源项目提功能,不是自己的玩具仓库。
4. 新增运行时依赖要克制,每加一个都要说得出理由,写进决策记录。

## 验收口径(两人共同确认)

1. 仓库原有 pytest 全量通过;
2. 新功能测试覆盖:正常校验、类型违规、必填缺失、空表、表不存在、schema 文件非法、退出码语义、HTML 自包含(无外链);
3. vitest 通过、tsc 干净、新 Python 代码 mypy 干净;
4. 端到端演示:造脏数据 → validate → 生成 HTML → 断言报告中出现预期违规;
5. 文档按仓库惯例补齐,新命令在文档索引里能找到。
