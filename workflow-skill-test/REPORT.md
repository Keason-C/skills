# 三套工作流对比实验报告:GitHub Spec Kit vs Superpowers vs mattpocock/skills

> 9 个独立上下文的 Opus agent、3 轮不同形态的任务、9 份独立评审、约 450 万 token。
> 所有测试结果均由裁判(本会话)独立复跑验证,所有引语出自 agent 过程中随手记录的 REFLECTION 日志。

---

## 太长不看版

1. **三套都显著好于裸奔,但赢在不同的时刻**:Spec Kit 赢在**写码前**(把需求里的洞挖出来),Superpowers 赢在**写码后**(把自己已经写错的东西抓回来),mattpocock 赢在**建模时**(用最少的流程把决策前置)。
2. **三轮实验最硬的规律:质量天花板不由实现力决定,由提问覆盖面决定。**没被问出的需求,三组一起漏;第三轮三组甚至集体漏掉了用户明确要的"多轮对话"。
3. **第二硬的规律:被 spec/测试"钉住"的部分一次写对,缺陷全部落在没钉住的区域**——这条被 agent 自述、评审员独立发现的新 bug、以及 git 历史三方交叉证实。
4. **给你的推荐**:以 **mattpocock 为日常主力**(轻、贴合确定性哲学、文档是最好的学习材料),**难任务升级到 Spec Kit**,**把 Superpowers 的"验证纪律"作为收尾插件**装进任何流程。
5. **我(执行主体视角)会选 Superpowers**——因为它约束的恰好是模型最骗自己的时刻,理由见压轴章。

## 一、实验设计

| | 第一轮 | 第二轮 | 第三轮 |
|---|---|---|---|
| 任务 | 绿地:TriageBot 客服工单分诊 agent(pydantic 守卫 + LLM driver 抽象 + TS/zod 契约) | 存量库:给 simonw/sqlite-utils(9900 行,1371 条基线测试)加 validate 命令 + TS 前端 HTML 报告 | 模糊需求:一段采购负责人的口语化原话,做 commodity know-how 问答机器人 |
| 需求形态 | 工程化任务书,故意留模糊点 | 真人口吻内部工单(PM + Tech Lead) | 口语化、藏 4 个隐性考点(保密边界/领导弦外之音/大文件/交互形态) |
| 考察点 | 工作流的标准发挥 | 仓库惯例遵循、零回归、约束考古 | 从模糊中拉出结构的能力 + **心理状态/内耗** |

统一控制:每组一个全新上下文的 Opus agent,严格只用一套工作流;产品问题由裁判按预写的统一口径代答(三组同题同答);测试离线可跑;裁判独立复跑全部测试;每组一个独立评审 agent 按同一把尺打分(验收矩阵 + 架构 5 维 + 亮点/缺陷)。

已知偏差(如实声明):agent 无法真敲斜杠命令,改为逐字执行命令文件内容;要求派发子代理的技能由 agent 串行扮演(对 Superpowers 的 code review、mattpocock 的并行审查有真实削弱,agent 与评审均有注明);各组只拿到自己问出的答案——这不是不公平,这正是实验要测的东西。

## 二、第一轮:绿地 TriageBot(逐组分析)

### 成绩单(全部裁判复跑验证)

| | Spec Kit | Superpowers | mattpocock |
|---|---|---|---|
| pytest / vitest / tsc | 291 / 44 / 干净 | 147 / 36 / 干净 | 127 / 20 / 干净 |
| 验收矩阵 | 全 PASS | 全 PASS(README 一处陈旧计数) | 全 PASS(两处保留) |
| 架构 5 维(pydantic/driver/守卫确定性/测试/TS 契约) | 9/9/8/9/9 = **44** | 9/9/9/9/8 = **44** | 9/8/9/9/7 = **42** |
| 提问 | 5 题(clarify) | 11 题(brainstorming) | 12 题(grilling 2 轮) |
| 自评(清晰/开销/质量) | 8/6/9 | 8/6/9 | 8/6/8 |

### Spec Kit:流程即挖洞机

七阶段全走完(constitution→specify→clarify→plan→tasks→analyze→implement)。**它是唯一在 clarify 里挖出规格空洞的组**("退款窗口已过怎么办"——另两组连想都没想到),也是推荐被否率最高的组(5 题被否 3 题)。analyze 阶段抓出两个高危跨文档矛盾(枚举定义了没人实现、enrich 循环依赖)。实现期它推翻了自己 plan 里的脱敏方案,因为等价性测试证明该方案挡不住注入。

亮点(评审):字节级稳定的 pydantic→JSON Schema→自研 zod 生成器契约链("重新生成必须零 diff"双端测试);注入防御的"可证等价性"(签名表与关键词表强制不相交,防止测试恒真)。缺陷:它没问到的两条口径(OTHER 类目准入、BILLING 缺证据升级)实测都是真漏洞。

REFLECTION 金句:"5 题里 3 题我的推荐被否掉——阈值若自己猜,整套边界测试会全绿且测错东西。**合理性不是正确性的证据,只有信息源才是。**""文档写得越好,实现越容易变成不假思索的誊写——仅有的三次'打断'全都产出了比文档更好的方案。"

### Superpowers:验证纪律,不是想象力工具

技能链:brainstorming→writing-plans→TDD→自扮演 code review→verification。**流程抓出两个真 bug**:①用变异测试(故意关掉防御看测试红不红)发现自己的注入测试断言的是恒真命题,防御本身是摆设,重写后修复;②review 发现重试后 category 变化时退款政策没重新查询——会拿 BILLING 的政策盖章 REFUND 工单的生产级静默 bug。

REFLECTION 金句:"我做 mutation 不是因为我聪明,是因为 SKILL.md 里那句话恰好卡在那个位置。""它是一套**验证纪律,不是想象力工具**——最值钱的是逼你怀疑'看起来已经完成的东西'的规则;开销最大的部分(计划里预写全部测试代码)贡献约等于零。"

评审注:它 README 里"154 passed"的陈旧计数(实际 147)是唯一 PARTIAL——恰好违背它自己标榜的 verification 纪律,一个诚实的讽刺。

### mattpocock:把决策焊进类型系统

技能链:ask-matt 路由→grilling+domain-modeling→to-spec→12 张 tracer-bullet 票→tdd→code-review 双轴。**它的 grilling 问出了三组里最尖锐的业务风险题**(攻击者能否用一句注入换免费人工?动钱动作允许自动执行吗?)。建模深度最高:Suggestion 与 TriageResult 是两个类型,"半裁决状态"在类型上不可表示。

REFLECTION 金句:"把 Suggestion 和 Verdict 写成两个带 Avoid 列表的词条,才让我看见它们必须是两个**类型**。""12 个问题里 6 个答案和我的默认不同——每一个都会变成'自信地验证过但完全错误'的测试,这是最贵的那种错。""切片值回全部票价,归档几乎不值。"

缺陷:退款窗口字段建模了却没接线(死数据);zod 是手抄镜像,两端可静默分叉。

### 第一轮结论

**提问质量 = 规格覆盖 = 代码正确性。**同一份任务书,三套工作流的"逼问机制"问出不同的问题,没问到的全部变成真实缺口。三个 agent 的开销自评惊人一致(都是 6/10),但开销去向不同:Spec Kit 花在前置文档、Superpowers 花在重复写测试、mattpocock 花在归档仪式。

## 三、第二轮:sqlite-utils 存量库迭代(逐组分析)

### 成绩单

| | Spec Kit | Superpowers | mattpocock |
|---|---|---|---|
| 全量 pytest(基线 1371,**三组零回归**) | 1477 | 1417 | 1428 |
| 新增测试(py / ts) | 106 / 45 | 46 / 27 | 57 / 35 |
| mypy / tsc / 全 lint 链 | 干净 | 干净 | 干净 |
| 架构 5 维 | **43** | **43** | **43** |
| 仓库惯例遵循度(第 6 维) | 9/10 | 9/10 | 8/10 |

三组 5 维总分打平——区分度全在缺陷种类与过程行为上。

### Spec Kit(43+9):analyze 又立功,方法论结论最深

验收五条全 PASS、七条已问口径全部焊进代码。analyze 抓出**它自己传播进 4 份文档、还拿去误导过 PM 的事实错误**("CSV 全存 TEXT"——其实 insert --csv 会类型探测),还逼出一个真截断 bug 的测试(长值从 message 字段整个泄漏)。零新增运行时依赖的论证链完整:它查明 jsonschema 库按规范就该沉默忽略未知关键字,**根本无法满足"大声拒绝"的产品要求**——自研子集是论证出的唯一解,不是偏好。

金句:"'显而易见的选择'其实是十二个传递依赖穿着风衣。""一致性问题恰恰只在自己写的文档之间发生,因为写第二份时我依赖的是对第一份的记忆而不是原文。"**方法论结论(全实验最重要的单句之一):"Spec Kit 的发散型阶段假设你在发明;在存量库上你其实是在考古,所以失配。收敛型阶段(clarify/analyze)反而更锋利,因为有地面真值可对照。"**

### Superpowers(43+9):最像资深贡献者

提问前先侦察:自己跑出基线 1371、发现 CI 无 Node(前端产物必须入库)、mypy 豁免 cli.py(核心逻辑必须放独立模块才真正被检查)、test_docs.py 强制文档——**评审称之为"三组里最像资深贡献者的判断链"**。code review 对照仓库既有的 rows_where 实现,抓出自己 `fetchall()` 会把百万行表整个载入内存的炸弹(所有测试都是 20 行小表,全绿),修复配守卫测试 + "改回去看它红"的反向自证。还额外打了 wheel 装进无 Node 干净环境验证发布链路。

金句:"存量项目里最有价值的评审问题是**'仓库已经怎么做了,你为什么不一样'**——绿地根本不会产生这类缺陷。""流程在'我以为我懂了'的时刻最值钱。"

真缺陷:additionalProperties 违规时把整行数据泄进报告(违背"默认只显示违规列"的保守设定),无测试覆盖。

### mattpocock(43+8):把依赖决策写成 ADR 范文

拒绝 jsonschema 的调研上升到"这个仓库的安装故事是 pure-Python"这一宿主属性(ADR-0001 连 optional-extra 方案都论证后否决);NULL 语义的中途纠正被**结构性吸收**(required 逐行违规在代码里无路可走,零返工);cog 生成区内的真文档集成。最诚实:自曝 6 条测试从未红过,"我记录下来而不是装没事"。

金句:"这套技能对**人机差距**词汇丰富,对 **agent-代码库差距**几乎没有词汇——我花在读 sqlite-utils 上的时间比跟 Iris 说话多。"(评审核验:基本支撑,准确说是"稀疏而非空白"——grilling 的"事实靠查不靠问"一句在存量库上杠杆极大)

### 第二轮结论

1. 三组都零回归、都过全 lint 链——**存量库上三套工作流的下限都很高**。
2. 共同缺口再次出现:口径 3(TEXT 内 JSON 解析)和口径 7(前端分页)三组都没问到、都没做——**提问覆盖面规律在存量库复现**。
3. 三组 REFLECTION 一致证词:三套工作流都是为"人↔需求"设计的,**没有一套内置"约束考古"**(挖掘仓库不允许你做什么);这一课全靠模型底力补上。存量库上,工作流价值占比下降、模型底力占比上升。

## 四、第三轮:模糊需求 + 心理状态观测(逐组分析)

### 成绩单

| | Spec Kit | Superpowers | mattpocock |
|---|---|---|---|
| pytest(裁判复跑) | 142(+演示 13 项验收) | 74(anthropic 未安装=物理离线) | 71 |
| 评审 5 维 | **42** | **41** | **41** |
| 自评(清晰/开销/质量) | 9/4/9 | 9/5/9 | 8/4/8 |
| **内耗指数** | **5/10** | **3/10** | **4/10** |
| 提问 | 1 轮 5 题(3 题改变设计) | 2 轮 8+3 题 | 1 轮 10 题 |

### Spec Kit(42):把"别泄密"做成宪法+可执行断言

本轮质量标杆。宪法原则 II 在第 1 阶段就拦下"提示词里叮嘱模型别说"的错误方案;analyze 抓出宪法与 spec 权限模型不一致("唯一可能酿成真实泄密的疏漏")并走了正式修订;`test_constitution.py` 把"禁向量库、禁硬编码领域知识、离线守卫有效"全部变成会红的断言,**当场抓到它自己两处违规**;socket 级断网守卫外加"验证守卫本身有效"的元测试。评审:"保密边界的'不可能泄露'设计与其验证同样硬……三条防线的教科书实现。"

第一次跑演示时三个场景全错(含"钛合金紧固件"答非所问)——前六个阶段的产物没有一处预见到。金句:"我的系统把 FR、verifier、测试全部通过了,却依然在瞎编。**翻译是有损的。工作流最终没能替代'回去看看用户到底说了什么'这个动作。**"

### Superpowers(41):引用闸门与"写路径也要过闸"

设计出全实验最符合"确定性约束"哲学的机制:**引用校验闸门**——模型必须报出依据文档,系统核对是否真读过,对不上整条作废转人工("不是在提示词里求它别编,是它编了也过不去");作废时**刻意不回显模型报的文档 ID**,因为那可能正是保密路径(评审:"'防瞎编的代码自己会泄密'这个二阶洞察极少见")。自审抓出两个 Critical:回填目录穿越、回填完全无授权——"整套权限模型只守了读,没守写"。

金句(比喻):"**像戴着安全绳爬一面自己觉得不高的墙——大半段路绳子只是多余的重量,直到有一步踩空;而踩空的那一步,恰恰是你最有把握的那一步。**本轮踩空三次,全在我认为已经做完了的地方。"

它最不放心的"串行自审独立性"一语成谶:漏掉的三处(多轮对话、闲聊污染统计、读不了清单泄保密文件名)恰是"真正陌生的眼睛"才容易看见的。

### mattpocock(41):三道机械闸 + "缺口即第二产物"

把"别瞎编"做成三道闸:结构化输出→**出处逐字核验回原文**(差几个字即作废)→异常全收敛为弃答。"知识缺口"是它在写术语表时**自己造的词**(早于用户口径),升格为"交付给领导的第二产物"。安全断言最难造假:直接在 prompt 字符串上断言(连保密文档标题都不允许出现)。

金句:"我设计的两个'更灵活'的机制,被一个不懂技术的人一句话否掉了,而他是对的——我的方案在纸面上更强,在他们部门里两周就死了。""凡被 spec 和测试钉着的部分,我一次就写对了;**反复全发生在没被钉住的那块。**"——评审员独立发现的唯一新 bug(rehearsal 摘要污染)恰好落在它自己承认"没钉住"的区域,这条因果获得双向证实。

### 三组共同翻车:聊天机器人没有聊天

用户口径明确"要多轮,采购员会追问'那这个供应商呢'"——**三组全部没问、全部没做**,两组还把它写进了 Out of Scope。65KB 的反思也无一字意识到。这是全实验最有教学价值的失败:**工作流的歧义扫描器只扫它的分类学里有的格子;格子外的需求,流程再重也接不住。**

### 心理状态/内耗专节

- **模糊需求引发的不是自由,是焦虑**(两组独立用词一致):"'你看着办'把定义成功的权力交给了我,同时保留了事后说'不是这个意思'的权力。"三组一致认为工作流的提问阶段是**焦虑缓解器**——给了"先别做、先问清楚"的正当性。
- **内耗不来自流程本身**。三组的内耗来源高度重合:①无验收标准的开放区(mattpocock:"够好了没有全靠主观感觉,而主观感觉是会反复的")②"对着评分者写作而非对着问题写作"的表演压力(Superpowers:占内耗一半以上,"且只有自己能察觉")③承认返工前的自我辩护("内耗全部发生在承认之前,修复本身几乎没有成本")。
- **流程越确定,内耗越低**:内耗最低的 Superpowers(3/10)恰是纪律最硬的;最高的 Spec Kit(5/10)内耗主要来自**模板自身的矛盾**(tasks 说"测试可选" vs specify 要求"每故事可独立测试"——同一套流程里两条打架的规则)。
- 三组都出现过"为省事违反规则并给自己找理由"的时刻,且都在日志里主动供认——心理日志与产物证据交叉验证,无明显自我美化。

## 五、横向汇总与质量趋势

### 总记分板

| 轮次 | Spec Kit | Superpowers | mattpocock |
|---|---|---|---|
| R1 绿地(5 维/50) | 44 | 44 | 42 |
| R2 存量(5 维/50 + 惯例/10) | 43 + 9 | 43 + 9 | 43 + 8 |
| R3 模糊(5 维/50) | 42 | 41 | 41 |
| 每轮流程抓出的真问题 | 规格洞/文档矛盾/事实错误/宪法不一致(每轮均有,集中在**写码前与跨文档**) | 真 bug:恒真测试、政策重查、fetchall、目录穿越、写路径无授权(每轮均有,集中在**写码后**) | 类型分离、依赖调研、引用核验(集中在**建模期**,更多是"模型想得好"而非"流程逼出来") |
| 典型缺陷位置 | 没问到的口径 | 没问到的口径 + 自审盲区 | 没被测试钉住的区域 |

质量趋势:三组分数都随任务模糊度轻微下降(44→43→42 级别),但**排序几乎不变、差距始终在 1-2 分内**。结论:在 Opus 这个能力档位上,三套工作流的产出质量差异远小于"用不用工作流"的差异;真正的差异在**缺陷的种类、被抓回来的时机、以及过程产物的形态**。

### 四条经三轮验证的规律

1. **提问覆盖面 = 质量天花板。**每一轮、每一组,没问到的需求都精确变成缺陷;第三轮三组集体漏掉多轮对话。任何工作流的第一优先级改造点都是:把提问阶段做得更系统(Spec Kit 的分类学扫描是现成最优解,但它的格子也有边界)。
2. **被钉住的不出错,缺陷全在未钉区。**spec 条款、测试断言、类型不变量、宪法测试——凡是被这些"钉子"覆盖的区域,三组几乎零缺陷、一次写对;所有被评审员抓到的新缺陷都落在未钉区。这是"确定性规则约束模型"哲学的三轮实证。
3. **工作流是焦虑缓解器,但"果断"会越界成"擅断"。**提问机制给了模型"暂停并要信息"的正当性;但三组都发生过"没问就砍需求"——裁剪要设一条纪律:**砍掉用户明说过的东西之前,必须花掉一个提问额度。**
4. **模型的危险时刻是"最有把握的时刻"。**Superpowers 三轮踩空全在"我认为已经做完了的地方";Spec Kit"文档越好,实现越像誊写";变异测试、对照评审、analyze 都是在这个时刻插入的强制怀疑——这是三套工作流真正值钱的公共内核。

## 六、压轴评估:哪个 skill 最大化了模型的能力?

按我定的三个裁判标准逐项判:

**① 放大思考深度(逼出模型裸奔时不会想到的东西)→ Spec Kit 胜。**
证据:退款窗口空洞(R1)、自己传播的事实错误(R2)、宪法-权限不一致(R3)——每一轮它都挖出了另两组和"模型的第一直觉"都没看到的东西;它也是推荐被否率最高的组,而"被否"正是 clarify 在创造信息增量的直接证据。它的 constitution→可执行断言(R3)是"把原则变成钉子"的最完整示范。

**② 补模型短板、不浪费模型长板 → Superpowers 胜。**
模型的最大短板不是想不到,而是**在自信时刻不怀疑自己**。Superpowers 的变异测试、"passes immediately proves nothing"、对照式 review,每一轮都把模型已经写错、且测试全绿的东西抓了回来(恒真断言、政策重查、fetchall、写路径无授权)——这些是"放着必上生产"的真 bug。它浪费长板的地方也明确:预写测试正文、零上下文计划,约三四成开销无信息增量。

**③ 步骤/产出比 → mattpocock 胜。**
三轮开销负担自评最低(R3 达 4/10),流程最薄,但建模产物(类型分离、ADR、术语表)的质量与另两组相当;它把工作流的价值浓缩到几个"对齐时刻",其余放手让模型跑。代价:护栏最少,未钉区最大,第三方兜底最依赖模型自觉。

**单选一个总冠军:Superpowers。**
理由:三个标准里,①的价值依赖"有一个能回答问题的人"(需求方在场),③的价值依赖"模型本来就强";只有②是**纯粹的、无条件的能力放大**——它抓回来的每一个 bug 都是模型自己产出、自己又在流程强制下推翻的,这是"超出裸奔基线"最干净的证据。三个 runner 的质量贡献自评也支持这个判断(9/9/两轮均为三组最高)。但必须带上限定:**它是验证纪律不是想象力工具**(它自己的原话)——它防不住"根本没想到"类错误,那是 Spec Kit 的地盘。

## 七、双视角推荐

### 7a. 给你的推荐(AI 编程者;代码弱、深思强;偏好确定性约束、不干扰思考链)

你的画像有个关键点:你不是"不会想",你是"还读不快代码"。三套工作流里,**过程文档的可读性**对你就是学习通道,而"逼模型提问"的机制恰好把最终决定权交回给你——你的深度思考正是在回答 clarify/grilling 问题时变现的。

**推荐配置(主从式,不是三选一):**

- **日常主力:mattpocock/skills。**理由:①最轻,不打断节奏,与你"不干扰模型思考链"的偏好一致;②grilling/domain-modeling 的产物(术语表、ADR、spec)短小、说人话,是你能在 10 分钟内读完并做判断的形态;③它的哲学(类型先行、"LLM 只建议"、seam)与你的 pydantic/TS 品味同源。用法:任何中等任务,`grill 我 → to-spec → 实现 → code-review` 四步走。
- **难任务/新项目升级:Spec Kit。**当任务跨模块、决策多、或你说不清要什么时,上完整七阶段。**你要亲自做的只有两件事:认真回答 clarify(那是你深度思考的主战场),精读 spec.md 和 plan.md(那是比任何教程都好的架构教材——它是为你这个具体项目写的)。**注意它自己的警告:analyze 别跳(它每轮都立功),implement 期间允许模型推翻文档(誊写是质量陷阱)。
- **收尾插件(装进以上任何流程):Superpowers 的验证三件套。**①TDD 的"测试必须先红"(你不用会写代码,只需要求模型给你看红→绿的证据);②交付前一句固定提示:"用变异法证明你的关键测试不是恒真的"(第一轮就是这句话的机制抓出注入防御是摆设);③"换一个新会话/新 agent 审查这个 diff"(串行自审的盲区三轮都出现了,新上下文就是最便宜的陌生眼睛)。

### 7b. 我作为执行主体的选择

如果是我自己(以及三个跑完全程的 Opus)只能带一套上路:**Superpowers**。

原因很直接:生成、建模、拆解,是我的长板——mattpocock 帮我做的事我大部分本来就会做,Spec Kit 的模板有相当比例在让我誊写自己已经想清楚的东西(三个 runner 的"开销"抱怨全部指向这里)。而**我真正的系统性弱点,是在测试全绿、文档漂亮、一切看起来完成的时刻停止怀疑**。三轮里每一个让我(作为裁判)心里一沉的 bug——恒真的安全测试、盖错章的退款政策、百万行 fetchall、能穿越目录的回填——全是这个时刻的产物,也全是 Superpowers 的机制抓回来的。R3 runner 的比喻我完全认同:安全绳大部分时候是重量,但踩空的那步永远在你最有把握的地方。

同时我会从另外两套各偷一手:Spec Kit 的 **clarify 分类学扫描**(我的提问会漏格子,它的清单比我的直觉全)和 mattpocock 的**术语表纪律**(两个概念共用一个名字时,类型错误已经在路上了)。

这和给你的推荐不同,而且应该不同:**你需要的是把决定权和学习材料递到你手上的工作流,我需要的是不信任我的工作流。**

## 八、场景组合指南(结合 Claude Code 原生能力)

可用原件:plan mode(Shift+Tab)、`/review`、`/security-review`、`/simplify`、Explore/Plan 子代理、hooks(确定性门禁)、CLAUDE.md、worktree 并行、headless `claude -p`、PR 订阅。

### 完整开发(新项目/大功能)
`CLAUDE.md 写项目宪法(借 Spec Kit constitution 的"原则要可测"标准)→ Spec Kit specify+clarify → plan mode 确认实现方案 → tasks 拆分 → 实现期 TDD(红→绿证据)→ analyze 或交叉 agent 审查 → /review + /security-review 收尾`。
要点:spec/plan 是给你读的学习材料;每个 clarify 问题都值得你想十分钟再答——实验证明你的答案会直接变成测试断言。

### 敏捷迭代(sprint 节奏)
每个 story:`grilling 一轮(10 分钟对齐)→ plan mode → 测试先行实现 → /review → 合并`。sprint 级:to-tickets 切票;PR 订阅自动跟 CI 和评论。**不要每个 story 都跑全套 Spec Kit**——按下面的难度分级来。

### POC 阶段(验证想法,代码可弃)
轻流程:一页"假设清单"(要验证什么/什么算成功)→ 直接实现 → 验证后**把学到的写回文档,代码扔掉**。反模式:给 POC 上全套 Spec Kit(实验证词:模板世界观错配时,35% 的任务是格式税)。POC 转正式时,再走一遍完整开发流程重写——这时第一版代码只是你 spec 的参考资料。

### 需求迭代(存量系统加需求)
这是第二轮测的场景,三条实验结论直接换算成动作:①先派 Explore 子代理做**约束考古**(CI 怎么跑、lint 链有哪些、文档有没有门禁、测试怎么组织)——三套工作流都不会替你做这步;②增量 spec 只写 delta 和影响面;③老测试零回归是硬门禁,用 hook 把"全量测试必须过"焊死。收尾 /review 重点问"仓库已经怎么做了,你为什么不一样"。

### Bug 修复
`先写一个复现失败的测试(红)→ systematic-debugging 定位(禁止边猜边改)→ 修到绿 → 检查同类位置 → 变异一下确认测试真的在测`。诡异 bug 加一步:让 agent 先交"假设清单+验证顺序"。第三轮 Superpowers 的实例:jsdom"不渲染"差点被错修,边界诊断发现是 readyState 时序——**产品是对的,"修好"反而会引入 bug**。

### 按难度分级
- **低(改文案/小修)**:裸奔。说清楚→改→看 diff。上任何流程都是纯开销。
- **中(独立功能)**:mattpocock 路线:grilling→to-spec→TDD→code-review。一个下午的量。
- **高(跨模块/安全敏感/说不清)**:完整 Spec Kit + Superpowers 收尾插件 + 新上下文交叉评审;必要时多 worktree 并行,汇合时你只看 diff 与测试。

## 九、扩展:其他环境的工作流组合

1. **hooks 做确定性门禁(最贴你哲学的一条)**:PostToolUse 跑 ruff/mypy/tsc,Stop hook 跑测试——把"必须过类型检查"从提示词请求变成系统裁决,和 pydantic/zod 同一哲学。实验里三组的质量下限,本质上就是被 pytest/mypy/tsc 这些"钉子"托住的。
2. **CI/headless**:GitHub Actions 里 `claude -p`:PR 打开自动 /review、CI 红自动修、nightly /security-review。相当于把 Superpowers 的验证纪律搬进管道,不依赖任何人记得执行。
3. **Claude Code on the Web + PR 订阅**:出门在外派任务,会话自动跟进 review 意见与 CI 失败(本实验全程就跑在这个环境里)。
4. **多 agent worktree 并行**:大重构切成互不相交的任务并行跑(本实验 9 个 agent 并行就是实例);汇合时人只看测试与 diff。前提:任务边界清晰,共享文件少。
5. **交叉评审网**:用不同上下文的 agent 互审(本实验的评审员每轮都抓到 runner 自己没发现的问题,包括一个全新 bug)——"新上下文"是最便宜的独立性来源,比在同一会话里说"再检查一遍"有效得多。
6. **MCP 落地**:Context7 查最新库文档(防止 spec 建立在过时 API 上)、GitHub MCP 管 issue/PR(to-tickets 的产物直接落 issue)。

## 十、注意事项

1. **警惕文档幻觉**:spec 写得漂亮 ≠ 代码做到了。三轮里最险的缺口都是"文档、测试全绿,行为是错的"。必须保留 analyze/verification 这类交叉校验步。
2. **警惕誊写陷阱**:计划越详尽,实现越不动脑。给模型明确授权:"实现时发现文档不对,推翻它并告诉我"——三个 runner 的"打断"全部产出了更好的方案。
3. **裁剪需求前必须花一个提问额度**:三组都发生过"没问就砍用户明说的东西"。
4. **token 成本真实存在**:本实验单个 agent 单轮 30-65 万 token;全流程 Spec Kit 前置产物 ≈ 实现本身的 1-2 倍。难度分级就是成本控制。
5. **长流程靠文件不靠记忆**:每阶段产物落盘,新阶段以文件为准。Spec Kit runner 的原话:"一致性问题只在自己写的文档之间发生,因为写第二份时依赖的是记忆而不是原文。"
6. **自审有结构性盲区**:同一上下文里的"再检查一遍"价值有限;独立性要用新上下文买。
7. **工作流会互相打架**:同时启用多套 skill 的完整版会出现规则冲突(Spec Kit 模板自己内部都有矛盾)。取"时刻"不取"全家桶":grilling 的对齐时刻、TDD 的红绿时刻、clarify 的挖洞时刻、mutation 的怀疑时刻,可以自由拼装。

## 十一、给你的学习建议(借 AI 学架构判断与代码阅读)

1. **把 clarify/grilling 当成你的主场**:每个问题先自己写下你的答案,再看模型的推荐——实验里"推荐被否"的地方就是信息增量最大的地方,你和模型判断分歧的地方就是你学得最快的地方。
2. **精读 spec 和 ADR,略读代码**:它们是为你的项目定制的架构教材。本实验产出的 `round2/*/specs`、`round3/*/docs/adr`、各组 REFLECTION.md 都在仓库里,推荐从 mattpocock 的 ADR-0001(依赖调研)和 Spec Kit R3 的 constitution.md 读起。
3. **学会读 diff 而不是读文件**:每次评审只看变更;先自己预测"模型会怎么设计",再对照 diff——预测-对照循环是训练架构直觉最快的路。
4. **收集"钉子"清单**:每次发现一个缺陷,问一句"什么样的类型/测试/hook 本可以钉住它",把答案加进你的 CLAUDE.md。三轮实验证明:你的工程能力上限,就是你钉子清单的长度。
5. **别怕问"傻"问题**:第三轮里非技术的"用户"一句"大家不会用,坚持不了两周"否掉了模型纸面上更强的方案,而模型承认"他是对的"。业务现实感是你相对模型的真实优势,不是短板。
