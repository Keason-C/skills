### Das Verhältnis dieser drei Dinge in einem Satz

Viele werfen Pydantic, Pydantic AI und Pydantic Graph von Anfang an durcheinander. Tatsächlich sind sie **dieselbe Philosophie, entfaltet auf drei Ebenen**:

```
┌────────────────────────────────────────────────────────────────────────┐
│  Pydantic Graph     Wenn der Ablauf zu komplex für eine Agent-Schleife │
│  (Graph/Zustands-   wird → Ablauf explizit zeichnen: Knoten,           │
│   maschine)         Verzweigungen, Parallelität                        │
├────────────────────────────────────────────────────────────────────────┤
│  Pydantic AI        Das LLM in einen "Vertrag" einspannen              │
│  (Agent-Framework)  → Agent, Tools, Dependencies, Capability-Karten    │
├────────────────────────────────────────────────────────────────────────┤
│  Pydantic           Das Fundament von allem: der "Vertrag" der Daten   │
│  (Datenvalidierung) → BaseModel: eine Tabelle mit Validierungsregeln   │
└────────────────────────────────────────────────────────────────────────┘
                    Jede Ebene baut auf der darunter auf
```

Ein Bild, das sich durch das ganze Buch zieht:

- **Pydantic** gibt Ihnen eine **Excel-Tabelle mit Datenvalidierung** – sie legt für jede Zelle fest, welcher Typ, welcher Wertebereich, ob Pflichtfeld oder nicht.
- **Pydantic AI** reicht diese Tabelle **als Vertrag an das LLM weiter** – „was du ablieferst, muss dieser Tabelle lückenlos entsprechen". Damit wird aus dem LLM statt eines „Praktikanten, der gut plaudern kann" ein „Festangestellter, dessen Abgaben garantiert konform sind".
- **Pydantic Graph** ist die Engine, mit der Sie den Ablauf **explizit zeichnen**, wenn **ein Vertrag nicht mehr ausreicht** und ein ganzer Prozess nötig wird (welcher Schritt folgt auf welchen, wann läuft etwas parallel, wann wird zusammengeführt).

> 👉 **CEO-Perspektive**: Diese drei Ebenen entsprechen den drei Ebenen Ihrer Produktarbeit – **Feldregeln** (was muss in dieser Zelle stehen, damit sie gültig ist), **Funktionsmodule** (wie definiere ich die Grenzen dieser KI-Fähigkeit) und **Geschäftsprozesse** (wie verkette ich mehrere Schritte). Sie denken täglich auf diesen drei Ebenen, Ihnen fehlte bisher nur das passende Code-Vokabular.

### Ist das die Unix-Philosophie?

Eine gute Frage, und die Antwort lautet: **Der „Kompositions"-Geist von Unix wurde übernommen, aber der Kern „loser Text" wurde ausgetauscht.**

| | Unix-Philosophie | Pydantic-Philosophie |
|---|---|---|
| Komponenten | Kleine Tools, jedes macht eine Sache | Kleine Komponenten, jede macht eine Sache ✅ gleich |
| Komposition | Frei zusammensteckbar | Frei zusammensteckbar ✅ gleich |
| **Was wird übergeben** | **Alles ist ein Textstrom** (`\|`-Pipe) | **Alles sind typisierte, strukturierte Daten** ❌ anders |
| Fehlerzeitpunkt | Erst zur Laufzeit entdeckt | **Zur Definitionszeit deklariert, an der Tür abgefangen** |

Der Vergleich in einem Satz:

> **Unix-Philosophie = kleine Tools + Text-Pipes + freie Komposition**
>
> **Pydantic-Philosophie = kleine Tools + strikt typisierte Verträge + freie Komposition**

Der wahre direkte Vorfahre ist **FastAPI** (derselbe Autorenkreis), und das Kerncredo lautet **„Typsicherheit + deklarativ"**: Sie **deklarieren** nur, „wie es aussehen soll", und das Framework **hält das Nicht-Konforme draußen**.

> 👉 **CEO-Perspektive**: Dieser Unterschied ist für Ihre Produktentscheidungen zentral. Sich für den Pydantic-Stack zu entscheiden heißt, sich für **„vorne mehr Aufwand in klare Regeln stecken, dafür hinten Fehler sofort abfangen"** zu entscheiden. Das sind zwei grundverschiedene Produktphilosophien gegenüber „erst mal live gehen, Probleme später nachbessern". Für KI-Produkte, deren **Ausgabeformat zuverlässig sein muss** und die **an Geschäftssysteme angebunden werden**, ist der Wert der ersten Variante enorm.

### Versionsbasis: Warum das zuerst gesagt werden muss

Zur Entstehungszeit dieses Buches hatte Pydantic AI gerade einen **großen Versionssprung (v1 → v2)** hinter sich, und die Schreibweisen in vielen Online-Tutorials sind **bereits veraltet**. Der gesamte Inhalt dieses Buches bezieht sich auf die folgenden Versionen, und **jedes Codestück wurde auf diesen Versionen tatsächlich ausgeführt und verifiziert**:

| Bibliothek | Version | Beschreibung |
|---|---|---|
| `pydantic` | 2.13.4 | Datenvalidierungsbibliothek |
| `pydantic-ai` | **2.17.0 (v2)** | Agent-Framework, zentrale große Iteration: **das Capability-Karten-System** |
| `pydantic-graph` | **2.17.0** | Graph-Engine, **auf Builder-Architektur neu geschrieben** |
| `pydantic-ai-harness` | 0.10.0 | Offizielles Erweiterungspaket für Capabilities (**Achtung: Alpha-Phase**) |

Zwei „Versionsfallen", die man vorab kennen muss:

> ⚠️ **Fallstrick 1: Die Kernänderung in v2 ist die „Konvergenz der Konfiguration auf Capability-Karten"**. Sehr viele Einstellungen, die ursprünglich über die `Agent(...)`-Parameter verstreut waren (`instrument=`, `prepare_tools=`, `history_processors=`, `event_stream_handler=` …), sind in v2 **einheitlich in `capabilities=[...]` zusammengeführt**. Wenn alter Code es anders macht, ist es v1.

> ⚠️ **Fallstrick 2: `pydantic-graph` 2.17 ist eine Neuentwicklung**. `Graph(nodes=[...])`, `graph.mermaid_code()` und `pydantic_graph.persistence` aus den meisten Graph-Tutorials im Netz **existieren in dieser Version nicht mehr**. Dieses Buch beschreibt ausschließlich APIs, die im Paket tatsächlich vorhanden sind.

> 💡 **Ein verbreitetes Missverständnis zur Versionsnummer**: Das offiziell mit dem Paket ausgelieferte Lern-Skill trägt `version: 1.1.1` – das ist **die Versionsnummer dieses Dokuments selbst**, nicht die der Bibliothek. Genau wie „Python-Tutorial", 3. Auflage, Python 3.12 behandelt: Die Auflage des Buches und die Version der Sprache sind zweierlei. Die tatsächliche Version der Bibliothek ist 2.17.0.

### Wie man dieses Buch liest

**Jeder Teil folgt dem Prinzip „erst die Karte, dann der Weg"**: Zuerst erklärt ein Abschnitt die Gesamtarchitektur des Moduls (aus welchen Bausteinen es besteht, wie sie zueinander stehen), danach geht es der Architektur folgend Baustein für Baustein in die Tiefe. Sie können:

- **Von vorne durchlesen**: Die drei Teile bauen aufeinander auf, Fundament → Framework → Orchestrierung; durchlesen ist der leichteste Weg.
- **Gezielt nachschlagen**: Jeder Wissensbaustein ist ein in sich geschlossener Abschnitt, den Sie direkt über das Inhaltsverzeichnis ansteuern.
- **Nur die CEO-Perspektive lesen**: Wenn Ihnen ein Codestück zu mühsam wird, überspringen Sie den Codeblock und lesen Sie nur den Teil `👉 CEO-Perspektive` – Sie bekommen trotzdem die vollständige Konzeptlandkarte.

Es gibt einige Wissensbausteine mit „Schlüsselcharakter"; wenn die Zeit knapp ist und Sie nur wenige Abschnitte lesen, dann diese:

| Priorität | Wissensbaustein | Warum |
|---|---|---|
| ⭐⭐⭐ | **BaseModel und JSON Schema** | Das Fundament des gesamten Systems: „wie aus Ihrer Tabelle eine Anleitung für das Modell wird" |
| ⭐⭐⭐ | **`output_type` – strukturierte Ausgabe** | Der Hauptgrund, warum Pydantic AI dem nackten API-Aufruf überlegen ist |
| ⭐⭐⭐ | **Das Capability-Karten-System** | Die zentrale große Iteration von v2, der Schlüssel zum Verständnis moderner Agent-Architektur |
| ⭐⭐ | **Tools und `tool` / `tool_plain`** | Die Wasserscheide zwischen Agent und Chatbot |
| ⭐⭐ | **Deps – Dependency Injection** | Die Infrastruktur für Mandantenfähigkeit und Rechtetrennung |
| ⭐⭐ | **Die Agent-Schleife ist selbst ein Graph** | Wer das versteht, dem erschließt sich das gesamte Framework |

Ein letzter Satz: **Alle Code-Ausgaben in diesem Buch stammen aus echten Läufen, nichts davon ist erfunden.** Wo etwas in der Praxis nicht läuft oder zusätzliche Abhängigkeiten braucht, wird das im Buch klar gekennzeichnet und nicht verschwiegen.
