# teaching-doc · 技术教程写作规范

一份可以直接拷进任何项目根目录的 `CLAUDE.md`，用来约束「写给非专业开发者看的技术教程」这类任务。

## 用法

```bash
# 新项目：直接放到根目录
cp teaching-doc/CLAUDE.md <你的教程项目>/CLAUDE.md

# 已有 CLAUDE.md：把内容追加进去（都是 XML 标签块，可以直接拼）
cat teaching-doc/CLAUDE.md >> <你的项目>/CLAUDE.md
```

## 它约束什么

| 标签 | 管什么 |
|---|---|
| `<audience>` | 读者画像、「XX 视角」段落怎么写、术语纪律 |
| `<structure>` | 架构先行、**先列表再精讲一个不落**、三件套、编号与交叉引用 |
| `<code-examples>` | 代码必须真跑过、输出必须是复制来的、顶层 await 禁令 |
| `<source-of-truth>` | **证据分级 A/B/C/D**、装源码 > 官方文档 > 训练知识、版本号陷阱、「实测」一词的使用纪律 |
| `<verification>` | 二手结论回源核实、分模块审校、自动化闸门、分块协作铁律 |
| `<checklist>` | 交付前逐项打钩 |

## 来源

规则提炼自《Pydantic 全栈教程 · PM 视角》（300 页中文 + 330 页德文，见 `../pydantic-tutorial-pm/`）的实际生产过程。

文中标注「实践教训」的段落，全部来自那次构建里**真实发生过的错误**，包括：

- 把 skill 文档的 `version: "1.1.1"` 当成库版本，据此判断还是 v1 —— 实际库已是 2.17.0，v2 有大量破坏性变更
- 某节要教「这段会抛 RuntimeError」，但示例里有顶层 `await`，读者复制过去先撞 SyntaxError，整节论证自我拆台
- 两处标着「实测」的结论其实只是读源码推断的
- 支持矩阵里一格标了 ✅，回源查注册列表根本没有该项，应为 ❌
- 4 处交叉引用在章节调整后失效，人工通读未发现，靠脚本扫出来
- 分块并行翻译时，拆出 12 块的协作者没有负责合回来

## 没有包含什么

刻意**不含**任务分派策略（什么活给哪个模型、并发多少）——那部分和具体工具环境强耦合，换个环境就不适用。这份规范只管**内容质量**和**事实准确性**，与执行方式无关。
