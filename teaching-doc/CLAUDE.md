# 技术教程写作规范

本文件用于「写一本给**非专业开发者**看的技术教程」。与技术栈无关，任何语言、任何框架通用。

读者的目标是**看懂并能做判断**，不是**能写生产代码**。所有规则都服务于这一点。

---

<audience>
## 读者与视角

### 读者画像

在动笔前必须先写死一句话画像，写进文档开头，全书据此校准。例：

> 读者是产品经理，不写生产代码，但希望看懂代码和概念、能参与技术决策。

画像决定了三件事：**哪些概念要展开、哪些可以跳过、类比往哪个方向打**。没有画像就会写成"给同行看的 API 文档"。

### 视角段落（本规范的核心要求之一）

**每一个功能点，都必须配一段「读者视角」。** 格式统一，便于扫读：

```markdown
> **👉 PM 视角**：……
```

（标签随画像换：CEO 视角、运营视角、设计师视角。）

写法要求：

- **挂到读者已有的直觉上**，不要在技术内部打转。
  - ✅「这就是提交按钮：不管用户在输入框里写了什么小作文，只有点了提交才算数，而按钮背后是一张必填校验过的表单。」
  - ❌「output_type 通过工具调用通道实现结构化输出的强制约束。」
- **回答「这东西改变了我的什么决策」**，而不是复述功能。排期、成本、风险、用户体验，挑一个说清楚。
- **允许说代价**。只说好处的视角段落没有价值，读者需要知道什么时候**不该**用。
- **一段就够**，2–5 句。超过就说明在讲功能而不是讲判断。

### 术语纪律

- 任何术语**第一次出现必须当场解释**，不能靠后文补。
- 解释先给「是什么」的类比，再给准确定义。顺序不能反。
- 全书术语表统一。同一个概念不允许出现两种译法（写完做一次全局扫描核对）。
- 保留英文原名的场合：API 名、类名、参数名、报错原文。这些是读者要去搜索、要和 AI 对话的关键词，翻译了反而有害。

### 禁止事项

- ❌ 不解释就用行话（「幂等」「反压」「柯里化」）。
- ❌ 用「显然」「众所周知」「简单来说」当作跳过解释的借口。
- ❌ 上来就贴大段代码。**先说它解决什么问题，再看代码。**
- ❌ 只讲 happy path。读者最需要知道的恰恰是「什么时候会出问题」。
</audience>

<structure>
## 文档结构

### 规则一：架构先行，逐层下钻

每个模块（章）**必须先给整体架构**，再往下拆。顺序固定：

```
① 一句话说清这个模块解决什么问题
② 架构图 / 总表（让读者先有全局地图）
③ 按架构逐块下钻，每块再重复 ①②③
```

读者在任何时刻都应该知道「我现在在地图的哪个位置」。做不到这点，就是结构没拆好。

### 规则二：先列表，再精讲，一个不落（硬规则）

**任何「有多个并列项」的东西，都必须先给总表，再逐项精讲。**

适用于：能力清单、参数选项、模式类型、生命周期钩子、配置项、错误类型……

```markdown
## 总表

| # | 名称 | 一句话 | 什么时候用 |
|---|------|--------|-----------|
| 1 | ...  | ...    | ...       |
| … | …    | …      | …         |

## 精讲 1 · ……
## 精讲 2 · ……
（表里有几行，下面就必须有几节，一个都不许省）
```

**「常用的讲，冷门的一笔带过」是明确禁止的。** 冷门的可以短，但必须有独立小节、必须有代码、必须有视角段落。教程的价值恰恰在于「查文档查不到的那些」。

写完后做一次机械核对：**总表行数 == 精讲小节数**。

### 规则三：每个功能点的三件套

顺序固定，一个都不能少：

```
1. 它解决什么问题      —— 一句话，用产品语言，不出现 API 名
2. 代码示例 + 实测输出  —— 见 <code-examples>
3. 读者视角            —— 见 <audience>
```

### 篇幅

**不设上限，宁厚勿薄。** 页数不是成本，读者读不懂才是。

但「厚」必须来自**覆盖度**（该讲的一个不落），不是来自**注水**（同一件事换三种说法讲三遍）。判断标准：删掉任意一段，是否有信息丢失？没有就该删。

### 编号与交叉引用

- 章节编号全书唯一、连续。写完做一次重复编号扫描。
- 交叉引用（「见 §3.14」）**必须逐条验证目标存在且内容对得上**。
  > 实践教训：一本 300 页的书里出现过 4 处失效交叉引用，全部是章节调整后忘记同步。这类错误人工通读极难发现，**必须写脚本扫。**
- 前向引用（「这个后面第 5 章会讲」）可以用，但要确保后面真的讲了。

### 附录（推荐）

厚教程建议配三样：
- **版本变更速查**（v1→v2 之类的破坏性变更对照表）
- **常见坑速查表**（现象 → 原因 → 解法）
- **决策树**（面对选择时走哪条路）

这三样是读者用完教程后**唯一会反复回来翻**的部分。
</structure>

<code-examples>
## 代码示例

### 必须真实可运行

**每一段代码都要实际跑过。** 不是「看起来对」，是真的执行了。

构建流程里要有一步自动检查：抽取所有代码块 → 逐个语法编译 → 报告失败项。

### 必须附实测输出

```markdown
​```python
（代码）
​```

​```text
（真实跑出来的输出，原样粘贴）
​```
```

**输出块的内容必须是复制粘贴来的，不许手写、不许「大概是这样」。** 手写的输出一定会和真实行为对不上，而这正是读者最容易被误导的地方。

如果某段代码因为缺 API key 之类的原因跑不了，两个选择：
1. 换成能跑的等价写法（用 TestModel / FunctionModel / mock 之类）
2. 明确标注「此段未实际执行」

**不允许第三种：假装跑过了。**

### 顶层 await 禁令

示例代码**不允许出现裸的顶层 `await`**（除非上下文明确是 REPL / notebook）。

> 实践教训：某章要教「这段代码会抛 RuntimeError」，但示例里有顶层 await，读者复制过去**先撞 SyntaxError**，根本看不到要教的那个错误——整节的论证自我拆台。
>
> 正确写法：包进 `async def main()` + `asyncio.run(main())`，或用同步 API。

### 长度与注释

- 一段代码**只演示一个点**。演示三个点就拆成三段。
- 无关的样板代码用 `...` 省略，但省略处要保证读者知道省了什么。
- 注释写给读者，不是写给编译器。解释**为什么**，不解释**是什么**。
  - ✅ `# 钱相关，别让模型发挥`
  - ❌ `# 设置温度为 0`
- 变量名可以用中文（教程场景下可读性优先），但**不要用在会出现在输出里的值上**——一旦输出块也要跟着改，就容易和真实运行结果脱节。

### 反例的用法

教「什么是坏写法」时，坏例子和好例子**必须并排给**，且明确标注：

```markdown
❌ 这样写：
​```python
（坏例子）
​```

✅ 应该这样：
​```python
（好例子）
​```
```

只给好例子，读者不知道自己现在写的是不是坏的。
</code-examples>

## 事实基准（本规范最重要的一节）

### 证据等级

写下任何一个技术断言前，先确认它属于哪一级：

| 级别 | 来源 | 可用性 |
|---|---|---|
| **A** | 在目标版本上**实际运行验证过** | 可以直接写，可以说「实测」 |
| **B** | 读了**已安装的包源码** | 可以写 |
| **C** | 读了**该版本的官方文档 / 仓库** | 可以写，但涉及行为细节的最好升到 A |
| **D** | 训练知识、印象、别处看到的教程 | **不许写**，必须先升到 C 以上 |

**D 级内容混进技术教程，是这类文档最主要的失败原因。** 生态迭代速度远快于训练数据。

### 安装源码 > 官方文档 > 训练知识

优先级不可调换：

1. **把目标版本装到一个真实环境里**，读它的源码、跑它的代码。
2. 官方仓库 / 官方文档（注意对齐版本分支，不要读 main 写 stable）。
3. 训练知识只能用来**提问**，不能用来**回答**。

冲突时**以已安装的源码为准**。文档滞后于代码是常态。

### 版本基准

- 全书开头**必须有一张版本表**，列出每个相关包的确切版本。
- 全书所有代码在**同一套版本**下验证，不允许混版本。
- 版本表要写明「本书所有代码在下列版本实测运行验证」，这是对读者的承诺。

### ⚠️ 版本号陷阱

**不要把「文档/skill 的版本号」当成「库的版本号」。**

> 实践教训：某个 skill 文件的 front-matter 里写着 `version: "1.1.1"`，据此判断库还是 v1，整整写偏一大段。实际上那是**该文档自身**的版本，库当时已经是 **2.17.0**，v2 有大量破坏性变更。
>
> **唯一可靠的做法：装进环境里，`importlib.metadata.version('包名')` 打印出来。**

同类陷阱：README 里的版本、教程里的版本、PyPI 页面缓存的版本、`__version__` 属性不存在的包。**以实际安装的分发版本为准。**

### 「实测」一词的使用纪律

**只有真的跑过，才能写「实测」「验证过」「我试了」。**

> 实践教训：审校时发现两处标了「实测」的段落，实际上只是读了源码推断的。
>
> 读者会因为「实测」二字**完全放下戒心**。滥用这个词等于骗人。

读源码得出的结论，就写「源码里是这样写的（`文件:行号`）」。推断得出的结论，就写「按这个逻辑推断，应该是……（未实测）」。

### 不确定的东西怎么办

三选一，**没有第四种**：

1. 去验证，升到 A/B 级
2. 明确标注不确定（「这一点我没验证，用之前请自己试一下」）
3. 删掉

**绝对不允许**用模糊措辞蒙混过去（「通常」「一般来说」「应该会」）——读者读不出你在心虚，只会当成事实。

### ✅/❌ 表格的纪律

功能支持矩阵（哪个特性支持什么）**每一格都必须有独立依据**。

> 实践教训：某张表里把一项标了 ✅，实际去查源码里的注册列表，那一项根本不在里面——应该是 ❌。这类表格读者会直接拿去做技术选型，错一格就可能导致选错方案。

做法：写完表格后，**逐格回源核对一遍**，不要相信自己填表时的记忆。

### 报错信息

- 报错原文**必须一字不差地照抄**，包括标点。读者会拿它去搜索、去问 AI。
- 必须写清**报错在什么时机抛出**。
  > 实践教训：某个 `ValueError` 被写成「构造对象时抛出」，实际是在**加载工具集时**才抛（构造时不检查）。差一步，读者就找不到断点该下在哪。
- 尽量给出**最常见的触发路径**，而不只是「参数冲突时」这种抽象描述。
</source-of-truth>

## 验证纪律

### 二手结论必须回源核实

任何**不是你自己跑出来的结论**——不管来自协作者、来自搜索、来自另一个模型——都是 C 级或更低。

**写进正文前必须自己回到源码/仓库确认一遍。** 越是「听起来很合理」的结论越要查，因为合理性正是幻觉最擅长伪装的东西。

### 分模块审校

每写完一个子模块（不是每写完一章），**立刻做一次独立审校**再往下写。

审校要求：
- 审校者**不复用写作者的上下文**，独立回源核对
- 输出必须是**具体的行号 + 具体的错在哪 + 正确的应该是什么**，不接受「整体不错，建议加强 XX」这类空话
- 审校发现的问题**当场改完再往下写**，不要攒到最后

理由：错误会传染。第 3 节基于第 2 节的错误结论往下推，最后返工成本是当场改的十倍。

### 自动化闸门

人工通读**无法**可靠地发现下面这些问题，必须写脚本：

| 检查项 | 为什么必须自动化 |
|---|---|
| 所有代码块能否通过语法编译 | 量大，人眼会漏 |
| 是否存在裸顶层 `await` | 眼睛扫不出来 |
| 章节编号是否重复/断号 | 调整章节后必错 |
| 交叉引用目标是否存在 | 人工核对成本极高 |
| 总表行数 == 精讲小节数 | 最容易「不知不觉少讲一个」 |
| 术语是否全书统一 | 分块写作必然分叉 |

**闸门要写成「不通过就拒绝构建」，不能只是打印警告。** 警告一定会被忽略。

### 分块协作的两个铁律

长文档需要拆块并行写时：

1. **拆块的人负责合回来。** 拆出去 12 块然后不管了，结果就是没人拼装、块与块之间风格和术语全对不上。
2. **合并前做结构校验。** 至少校验：代码围栏数量是否与原文一致、章节层级是否连续。校验不过**拒绝写盘**，不要「先合了再说」。

### 翻译版本（如果有）

翻译版必须有独立闸门，逐块比对原文与译文：

- **程序输出、报错原文、图表**：必须**逐字节相同**。译了就和上面的代码对不上了。
- **代码块**：除注释外必须相同。字符串字面量、API 名、变量名一律保留。
- **表格行数、章节数**:必须一致。

判断某个值该不该译，只有一条标准：

> **这个值会不会出现在下面的输出块里？**
> 会 → 一个字都不能动。
> 不会（纯示意的占位符、举例用的文案）→ 该译就译。

必须保留原文、但读者不理解就 get 不到要点的，**保留原文 + 加括注**。
</verification>
