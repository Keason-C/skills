# Claude Code 工作流对比基准：Matt Skills vs Matt Grilling→Spec vs pstack

> 测试日期 2026-10-08 · 无人值守运行 · 主模型 `claude-opus-5-5`（effort high） · Python + TypeScript 双技术栈

## 一句话结论

**三种工作流在“能不能做对”上几乎打平，差距出在工程质量、可扩展性和成本上。**
综合分（权重见下）：**Grill→Spec 88.2** ＞ pstack 81.9 ≈ Matt `/implement` 81.8。

| 选手 | Python 综合 | TS 综合 | 平均 | 一句话画像 |
|---|---:|---:|---:|---|
| **grill**（`/grilling` → `/to-spec` → `/implement`） | **88.5** | **88.0** | **88.2** | 盲评 8 次中 7 次第一；TS 可扩展性碾压；成本约 matt 的 2 倍 |
| **pstack**（`/pstack:poteto-mode`，Claude Code 移植版） | 82.1 | 81.8 | 81.9 | 测试最重、TS 盲评均分最高；最贵最慢，约一半花费在 Fable 子代理 |
| **matt**（`/implement` → tdd → code-review） | 87.5 | 76.2 | 81.8 | 最快最便宜；Python 很稳，TS 出现真实缺陷（深依赖链栈溢出） |

## 1. 实验设计

### 题目（两道，难度较高，带隐藏验收）

| 题目 | 技术栈 | 核心难点 |
|---|---|---|
| **gridcalc** 内存电子表格引擎 | Python 3.13，仅标准库 | 公式解析（`-2^2=4`、`2^3^2=64` 等 Excel 陷阱）、增量重算、静态环检测、插入/删除行列时公式引用重写（字节级保留原文）、带 `$` 的复制粘贴、5 万单元格性能、5 万长依赖链不能递归溢出 |
| **taskflow** 依赖感知的异步调度器 | TypeScript（Node 22，strict） | DAG 依赖与前向引用、并发上限、优先级+就绪顺序+添加顺序三级排序、同步派发、指数退避重试、单次超时（释放槽位并同步补位）、取消级联、精确事件顺序、注入时钟、零定时器泄漏、零未处理 rejection |

每道题都有一份公开 `BRIEF.md`（规格）和一份**不公开**的“产品负责人决策”（12 条，规格故意留白的点，例如数字转文本格式、跨类型比较、ROUND 舍入方式、退避为 0 时的行为、TaskError 的 cause 链等）。

### 选手与隔离

| 选手 | 技能栈 | 启动方式 |
|---|---|---|
| matt | Matt Pocock skills（20 个） | `/implement <任务>`（skill 内部驱动 `/tdd` 与 `/code-review`） |
| grill | 同上 | `/grilling` 多轮拷问 → `/to-spec` 写规格 → `/implement 规格` |
| pstack | `michael-denyer/pstack-claude` v0.9.78（插件形式加载） | `/pstack:poteto-mode <任务>` |

- **互不可读**：每个选手运行在独立的 mount + PID 命名空间中：`/arena` 只挂载自己的工作区，`/root` 是独立 home（只含自己的技能），`/tmp`、`/home/user`、隐藏测试和其他选手全部不可见；PID 命名空间隔离防止通过 `/proc/<pid>/root` 越界。
- **同条件**：同一模型 `claude-opus-5-5`、`--effort high`、`--permission-mode auto`、禁用 WebFetch/WebSearch、相同任务提示词（只有工作流入口不同）。
- **模拟用户（PO）**：所有选手都能用 `ask-po "问题"` 询问产品负责人（由独立的 Claude 扮演，只按决策文件回答被问到的问题，不主动透露）。grill 的拷问轮次和任何“回合结束时留给用户的问题”都由驱动器转交同一个 PO 回答。这样“问问题”的工作流不会因为没有人类而吃亏。
- Matt 两位选手预置了 `setup-matt-pocock-skills` 的本地 markdown issue tracker 配置（这是 Matt 技能的前置条件）；pstack 使用插件默认配置（含其默认的多模型路由：最强判断用 Fable，评审面板混用 Sonnet/Haiku）。

|---|---:|---:|---:|---:|---:|---:|---:|---|
| matt-py | 7.5 | 7.0 | 6.5 | 7.0 | 6.5 | 7.5 | 7.0 | 2,3,3,2 |
| **grill-py** | **9.0** | 7.0 | **7.75** | **8.75** | **9.25** | **9.0** | **8.75** | **1,1,1,1** |
| pstack-py | 6.5 | **8.0** | 7.0 | 6.0 | 8.0 | 7.75 | 7.0 | 3,2,2,3 |
| matt-ts | 5.5 | 7.0 | 6.25 | 5.75 | 6.0 | 7.5 | 6.0 | 3,3,3,3 |
| grill-ts | **9.0** | **8.0** | **8.0** | 8.0 | 8.0 | 7.75 | 8.0 | 1,1,2,1 |
| pstack-ts | 8.0 | 7.5 | 7.75 | **8.25** | **9.5** | **8.5** | **8.33** | 2,2,1,2 |

裁判代表性评语：
- **grill-py**：“全迭代流水线（词法→调度场→代码生成→栈式 VM），不碰递归上限；Kahn 排序 + 只对剩余部分跑 Tarjan；二维二进分区间索引；结构编辑增量重定位；随机差分自测。” 缺点：概念多、`type: ignore` 噪声大。
- **pstack-py**：“模块小而清晰、函数注册表加函数很容易、黑盒测试 + 决策测试两套。” 缺点：递归 AST 求值依赖临时调高 `sys.setrecursionlimit(20000)`，结构编辑全量重建索引并全表重算。
- **matt-py**：“完全无递归（调度场 + 显式栈编译 + 平坦 VM）、结构编辑增量。” 缺点：函数元数据和实现分散在两个模块、长函数、测试偏少。
- **matt-ts**：4 位裁判一致指出递归 `findCycle` + 每层复制路径（栈溢出风险，已复现）与线性扫描调度（O(n²)）。
- **pstack-ts**：“状态用判别联合（discriminated union）表示，非法状态难以构造；测试是三者最强：精确事件序列断言、定时器/`Date.now` 监控、未处理 rejection 陷阱、重入用例和变异测试脚本。” 缺点：所有逻辑在一个文件，`src` 零注释。
- **grill-ts**：“通用 Heap 与 Emitter 独立成模块；未满足依赖计数器 + 仅在前向引用/自依赖时才做环检测，普通 add 只需 O(deps)；所有图遍历都是迭代的；先提交状态再发事件。” 缺点：重入时的级联顺序较难理解，部分理由写在外部 spec.md 中。

## 3. 分析

**① 正确性被模型能力“打满”了。** 两道题都属于高难度，但 6 份实现的隐藏验收都 ≥99.8%，差分模糊 ≥99.7%。对 Opus 5.5 这一级的模型，一份写得清楚的规格加上能问人的通道，工作流不再决定“对不对”，而是决定“好不好、快不快、贵不贵”。

**② Grilling→Spec 的价值体现在设计质量，而不是需求澄清。** 本来设想 grilling 的优势是把留白点问清楚，但 PO 类测试三方都满分（matt 自己也会用 `ask-po` 主动问 23 次；pstack 只问 1 次也全对）。grill 真正赢在：拷问阶段把测试缝（seam）、性能预算和 17–22 个边界语义都谈定了，随后的实现设计得分 9.0/9.0、可扩展性最好，NOTES 文档评分最高（Py 9.0）。代价是约 2 倍时间和成本。

**③ Matt `/implement` 是性价比之王，但“只做到能过测试”。** 它最快最省（TS 11 分钟 $2.94），Python 版质量中上。但 TS 版出现了算法层面的捷径（递归找环、线性扫描），隐藏测试和模糊测试都抓不到，只有规模探针和读代码的裁判发现。缺少前置设计环节时，模型倾向于先写出能通过测试的最简实现。

**④ pstack 的强项是验证纪律与可审计性，弱点是成本和 Python 设计取舍。** 它写了最重的测试（TS 2365 行，自建变异测试脚本，`deslop`/`no-comments` 清理，决策轨迹 `decisions.tsv`），TS 盲评综合分最高（8.33）、鲁棒性满分。但它按设计把最难的部分路由给 Fable，约一半花费在 Fable 子代理上，成本是 matt 的 2.3–4.8 倍；Python 版选择了递归求值 + 调高递归上限、结构编辑全量重算，被裁判扣了设计分。

**⑤ 工作流的“过程忠实度”。** grill-ts 在拷问结束后，PO 回答“yes”就直接开始实现，`/to-spec` 是事后补写的（Python 版按正常顺序执行）。这说明 Matt 的拷问流程在无人值守时，阶段边界取决于模型对“yes”的理解。

## 4. 建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 原型、一次性脚本、规格清晰的小模块 | **matt `/implement`** | 正确性不输，速度和成本最优；上线前补一次规模/性能检查 |
| 要长期维护的核心模块、有性能要求 | **grill → spec → implement** | 设计、可扩展性、文档全面领先，成本约 2 倍可接受 |
| 高风险变更、需要审计轨迹和强测试 | **pstack** | 测试与验证纪律最强、过程透明；预算要按 3–5 倍准备；无头 `-p` 运行时需关闭后台任务（见下） |

## 5. 局限与说明

- **每个组合只跑了 1 次（n=1）**，同一工作流重跑结果会有波动；差距较小的项（如 matt-py 与 grill-py 的正确性）不应过度解读。
- 题目对当前模型偏容易（正确性天花板效应），区分度主要来自补充维度；可扩展性与效率的权重带主观性。可以去掉效率重新加权：grill 83.0 / pstack 78.7 / matt 71.9（90 分制平均），排名不变，matt 与 pstack 的差距拉大。
- **pstack 不是同模型对比**：它按设计调用 Fable/Sonnet 子代理，这是它产品的一部分，本测试保留了默认路由。
- **pstack 重跑**：首轮运行中，pstack 按规范用 `run_in_background: true` 派子代理，而 `claude -p` 在回合结束时会杀掉后台子代理（日志 `task_updated: killed`），导致工作中断。为公平起见，两次 pstack 运行都已作废并以 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`（子代理改为前台）从零重跑；Matt 两位选手从不使用后台子代理，不受影响。作废运行保留在 `runs_aborted/`。
- PO、隐藏测试、参考实现、裁判都是 Claude 家族模型，可能存在同源偏好；裁判输入已匿名化并抹去工作流关键词，但代码风格本身可能泄露来源。
- 计时在 4 核共享容器上进行；TS/Python 规模探针在所有选手结束后串行执行，Python 探针执行时有判分 API 进程并行（CPU 占用很低）。

## 6. 复现

目录结构：`harness/`（沙箱 `arena.sh`、驱动器 `drive.py`、PO 服务、评分/盲评/指标脚本）、`tasks/`（规格、起始代码、PO 决策）、`hidden/`（隐藏测试、参考实现、模糊/规模/复现探针）、`submissions/`（6 份选手代码 + 驱动日志 + PO 问答）、`results/`（全部评分 JSON）。

```bash
python3 harness/drive.py <matt|grill|pstack> <py|ts>   # 运行一个选手（需 PO 服务: python3 harness/po/server.py）
python3 harness/grade.py && python3 harness/metrics.py && python3 harness/judge.py py 4 && python3 harness/score.py
```
