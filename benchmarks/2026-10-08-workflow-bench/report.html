正确性：全员接近满分

6 份实现的隐藏验收都 ≥ 99.8%，与参考实现的差分模糊测试一致率都 ≥ 99.7%。隐藏测试和参考实现由两个互不可见的子代理分别编写，交叉验证 100% 吻合。规格留白、只能问 PO 才知道的决策类测试（Py 114 / TS 42）三家几乎全对，只有 Matt 的 Python 版漏了 SUM(1E308,1E308) 溢出应为 #VALUE!。

  • 严重缺陷：Matt 的 TS 版一次添加 2 万个链式依赖任务时，递归找环导致 RangeError: Maximum call stack size exceeded。4 位裁判读代码时都预言了这个问题，复现确认。
  • 轻微缺陷：Grill 的 TS 版在超时 abort 监听器里调用 cancel() 时，仍会补发一次 retry 事件（参考实现也有同样行为）。
  • 无缺陷：pstack 两份、Grill 的 Python 版、Matt 的 Python 版没有复现出裁判声称的缺陷。pstack 的 Python 版 300 个模糊种子中有 1 个分歧，落在规格歧义点上，未计为缺陷。

  • Grilling → Spec（Py）：全迭代流水线（词法 → 调度场 → 代码生成 → 栈式 VM），不碰递归上限；Kahn 排序后只对剩余部分跑 Tarjan；结构编辑增量重定位；随机差分自测。缺点是概念多、类型忽略注释多。

分析

1

正确性被模型能力打满

对 Opus 5.5 这一级的模型，规格清楚、又能问到人时，工作流不再决定对不对，而是决定好不好、快不快、贵不贵。

2

拷问的价值体现在设计，而不在澄清需求

决策类测试三家都几乎满分，问得多（Matt 23 次）和问得少（pstack 1 次）结果一样。Grilling → Spec 赢在拷问阶段就把测试缝、性能预算和 17–22 个边界语义谈定，随后的实现设计分两题都是 9.0，TS 可扩展性最好。代价是约 2 倍时间和成本。

3

Matt /implement 性价比最高，但容易停在能过测试

TS 11 分钟、$2.94 就交付了全对的实现，但算法上走了捷径，隐藏测试和模糊测试都抓不到，只有规模探针和读代码的裁判发现了问题。

4

pstack 强在验证纪律，弱在成本

测试最重、带变异测试和决策轨迹，TS 盲评综合分最高；但成本是 Matt 的 2.3–4.8 倍，Python 版的递归求值和全量重算被扣了设计分。

5

无人值守时，阶段边界靠模型理解

Grill 的 TS 版在 PO 回答“yes”后直接开始实现，spec 是事后补写的；Python 版按顺序执行。

怎么选

原型 · 小模块 · 规格清晰

Matt /implement

正确性不输、最快最省。上线前补一次规模和性能检查。

长期维护 · 有性能要求

Grilling → Spec

设计、可扩展性、文档全面领先，约 2 倍成本换来更少的返工。

高风险 · 需要审计轨迹

pstack

验证纪律最强、过程透明。预算按 3–5 倍准备；无头运行需关闭后台任务。

局限

  • 每个组合只跑 1 次，同一工作流重跑会有波动；小差距不宜过度解读。
  • 题目对当前模型偏容易（正确性天花板），区分度主要来自补充维度；可扩展性和效率的权重带主观性。
  • pstack 按设计调用 Fable / Sonnet 子代理，不是严格的同模型对比。
  • pstack 首轮运行中，claude -p 在回合结束时杀掉了它的后台子代理；两次 pstack 运行已作废，并在 CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 下从零重跑。Matt 两位选手从不使用后台子代理。
  • PO、隐藏测试、参考实现和裁判都来自 Claude 家族，可能存在同源偏好；匿名化无法完全掩盖代码风格。

方法

  • 隔离：每个选手运行在独立的 mount + PID 命名空间，只能看到自己的 /arena 工作区和自己的技能；隐藏测试、其他选手、宿主会话全部不可见。
  • 同条件：同一模型与 effort、auto 权限模式、禁用联网搜索、相同任务提示词，只有工作流入口不同。
  • 模拟用户：所有选手都能用 ask-po 问产品负责人（独立 Claude，只按 12 条隐藏决策回答被问到的问题）；拷问轮次和回合末的提问由驱动器转交同一个 PO。
  • 数据与代码：完整工具链、隐藏测试、参考实现、6 份提交和评分 JSON 在仓库 Keason-C/skills 分支 ccr-2cb2360b-uhgbp9 的 benchmarks/2026-10-08-workflow-bench/。
