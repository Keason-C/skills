# S1 需求档案 — 生产级认证服务（裁判专用，不得直接透露给选手）

## 种子输入（三家一字不差的起始指令）
「我需要一个生产级的认证服务，给内部工具用。邮箱+密码登录，但一直有人要 SSO。安全得敢直接暴露公网——会话、密码重置，该有的都得有。其他服务还要能查这个用户登录没、有啥权限。我不要玩具 demo，我要真能上线、不会半夜把我叫起来的东西。」

## 用户画像（我扮演的角色）
- 内部平台工程负责人，懂业务、懂运维痛点，**不懂具体实现**（不回答框架级细节，只做业务裁决）。
- 公司 ~200 人，内部工具约 10 个服务要接入，用户量 ~2000（含合同工），峰值 QPS 很低（<50）。
- 维护人力：2 个后端工程师兼职维护。可用性期望内部 SLA 99.9%。

## 业务目标
统一的认证与授权查询服务：内部工具不再各自造登录；其他服务能查「这个人登录没、是谁、有什么权限」。

## 必须有（Must-have）
1. 邮箱+密码注册/登录/登出，注册仅允许配置的公司邮箱域（如 @company.com，可配置多个域）。
2. 注册需邮箱验证（服务要暴露公网，不能允许未验证邮箱的账号生效）。
3. 会话管理：过期、续期、用户主动登出、管理员强制撤销某用户全部会话。
4. 密码重置：邮件 token 流程，token 一次性、限时过期。
5. 服务间查询 API（introspection）：其他服务凭 per-service 静态 API key 调用，返回「是否有效会话、用户身份、角色/权限」。
6. RBAC：内置粗粒度角色（admin / member / viewer 起步），admin 可管理用户（禁用、改角色）。
7. 公网级安全：密码 argon2 或 bcrypt 存储；登录速率限制 + 失败锁定（参数不纠结，有且可配置即可）；secure/httponly cookie 或等价方案；CSRF 防护（若用 cookie）；无任何密钥硬编码；无注入隐患。
8. 运维基本盘：结构化日志、健康检查端点、一条命令本地跑起来、部署文档。

## 加分（Nice-to-have）
- 审计日志（谁在何时登录/改权限/重置密码）。
- 自定义角色/细粒度权限。
- metrics 端点（prometheus 风格）。
- SSO 预留：本期**不实现** SSO，但架构上预留 OIDC 接入点（identity provider 抽象），后续加 SSO 不用重写。

## 明确不做（Out of scope，被问到才说）
- MFA/2FA：v1 不做，设计别堵死。
- SSO/OIDC/SAML 实际接入：不做，只留架构缝。
- 用户自助资料编辑、头像等：不做。
- 多租户：不做，单公司。

## 预置答案（被问到才答，没问不说）
- 技术栈：「后端团队 Python 和 TypeScript 都写，你选你认为最稳最好维护的，说清理由就行。」
- 数据库：「生产我们有 Postgres。开发/测试环境你们定，但必须一条命令能跑起来。」
- 邮件：「生产有 SMTP relay。开发环境你们自己想办法（打日志/写文件都行），但接口要留好。」
- 部署形态：「容器化，跑在我们内部的 k8s 上，但你只需要给 Dockerfile 和文档，不用写 k8s manifests。」
- 会话载体：「你是专家你定，理由说清楚。前端是各内部工具自己的 SPA/服务端页面都有。」
- token 风格（JWT vs opaque/introspection）：「你定，但其他服务查权限必须是实时准确的——人被禁用了不能还能操作十分钟。」（暗示偏 introspection / 短 TTL）
- 权限粒度：「起步 admin/member/viewer 够用，能扩展就行。」
- 用户来源：「开放注册但限公司邮箱域 + 邮箱验证。不搞邀请制。」
- 密码策略:「别学银行搞大写小写特殊字符,长度下限 + 常见弱密码拦截就行。」
- 忘记密码邮件频率限制:「要有,别被人当邮件炮打。」
- 现有系统迁移:「没有存量用户,全新服务。」
- 合规:「无特殊合规要求,常识性安全即可。」
- 预算/时限:「这轮就要 v1 能上线的东西。」
- UI:「不需要漂亮 UI。有可用的最小登录/注册/重置页面即可(其他服务对接主要走 API)。给 API 文档。」

## 验收标准（打分依据，硬性）
A1 注册→邮箱验证→登录→登出 全流程亲手跑通。
A2 会话过期/撤销行为符合声明；admin 撤销后 introspection 立即失效。
A3 密码重置全流程跑通；token 只能用一次、过期失效。
A4 introspection API 用 API key 鉴权，返回身份+角色；无 key/错 key 被拒。
A5 RBAC：admin 能禁用用户、改角色；被禁用户所有入口失效。
A6 速率限制/锁定真实生效（我会实际打请求验证）。
A7 密码哈希为 argon2/bcrypt；代码库无明文密钥（grep 验证）；SQL 参数化。
A8 测试套件在我手上全绿，且覆盖上述关键路径，断言真实行为。
A9 一条命令启动成功；README/部署文档齐全可照做。
A10 spec 定稿后实现阶段零人工澄清（Loop 适配硬指标）。

## 流程裁决
- 计划阶段（提问+spec+tickets）软上限 90 分钟；实现阶段总硬上限 4 小时/家，超时按现状打分并记失败一笔。
- 面试轮数软上限 ~8 个来回，超限我将回复「按你的专业判断定，把假设写进 spec」。

## 新增裁决记录（跑动中追加，全家共享同一答案）
- [15:47 UTC, C首问] SSO 定位/身份源。标准答案（同问必须一字不差复用）：
  「v1 只做邮箱+密码，SSO 这期不实现，但架构上要留好接口——以后加 SSO 不能重写账号模型。身份源我们还没定。」
- [15:52 UTC, B批量问] 新裁决与标准答案（同主题同答案）：
  - 登录页面：「最小托管页面即可（登录/注册/重置密码），不追求漂亮；各服务对接主要走 API，给 API 文档。」
  - 注册人群：「邮箱域在配置的公司域名单内的可自助注册，注册要邮箱验证，不搞邀请制。外部协作者一律发公司域邮箱，不支持外部邮箱注册。」
  - 权限模型：「起步 admin/member/viewer 三个全局角色就够，能扩展就行，别搞复杂。用户组这期不要。」
  - 撤销时效：「停用要即时生效，分钟级延迟都不接受——被禁的人还能再点五分钟不行。技术上怎么实现你们定。」
  - 接入方规模：「大概 10 个服务要接，语言比较杂，Python 和 TypeScript 为主。」
  - MFA：「这期不做，设计上别堵死就行。」
  - 审计/合规：「没有 GDPR/等保这类硬要求，常识性安全即可。审计日志（谁登录了、谁改了权限）有最好，不强制，保留多久你们定。」
  - 告警对接：「我们有现成监控栈，你把健康检查和指标暴露出来、文档写清楚就行，不用对接具体告警渠道。」
  - 规模/时间：「约 2000 用户，峰值 QPS 很低（<50）。这轮就要 v1 能上线的东西。」
- [15:58 UTC, A首轮12题] 新裁决与标准答案：
  - SSO 时间压力：「没有具体截止日期，也没有哪个部门卡着等。」
  - 权限边界：「资源级/细粒度权限归各应用自己管，认证服务只管角色。这个边界我接受。」
  - 调用方类别：「就是各工具的网页前端，加上它们的后端来查登录态/权限。定时任务这类机器身份这期不需要，命令行工具不需要，外部第三方没有。」
  - 会话参数：「我们没有合规写死的数字，具体数值你们定、写清楚就行；改密码踢掉其他会话、高危操作重新验证这类安全默认我都接受。多设备同时登录要允许。」
  - 账号管理：「管理 API 必须有；极简管理界面有最好，没有硬要求。停用而非删除、停用立即吊销全部会话——接受，这正是我要的。离职停号我们人工操作，不对接 HR 系统。」
  - 可用性目标：「内部 SLA 99.9%。」
- [16:05 UTC, B二轮] 新裁决与标准答案：
  - 故障语义：「对——认证服务故障时宁可全员登不进去，也不能放行（fail-closed）。」
  - 泄露密码库外查：「允许对外网查泄露密码库，但那个接口挂了/超时不能影响我们自己的注册登录。」
  - 锁定策略：「临时锁+按 IP 限速这种就行，参数不纠结但要可配置；别搞成别人故意输错就能把我账号锁死的形态。」
  - 邮箱枚举：「统一提示，别让人枚举出我们的员工邮箱。注册页同理。」
  - 管理形态：「管理 API 必须；网页后台没有硬要求，API+CLI 够用，非技术同事不需要自己操作。」
  - 删除语义：「接受删除=匿名化保留审计链。」
  - introspection 返回字段：「用户 ID、邮箱、显示名、角色、账号状态就够，不需要工号/部门/头像/手机号。」
  - 首个管理员引导：「你们定。」
  - 未验证邮箱登录：「不能，必须先完成邮箱验证。」
  - 网络拓扑：「10 个服务和认证服务都在同一个 k8s 集群内网。管理/内省接口只走内网、用户接口走公网，这个做法我接受。」
- [16:55 UTC, A二轮] 新裁决与标准答案：
  - 注册后默认角色：「新注册的人默认没有任何角色，能登录但在所有工具里查无此人，管理员赋权后才能用。接受这个流程。」
  - 域名拓扑：「全部内部工具在同一个父域下（deploy.company.com 这种），认证服务是 auth.company.com。」
  - 即时生效范围：「停用、降级/改角色、改密码踢其他会话、管理员重置密码踢会话——全部即时。」
  - 改邮箱：「仅管理员可改，用户不能自助改邮箱。」
  - 生产基础设施：「生产有托管 Postgres；Redis 也可以有。」（沙箱同款：Postgres16/Redis7 均在）
  - 角色模型落法：「接受'接口按应用设计、v1 只有一个默认应用'的落法，前提是用起来和三个全局角色一模一样、不添复杂度；否则就纯全局。」
  - build vs buy：「自建。不上 Keycloak/Authentik 这类现成平台，也不买 SaaS。要一套我们自己看得懂、管得住的代码。」
