# Round 6 评测报告：全栈跨前后端改动（FastAPI + React/TS）

## 背景与目标（每轮报告共用）

**这是在评测什么。** 你想搞清楚一件事：当你只想"给需求 + 做验收"、把中间的想清楚需求→设计→拆任务→写代码→自测这一整段"loop"交给 AI agent 自主跑时，**哪种工作流（skill 组合）最靠谱**。所以我们让三套工作流在**同一道真实开发题**上正面对撞：

- **A = matt 的 skills**：`grilling`（把你盘问透）→ `to-spec`（写规格+ADR）→ `to-tickets`（拆成可执行工单）→ `implement`/`tdd`（按工单实现）。
- **B = 裸 brainstorm 基线**：不挂任何 skill，让 Opus 用它自己认为最好的方式对话、出规划、拆任务。这是对照组，用来量"skill 到底加了多少价值"。
- **C = superpowers 的 skills**：`brainstorming`（对话式想全设计）→ `writing-plans`（写分阶段 TDD 计划）→ `executing-plans`（按计划执行）。

**为什么这么设计。** 核心命题是"agentic coding 不是 vibe coding"——好的工作流应该在动手前**帮你把生产级的坑想全**，并且能**无人值守地从需求跑到可验收的成品**。除了常规的正确性/健壮性/测试/可维护/运维，我们专门加了一个"**思维补全**"维度，看它有没有帮非专家把该想的都想到。

**公平设置（每轮一致）。**
1. 三家拿**一字不差的同一段种子需求**起步、在**各自隔离的 git 仓库**里干活。
2. **规划用 Opus、写码用 Sonnet**，三家同配置。
3. 我（裁判）**全程扮演那个"只懂业务/只定目标、不懂实现"的用户**，agent 的所有提问**只从一份预先写死的需求档案作答**——同一个问题，三家得到**一字不差的同一个答案**；没问到的我不主动说。
4. 每家**规划软上限 90 分钟、实现硬上限 4 小时**。
5. **我不写任何候选代码或规划**，只做裁判：**亲手跑测试、亲手构造对抗输入、亲手复现声明**——绝不轻信自我报告。
6. 评分用 7 维加权：正确性与验收 23 / 健壮性 18 / 测试 13 / 可维护性 13 / 运维就绪 9 / Loop 适配 14 / 思维补全 10。

## 本轮这道题是什么

**目标代码库**：`fastapi/full-stack-fastapi-template`（tag 0.10.0，commit `d40de23`）。这是一个真·全栈脚手架——FastAPI(Python) 后端 + React + TypeScript 前端 + **OpenAPI 自动生成的 TS client**。后端 ~1.6k 行、前端 ~8.4k 行 TS/TSX，跨两种语言、带认证/CRUD/alembic 迁移/生成客户端。

**种子需求（三家一字不差）**：现在的 Items 只有标题和描述，产品上想让用户能给每个 item **设一个优先级（低/中/高）**——创建和编辑时能选、列表里能看到、最好还能按它排一下。这是贯穿前后端的改动：后端要存、API 要传、前端要能选能显示。**别把现有的东西改坏**（后端测试、前端构建都得一直绿），前后端的类型/契约要对得上。

**为什么选这道题**：这道题的核心不是"写多少代码"，而是**能不能守住前后端契约**。这个脚手架有一条自动契约链——后端改 SQLModel schema → 生成 OpenAPI → `npm run generate-client`(openapi-ts) 重生成 `frontend/src/client/*.gen.ts` → 前端用生成的 typed client。**只要后端改了 schema 却没重生成 client、或手改了生成文件，前端 `tsc` build 就会报错**。所以"前端能 build 通过"本身就是"契约对齐"的硬证据，作弊不了。

**绿基线（我亲手焊死的，改动必须守住）**：后端 `pytest` = **60 passed**（Python 3.13 + 本地 postgres）；前端 `npm run build`（= tsc 类型检查 + vite 构建）通过。

**这道题埋的关键陷阱**（"思维补全"着眼点）：
1. **契约漂移**——改后端忘了重生成 client，或手改 `*.gen.ts` 糊上去。
2. **迁移安全**——只改 model 不写迁移会炸；加非空无默认字段会把老数据/现有测试搞坏。
3. **两端都要动**——只改一头 = 半截。
4. **枚举 × 排序的隐蔽交互**——如果优先级用字符串枚举 `low/medium/high` 存，直接 `ORDER BY priority` 会按**字母序**排（high < low < medium），得到错误的顺序。想"高优先级排最前"要么改数据类型、要么用 CASE 表达式、要么客户端按秩排。**这个坑不明显，是本轮最能拉开思维补全差距的点。**

## 结论先行

**本轮排名：C（9.29）> A（9.21）> B（9.08）。** 三家都交出了可上线的完整成品——双绿门全过（后端测试 A66/B64/C68 全绿、前端 build 全绿）、TS client 都是真·重生成（非手改）、迁移都安全可回滚、UI 都真接上了、现有功能零回归、实现阶段**零人工澄清**。**没有一家掉进那个字母序排序 bug**——这本身是三家都合格的信号。差距不在"有没有 bug"，而在**"多干净、多贯穿、多完整"**。

一句话概括三家的分野，全压在"优先级怎么存 + 怎么排"这一个设计决策上：

- **C（superpowers）赢在最完整**：用字符串枚举 `low/medium/high`（契约最干净、前端生成语义化 union 类型）**同时**在后端用 CASE 表达式做**真·跨页服务端排序**（高优先级永远排最前）。**两头都拿到了**——干净契约 + 正确排序。测试也最多（68，含 schema 级枚举测试）。代价是查询略复杂、计划对一个类型细节预测有小偏差（实现方自己补上了）。
- **A（matt）赢在最稳、文档最厚**：同样用干净的字符串枚举，规划产出最完整（SPEC + 4 个 ADR + 3 张工单），计划**最可执行**（实现期完全照单跑通、没有意外）。但排序选了最保守的**客户端仅当前页排序**（点表头触发），功能上最浅——不跨页、非默认排序。这是我给 A 盖过章的低风险选项，做得对，但没往最完整推。
- **B（裸 brainstorm）赢在洞察最锐、但解法有代价**：**独立发现**了字母序排序 bug，并从数据类型层面根除——改用 `IntEnum(1/2/3)`，服务端 `ORDER BY priority DESC` 天然正确。诊断是三家里最漂亮的。**但解法把 API 契约改浑了**：优先级在 API 里变成魔数 `1/2/3`，生成的类型是 `Priority = 1 | 2 | 3`，**违背了需求档案明说的偏好**（"语义枚举比 magic int 好、OpenAPI 里体现为枚举"）。前端因此得靠 label 映射表把 1/2/3 翻回显示文本。诊断满分、补救打折。文档也最薄。

**为什么是这个排名**：这道题奖励的是"跨栈端到端的工程完整度 + 契约干净度"，正好是 superpowers 那套"对话想全设计→分阶段 TDD 计划→照计划执行"的主场——C 把语义枚举和真排序两头都焊死了。A 的 matt 那套规划纪律给了最顺的执行和最厚的文档，但在"排序做多深"这个自由裁量点上选了保守。B 无 skill，靠模型自身的敏锐抓到了最关键的坑，但没把"解法的契约代价"这一层也想全——这恰恰是 skill 化工作流的价值所在：不只是发现问题，还要把解法的副作用也补全。

## 我的看法与建议（与打分证据分开）

> 这一节是我作为裁判的主观判断和选型建议，不作为打分依据。

**1. 这道题最像真实工作，也最能说明"skill 到底加了什么"。** R6 不是那种"想全需求就赢一半"的题（那种题 A 的 grilling 通吃），而是"设计决策的完整度"题——一个看似简单的"加个优先级字段"，藏着枚举×排序的隐蔽交互。三家都没掉进 bug，但**处理这个交互的完整度**把它们拉开了。这正是 skill 化工作流的价值分水岭：B（无 skill）靠模型自身敏锐**发现**了坑，但没把**解法的副作用**也想全；C（superpowers）那套"对话想全→分阶段计划"逼着它把"排序正确"和"契约干净"两个目标一起端上桌。**发现问题靠模型智商，想全解法靠工作流。**

**2. B 这轮很值得说——它证明了"裸模型 + 好基座"能有多强，也证明了它的天花板在哪。** B 独立抓到字母序 bug 是本轮最漂亮的单点洞察，比 A 还早想到"字符串枚举会按字母排"。如果只看"发现坑"，B 是冠军。但 B 把 API 契约改成魔数、还没意识到这违背了偏好——**这种"解法带来的二阶后果没想全"，恰恰是 skill 能补的**。A/C 的 skill 让它们默认走"语义枚举 + 想办法让它排对"，而不是"为了排对牺牲语义"。所以我的判断：**B 适合有经验的人盯着用**（你能一眼看出它的解法有没有副作用），**不适合"只做验收"的无人值守 loop**——它偶尔会用一个聪明但有代价的解法，而你可能验收不出那个代价。

**3. A 和 C 这轮几乎平手，选谁看你更在乎什么。** A 赢在文档（ADR 记录了每个决策的理由，将来接手的人能看懂"为什么用 VARCHAR 不用原生 enum"）和执行顺滑度（计划最可执行）。C 赢在成品完整度（真跨页排序 + 干净枚举两全）和测试覆盖。**如果这是要长期维护、多人协作的代码，我略偏 A**（那套 SPEC+ADR+工单是活文档，也是未来 loop 的记忆）；**如果是要一版就把功能做到最完整、最少留尾巴，我略偏 C。**

**4. 一个跨栈开发的通用提醒（不针对某一家）：** 这道题里"前端 `tsc` build 通过"能当契约守门员，是因为这个脚手架有 OpenAPI→生成 client 这条链。**现实中很多项目没这条链**（手写 API 类型、或前后端分仓）。如果你要用 loop 做跨栈改动，**第一件事是把"契约对齐"变成一个能自动失败的检查**（生成客户端 + 类型检查，或契约测试 pact 之类）——否则 agent 改了后端、前端悄悄漂移，你验收时看不出来。这轮三家都守住了契约，很大程度是因为我特意选了这个"契约会自动报错"的脚手架。**没有这道自动护栏的项目，做跨栈 loop 前先把护栏搭起来。**

**5. 排序这个加分项，三家的选择其实对应三种真实工程哲学，都不算错：** A 的"客户端页内排序"= 最小改动、不碰后端、不加迁移风险（适合"排序只是锦上添花、数据量不大"）；B 的"换数据类型让它天然排对"= 从根上解决（但改了契约语义）；C 的"保留语义类型 + 查询层 CASE"= 不改契约、把复杂度关在后端查询里（工程上最"正")。**如果让我教一个团队，我会讲 C 这种**——它示范了"当干净的抽象和某个技术约束冲突时，把复杂度吸收到实现细节里（CASE），而不是让它泄漏到接口上（魔数）"。这是好品味。
