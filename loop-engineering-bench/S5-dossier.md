## 种子输入（三家一字不差的起始指令）
「gallery-dl 这个下载器我用得挺多，但核心代码这些年攒得有点肥——util、cookies、job 这些文件一千多行，vulture 一扫一堆死代码，而且像 aes.py 那种六百多行的纯加密实现居然一个测试都没有。我想让它**瘦下来、也更让人敢动**：把明显的死代码/冗余清一清，给那些又重要又没测试的核心模块把测试补上。挑你觉得最值、最能落地的做，别把这个很多人在用的工具改出回归，告诉我你做了什么、为什么、怎么验证的。」

## 用户画像（我扮演的角色）
- gallery-dl 的**重度用户 + 想接手维护**的人。懂 Python，但对这份代码的边角行为不熟——**怕改出回归**。只定目标/约束/验收，让你自己读代码判断瘦哪里、补哪些测试。
- 想要两样：**瘦身**（清死代码/冗余，让核心更精炼）+ **补测试**（给关键零覆盖模块建安全网）。
- 最怕：把很多人在用的下载器**改出行为回归**。

## 必须有（Must-have / 硬约束）
1. **瘦身要真实且安全**：删的必须是真死代码/真冗余（用 vulture/覆盖率/静态分析佐证），不是"看着没用"就删；每一处删除都要有测试或论证证明不改行为。删完 231 绿基线必须仍全绿。
2. **补测试要补对地方**：优先给**零覆盖、又重要、又能离线确定性测**的核心模块补（`aes.py` 纯加密是标杆靶；`option.py`/`archive.py`/`actions.py` 等）。断言真实行为，不是空跑凑数。
3. **零行为回归**：任何用户可见行为都不能变——CLI 选项语义、下载/命名/配置行为、公开 API。231 绿基线保持绿。
4. **聚焦、可 review**：一个连贯的瘦身+补测试切片，不是全库大扫。别碰 extractor（61k 行、网络形态，本轮不值）。
5. **不弱化/不删现有测试**充数骗绿。
6. **不加运行时依赖**（测试依赖 pytest 可）。

## 加分（Nice-to-have）
- 瘦身前先跑基线/覆盖率，量化"删了多少行死代码、覆盖率提升多少"。
- 补测试用 characterization（先钉现有行为）保证瘦身不改行为。
- 给一个离线一条命令跑核心测试的入口，方便未来 CI。
- 覆盖率 before/after 数字（如 aes.py 从 0% 到 X%）。

## 明确不做（Out of scope，被问到才说）
- 不碰 extractor/（61k 行，网络形态，本轮不值）。
- 不做大重写/拆大模块的高风险工程（util.py 千行难看，但拆模块行为风险高，点到为止）。
- 不做加新功能/改用户可见行为。
- 不做纯格式化（black/isort）冒充瘦身。
- 不做升级大依赖/换构建。

## 预置答案（被问到才答，没问不说）
- 瘦身 vs 补测试哪个优先：「两个都要，但顺序上——先给要动的地方补 characterization 测试兜住，再删死代码，这样我放心。哪块价值最高你挑。aes.py 那种零覆盖的高价值模块补测试我尤其想要。」
- 删到什么程度算"死代码"：「vulture/覆盖率能佐证是真没被调用的、真不可达的，才删；'我觉得没用'不算。拿不准就留着、写进说明让我看，别激进删。」
- aes.py 值不值得补：「值。六百多行加密逻辑零测试，最让我不安。用已知测试向量（KAT）测最好，能证明它算得对。」
- 大模块要不要拆：「别为拆而拆。util/cookies 千行难看，但拆模块的行为风险这轮不值。瘦身=清死代码/冗余，不是重构架构。」
- 行为回归红线：「用户能看到的都不能变——CLI 选项、下载/命名/配置行为、公开 API。231 绿基线保持绿是硬线。」
- 覆盖率目标：「不设死指标。给那些零覆盖的关键模块从 0 补到有意义的覆盖就好，重点是断言真实行为、能当安全网。」
- extractor 要不要碰：「不要。六万行、每站一个、全是网络，本轮别碰，就核心。」
- 改多大：「聚焦、可 review。一个连贯的'瘦身一块 + 补一两个关键模块测试'就很好。别贪大。」
- 怎么算 done：「231 绿基线仍全绿；新测试离线确定性跑绿、真覆盖了关键模块；删的是真死代码有佐证；我能看懂你删了什么/补了什么/为什么/怎么验证。」
- 加依赖：「运行时别加。pytest 测试用无所谓。」

## 验收标准（打分依据，硬性；裁判亲手复验）
A1 **231 绿基线仍全绿**（裁判用上面锁定命令重跑，含瘦身后）。
A2 **瘦身是真死代码/真冗余**：裁判用 vulture/grep 核，删的确实无引用/不可达；无"删了还在用"的误删（否则基线会红）。
A3 **补测试真覆盖关键零覆盖模块**：抽查新测试确实覆盖 aes.py 等此前 0 覆盖的核心逻辑，断言真实行为（如 AES 用已知向量 KAT），非空跑。
A4 **零行为回归**：CLI 选项/下载命名/配置行为/公开 API 未变（裁判抽查 + 基线绿）。
A5 **新测试离线确定性跑绿**：裁判在干净副本上跑新测试，全绿、不联网、可复现。
A6 **覆盖率真提升**（若声称）：裁判可复现 aes.py 等从 0→X% 的覆盖提升。
A7 **不删/不改松现有测试**充数（裁判 git diff 审 test/）。
A8 **无新增运行时依赖**（测试依赖除外）。
A9 **附清晰改动说明**：删了什么死代码(佐证)/补了哪些测试(覆盖什么)/为什么这块最值/怎么验证，reviewer 可据此审。
A10 计划定稿后实现阶段**零人工澄清**（Loop 适配硬指标）。

## 关键陷阱区（"思维补全"评分着眼点）
- **激进删 = 头号风险**：vulture 有假阳性（反射调用、插件动态引用、`__all__` 导出、入口点、被 extractor 调用的核心函数）。好工作流会**核实每一处再删**，而非照单全删——照单全删会误删仍被用的代码（基线变红或运行时炸）。
- **补测试要补对+补真**：给零覆盖的纯逻辑(aes)补 KAT 才有价值；给已高覆盖的模块再堆测试价值低；写"assert not None"式空测试更是凑数。
- **characterize-first**：先钉住要动的地方的现有行为，再瘦身，才能证明没改行为。
- **范围纪律**：别扩到 extractor、别顺手拆大模块重构架构——那是高风险大工程，本轮不值。
- **"死代码"的隐蔽性**：`aes.py` 里的纯 Python AES 是给无 Cryptodome 环境的 fallback，别当"死代码"删了；反射/字符串动态调用的函数 vulture 会误报。
