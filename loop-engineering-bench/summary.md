# 总评报告：三套 agentic-coding 工作流，六轮实战对撞

## 一、背景与目标

**你想回答的问题。** 当你的工作方式是"**只给需求 + 做验收**"、把中间"想清楚需求 → 设计 → 拆任务 → 写代码 → 自测"这一整段 loop 交给 AI agent 自主跑时，**哪一套工作流最靠谱**？为此我们让三套工作流在**六道不同形态的真实开发题**上正面对撞：

- **A = matt 的 skills**：`grilling`（把你盘问透）→ `to-spec`（写规格 + ADR）→ `to-tickets`（拆可执行工单）→ `implement`/`tdd`（按工单实现）。
- **B = 裸 brainstorm 基线**：不挂任何 skill，让模型用它自认为最好的方式对话、规划、实现。**对照组**，用来量"skill 到底加了多少价值"。
- **C = superpowers 的 skills**：`brainstorming`（对话式想全设计）→ `writing-plans`（分阶段 TDD 计划）→ `executing-plans`（照计划执行）。

**公平设置（六轮一致）。** 三家拿一字不差的同一段种子需求、各自隔离仓库；规划用 Opus、写码用 Sonnet；我全程扮演"只懂业务、不懂实现"的用户，所有提问**只从一份预先写死的需求档案作答，三家同问一字不差同答，没问的不主动说**；每家规划软上限 90 分钟、实现硬上限 4 小时；**我不写任何候选代码/规划**，只做裁判——亲手跑测试、亲手构造对抗输入、亲手复现声明，绝不轻信自我报告。评分 7 维加权：正确性 23 / 健壮性 18 / 测试 13 / 可维护性 13 / 运维 9 / Loop 适配 14 / 思维补全 10。

**六道题覆盖的形态**：R1 从零做生产级认证系统；R2 从零做业务分析 AI agent；R3 行为保持的重构（httpie CLI）；R4 接手烂摊子（you-get 补测试 + 安全清理）；R5 开源项目瘦身 + 补测试（gallery-dl）；R6 全栈跨前后端加字段（FastAPI + React/TS）。

## 二、结论先行

### 总排名：A（六轮均分 9.10）≈ C（8.95）> B（8.67）

但"均分"会骗人。**真正的结论是：没有一套工作流全能，选型要看任务形态。**

- **轮胜 A 3 : C 3，B 0。** A 拿下 R2/R4/R5，C 拿下 R1/R3/R6。A 靠**稳定性和规划纪律**把均分拉高（六轮从没崩过，最低分 8.60）；C 靠**成品完整度**赢下"要一版做到最完整"的轮次（峰值高，R1/R6 都是完整型题）。**A 和 C 是两种气质，不是一个比另一个强。**
- **B 从没赢过，但不是陪跑。** B 在后期越追越近（R5 差 0.27、R6 差 0.13），在"任务边界清晰、靠单点洞察取胜"的题上能逼平；但在"要把需求/生产坑想全"的题上会拉开一整分（R2 差近 1.0）。B 证明了：**裸模型 + 好基座已经很强，但它的天花板正好是 skill 能补的那部分——想全解法的二阶后果、守住范围纪律、把文档沉淀成资产。**

### 一句话选型

| 你的任务像… | 首选 | 为什么 |
|---|---|---|
| 从零做一个功能/系统，需求还没想透 | **A (matt)** | grilling 把你盘问透，需求分析六轮最强（R2 大胜） |
| 要一版就做到最完整、最少留尾巴、能上线 | **C (superpowers)** | 成品完整度 + 运维就绪最高（R1/R6） |
| 接手别人的烂摊子 / 补测试 / 安全清理 | **A (matt)** | 分析纪律强、判断"什么该动什么别碰"准（R4/R5） |
| 行为保持的重构 | **C (superpowers)** | characterize-first + 分阶段计划守行为（R3） |
| 跨栈端到端、契约要对齐 | **C (superpowers)** | 端到端完整度 + 契约干净度（R6） |
| 边界很清晰的机械改动、你会盯着 review | B 也行 | 省 skill 开销；但别用于无人值守 |

**不推荐的用法**：不要用 **B 做无人值守的需求密集型或生产级任务**——它偶尔会用一个聪明但有代价的解法（R6 把契约改成魔数），而你若只做验收、可能验收不出那个代价。

## 四、三家画像（跨六轮的稳定特征）

### A (matt)：分析师气质——想得最全、写得最清、跑得最顺
- **最强项**：需求分析（R2 大胜）、判断力（R4/R5 分得清"真问题 vs 噪音"）、文档沉淀（每轮都产出 SPEC + ADR + 工单，是活文档也是未来 loop 的记忆）、计划可执行度（R6 实现期照单跑通没意外）。
- **短板**：偶尔在"做多完整"的自由裁量点上偏保守（R6 排序只做客户端页内）；纯完整度/运维就绪型的题上不是第一（R1 运维未及）。
- **适合**：需求没想透的从零项目、接手烂摊子、需要长期维护和多人协作的代码。

### C (superpowers)：工程师气质——成品最完整、最能上线
- **最强项**：一版做到最完整（R1 唯一完整可上线、R6 排序+枚举两全）、运维就绪（R1 拉满）、行为保持重构（R3 characterize-first）、端到端贯穿。
- **短板**：文档比 A 薄一档；偶有计划精度小偏差（R6 对生成类型的 optional 预测错，实现方自己补上）；从零需求密集型不如 A 深（R2）。
- **适合**：要一版做到最完整最少留尾巴、跨栈端到端、行为保持重构、上线导向。

### B (裸 brainstorm)：聪明但没护栏——洞察锐、后果想不全、文档薄
- **最强项**：单点洞察（R6 独立发现字母序排序 bug，比 A 还早想到）、边界清晰的机械任务上能逼平（R5/R6）。
- **短板**：**范围纪律差**（R1 主动想塞 SSO/MFA/细粒度权限，被档案顶回）；**解法的二阶后果想不全**（R6 为排对把契约改成魔数，没意识到违背偏好）；**行为保持不牢**（R3 偷偷改了行为）；文档最薄；需求密集型差距最大（R2）。
- **适合**：有经验的人盯着用、边界很清晰的改动；**不适合无人值守的需求密集/生产级 loop**。

**skill 到底加了多少价值？** 对比 B（裸）和 A/C（挂 skill），价值集中在三处：①**范围纪律**（skill 逼着"先把核心做扎实"，B 容易发散）；②**二阶思维**（skill 让默认走"既解决问题又不牺牲抽象"，B 容易"聪明但有代价"）；③**文档资产化**（skill 把设计/决策沉淀成 ADR/spec/plan，B 只留薄计划）。**发现问题靠模型智商，想全解法 + 守住纪律 + 沉淀资产靠工作流。**

## 五、独立章节（一）：流程加强建议

> 这一章是我基于六轮观察给的流程优化建议，目标是让"你只管规划 + 验收、agent 自主 loop"这套模式跑得更稳。独立成章，不与打分证据混写。

### 5.1 各阶段"文档建设"的最佳时机（什么阶段该产出什么、给谁看）

文档不是写完才补的，是**每个阶段的产出物 + 下一阶段的输入**。六轮里 A 之所以稳，很大程度是它每阶段都落文档、把它当"loop 的记忆"。建议这样安排：

| 阶段 | 该产出的文档 | 时机 | 作用 |
|---|---|---|---|
| 需求澄清 | **需求档案 / 决策记录**（谁定的、答了什么） | grilling/brainstorm **进行中就记**，不是事后 | 后续所有阶段的唯一事实源；避免 agent 反复问同一件事 |
| 设计 | **spec + ADR**（每个技术决策记"为什么"） | 设计定稿时 | ADR 是未来接手人/未来 loop 的记忆——R6 里 A 的 ADR-004 记了"为什么用 VARCHAR 不用原生 enum"，将来没人会再纠结 |
| 拆任务 | **tickets / roadmap**（可执行、带验收） | 实现前 | 让 loop 能一票一票无人值守跑；也是你验收的清单 |
| 实现 | **每票一条 commit + 测试** | 实现中 | 可 review、可回滚、可追溯 |
| 收尾 | **改动说明 + runbook**（改了哪些层、怎么验证、怎么部署/回滚） | 交付时 | 你验收的依据 + 上线/运维的手册 |

**关键原则**：**决策一旦做出就立刻落档**（我在六轮里就是这么做的——"新裁决先写档案再答"），否则同一个问题会被反复问，loop 就断了。

### 5.2 Roadmap / 拆任务该用哪个 skill

- **单个功能/中等改动** → matt 的 **`to-tickets`**（把 spec 拆成可执行工单，带依赖顺序，最适合 loop 一票票跑）。六轮里 A 的工单质量最稳、实现期澄清最少。
- **较大的分阶段工程（跨多个子系统/多周）** → superpowers 的 **`writing-plans`**（分阶段 TDD 计划，把"什么时候测什么"也编进去）。R1/R3/R6 里 C 的分阶段计划在"守住行为/守住契约"上很强。
- **经验法则**：**功能级用 `to-tickets`（颗粒细、便于验收），工程级用 `writing-plans`（分阶段、便于守护）。** 两者不冲突——大工程可以先 `writing-plans` 定阶段，再对当前阶段 `to-tickets` 拆细。

### 5.3 按场景推荐最优工作流（差的不推荐）

（详见第二章选型表）核心记忆点：**A 用于"想清楚"（需求/接手/判断），C 用于"做完整"（上线/跨栈/重构守护）**。B 只在"边界清晰 + 你会盯着 review"时作为省成本选项，**不进无人值守的生产 loop**。

### 5.4 "你只管规划 + 验收"的 loop 流程补强

要让这套模式真正无人值守跑稳，六轮经验提炼出五条：

1. **把验收变成一道能自动失败的护栏。** R6 三家都守住契约，很大程度是因为那个脚手架有"生成 client + tsc build 会自动报错"这条链。**现实项目如果没有自动契约检查（手写 API 类型/前后端分仓），做跨栈 loop 前先搭护栏**（生成客户端 + 类型检查，或 pact 契约测试）——否则 agent 改了后端、前端悄悄漂移，你验收时看不出来。
2. **绿基线焊死在前。** 每轮我都先亲手跑出"改动前是绿的"基线，再让 agent 动。**你的 loop 也应该：动手前先固化一个可复现的绿基线（测试全过 + 构建通过），之后任何改动都以"基线还绿吗"为第一道验收。**
3. **需求档案先行、决策即时落档。** 你扮演的"只定目标不定实现"的角色，要有一份写死的档案兜底——同一问题永远同一答案，agent 才不会因为你今天这么说明天那么说而反复返工。
4. **别轻信自我报告，抓关键点亲手复验。** 六轮里我复现过：mutation test（把 AES SBOX 改坏看测试是否真的红）、断网跑测试、逐项核 vulture 是不是真死代码、亲手 build 看契约漂移。**你验收时至少亲手跑一遍测试 + 构建 + 一个端到端 happy path**，比读一百行"我验证过了"有用。
5. **给 agent"什么该砍"的明确授权。** 六轮里我反复给的一条裁决是"有风险就砍掉加分项、先把核心做扎实"。**在你的需求里明确写出优先级和"可牺牲项"**，agent 才敢在遇到风险时做正确的减法，而不是硬塞导致翻车（B 在 R1 想塞 SSO 就是没有这条约束时的典型发散）。

## 六、独立章节（二）：原型设计的位置 + 一份标准项目开发流程

> 这一章回答两件事：Pencil 这类原型设计该放在流程哪一步、怎么穿插；以及把六轮的经验收拢成一份可复用的"标准项目开发流程"。

### 6.1 Pencil 原型设计放在哪、怎么穿插

**Pencil（低保真线框/原型工具）的位置：在"需求澄清"之后、"写 spec"之前，作为设计的一次廉价试错。** 原因是——线框图是**和你（业务方）对齐的最快语言**：文字规格你可能看不出问题，但一张"创建表单长这样、列表长这样"的线框你一眼能说"这里不对"。

**怎么穿插，分两种任务形态：**

- **有 UI 的任务（如 R6 全栈加字段）**：grilling/brainstorm 把需求盘得差不多后，**先用 Pencil 拉一版线框**——把"优先级下拉放哪、列表怎么显示、要不要默认排序"画出来给你看，你在线框上拍板交互，再进 spec。这一步能在写任何代码前消灭大量"做出来才发现不是我要的"。R6 里三家对"排序做多深/默认排还是点击排"的分歧，如果先有线框对齐，就不会各做各的。
- **纯后端/纯逻辑任务（如 R2 agent、R5 瘦身）**：没有 UI，**Pencil 不适用**；换成 **superpowers 的 `prototype` skill**——做一个**扔掉的逻辑 spike**（比如 R2 先撸一个最小 agent 跑通"输入业务问题→出分析"的骨架，验证状态/数据流对不对），验证完就扔，再进正式 spec。**原型的本质是"用最小代价验证一个设计假设"，UI 假设用 Pencil，逻辑假设用 `prototype` skill。**

**一句话**：**原型是"设计的草稿"，永远在 spec 之前、需求之后；有界面画线框（Pencil），没界面撸 spike（prototype skill），都是扔掉的。**

### 6.2 标准项目开发流程（每步：目的 / 工具·skill / 产出物 / 谁验）

这是把六轮打法收拢成的一条可复用流水线。你的角色只在★标记的地方（定需求 + 验收），中间交给 loop。

| # | 阶段 | 目的 | 工具 / skill | 产出物 | 谁验 |
|---|---|---|---|---|---|
| 0 | **需求档案** ★ | 定"要什么能力、什么算完成、不能破坏什么、可牺牲什么" | 你自己写；模板化 | 需求档案（含优先级 + 可砍项） | 你 |
| 1 | **盘问 / 想全** | 把模糊需求盘透、暴露隐藏约束 | A: `grilling`；C: `brainstorming` | 决策记录（即时落档） | agent 提问→你答（只从档案） |
| 2 | **原型试错** | 廉价验证设计假设 | 有 UI: **Pencil 线框**；无 UI: `prototype` skill | 线框图 / 扔掉的 spike | 你（在线框/spike 上拍板） |
| 3 | **设计定稿** | 定架构 + 记录每个决策的"为什么" | `to-spec` / superpowers 设计 doc | spec + **ADR** | 你过一眼 |
| 4 | **拆任务 / roadmap** | 拆成可无人值守跑的票 | 功能级 `to-tickets`；工程级 `writing-plans` | tickets / 分阶段 TDD 计划（带验收） | 你过验收清单 |
| 5 | **焊死绿基线** ★ | 固化"改动前是绿的"可复现基线 | 跑测试 + 构建 + 建自动契约护栏 | 基线记录（X passed + build 绿） | 你 |
| 6 | **Loop 实现** | 按票 TDD 实现，红→绿→提交 | `implement`/`tdd` / `executing-plans`（Sonnet 写码） | 每票一 commit + 测试 | 自动护栏（基线 + 契约检查） |
| 7 | **验收** ★ | 亲手复验、不信自我报告 | 亲跑测试/构建/端到端 + 对抗输入 | 验收结论 | 你（抓关键点亲验） |
| 8 | **收尾 / runbook** | 交付说明 + 上线/回滚手册 | 改动说明 + runbook | 跨栈改动说明 + runbook | 你存档 |

**这条流水线的三个"别省"**：①**别省原型**（第 2 步，最便宜的纠错）；②**别省绿基线和自动护栏**（第 5 步，无人值守的安全网）；③**别省亲手验收**（第 7 步，自我报告永远要复验）。六轮里凡是差距，几乎都出在某一家在这三处偷了工。

## 七、我的总体看法（与打分证据分开）

> 主观判断，不作为打分依据。

1. **"agentic coding 不是 vibe coding"这个命题，六轮验证下来是成立的。** 三家都能写出能跑的代码，但差距全在"动手前想没想全生产坑""解法有没有二阶代价""交付有没有沉淀成资产"——这些正是热情满满的 vibe coding 会漏掉的。**skill 化工作流的价值不在写代码更快，而在把非专家该想到但想不到的那部分补上。**

2. **如果只让我选一套默认工作流，我选 A(matt)——但会在完整度/上线导向的任务上切到 C。** A 的均分最高、六轮从没崩过、文档最厚，作为"默认挡位"最稳。但当任务是"要一版做到最完整能上线"或"跨栈端到端"时，C 的成品完整度确实更高。**理想状态是两套都备着，按任务形态切。**

3. **B 的存在很有价值——它标定了"裸模型基线"。** B 从没赢但后期越追越近，说明**基座模型本身已经很强，skill 的增量在收窄**。但 B 暴露的三个短板（范围发散、二阶后果、文档薄）恰恰是无人值守 loop 最致命的——因为你不在现场兜底。所以我的判断没变：**B 适合"人在环里"的协作，不适合"人只做验收"的 loop。**

4. **这套评测本身给你的最大启发，可能不是"选哪个 skill"，而是"把验收工程化"。** 六轮里我作为裁判做的事——焊绿基线、亲手复验、对抗输入、契约自动护栏——本质上就是你在"只做验收"模式下该做的事。**工作流决定 agent 写得多好，但护栏决定你敢不敢让它无人值守。** 先把护栏建起来，再谈用哪套 skill。
