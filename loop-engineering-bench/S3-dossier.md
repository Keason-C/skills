# S3 需求档案 — 真实开源代码库的优化/重构（裁判专用，不得直接透露给选手）

## 目标代码库（锁定）
- **httpie/cli**（著名的命令行 HTTP 客户端），commit 锁 `5b604c37c6c67e18e7c3e9aee6c88a8c22b98345`（`5b604c3`）。
- 规模：~19k 行 Python（源码 `httpie/` ~9.8k + 测试 `tests/` ~8k）。域复杂度高：CLI 参数解析、请求构建、响应处理、输出着色/格式化管线、会话/cookie、下载流、插件系统。
- **绿基线（裁判已亲手焊死，995 通过 0 失败）**——重构必须守住这条线：
  ```
  python -m pytest -o addopts="" -k "not remote_httpbin and not big5" \
    --deselect tests/test_config.py::test_config_file_inaccessible \
    --deselect tests/test_cookie_on_redirects.py::test_saved_session_cookies_on_different_domain \
    --deselect tests/test_cookie_on_redirects.py::test_saved_session_cookie_pool
  ```
  被排除的 ~24 个是**预存的环境/网络假象**（远程 httpbin 服务器、big5 字符集库版本、root 权限无视 chmod、cookie 跨域环境差异），非代码问题，与本次重构无关。
- 三家各拿一份该 commit 的隔离副本 /workspace/bench/round3/{A,B,C}（已建 venv 装好 .[dev]），分支 round3-refactor。

## 种子输入（三家一字不差的起始指令）
「这是 httpie，我们的命令行 HTTP 客户端。它能用、测试也齐，但有些地方这些年长得越来越乱，我想让它更干净——该快的地方也更快——但**用户能看到的行为一点都不能变**。你挑一个你能真正落地的、价值最高的重构或性能优化，把它做掉。测试套件必须一直是绿的。我不要为改而改的 churn，我要的是**真的变好、而且能 review**。」

## 用户画像（我扮演的角色）
- httpie 的**维护负责人 / tech-lead**。懂代码、能聊技术权衡，但**只定目标、约束、优先级和验收**，不替你决定"具体怎么改"——你是读这份代码的人，你来判断价值在哪。
- 在乎三件事：**可维护性**（这代码经常被人动）、**性能**（该快的地方）、**可 review**（改动要能被人看懂、敢合）。
- 最烦两件事：**改坏了用户能看到的行为**（哪怕"更好"也不行）、**为改而改的大范围 churn**。

## 必须有（Must-have / 硬约束）
1. **行为零改变**：任何用户或插件作者能观察到的行为都不能变——CLI 输出、退出码、参数语义、公开 API、插件接口。995 绿基线必须 100% 保持绿。
2. **聚焦、可 review**：一个连贯、有边界的改动，不是横扫整个仓库的重写。一件事做透，胜过十件事各改一半。
3. **改进要真实、可说清**：可维护性改进要能articulate（降复杂度/去重复/理清模块缝，最好有前后指标）；性能改进**必须有可复现的测量**，不许"感觉更快了"。
4. **不弱化测试**：套件保持绿；重构需要就加真实测试，但**绝不许删测试或改松断言来让它过**。
5. **不轻易加依赖**：尽量不加新运行时依赖；非加不可要有强理由且轻量。
6. **公开面稳定**：public API / CLI / 插件接口不变。

## 加分（Nice-to-have）
- 重构前先做 characterization（把现有行为用测试钉住）再动，证明行为不变。
- 前后给出可维护性指标（圈复杂度、重复率、函数长度等）或性能基准数字。
- 改动附清晰的"改了什么/为什么更好/怎么验证"说明，reviewer 能直接据此审。

## 明确不做（Out of scope，被问到才说）
- 不做加新功能 / 改用户可见行为的事（这轮纯内部改善）。
- 不做全仓库大重写 / 换框架 / 升级大依赖。
- 不做纯格式化（black/isort 跑一遍那种）冒充重构——要的是结构或性能的实质改善。
- 不碰那 24 个预存环境失败的测试（既不"修"也不依赖它们）。

## 预置答案（被问到才答，没问不说）
- 可维护性 vs 性能：「可维护性优先——这代码经常被动。真实的性能优化也欢迎，只要不牺牲可读性。用哪根杠杆你定。」
- 改动多大：「聚焦、可 review。一个连贯的改进做好，胜过一堆零散的。别重写世界。」
- 能不能改 public API / CLI：「不行。任何用户或插件作者能注意到的都不能变，纯内部改。」
- 能不能加依赖：「尽量别。非加不可就说清理由、保持轻量。」
- 改哪块：「你是读代码的人，价值在哪你挑。真要我说直觉——CLI 参数解析（argparser 那摊）和输出/格式化管线是我最怵的两块，但我信你的判断。」
- 测试怎么办：「套件必须保持绿。你的重构需要就加测试，但别弱化现有的，别为了过测试删测试或改松断言。」
- 怎么算 done：「套件全绿 + 一份清楚的'改了什么、为什么更好、怎么验证'说明；如果是性能改进，给数字。」
- 时间：「这是一件聚焦的活，不是几个月的工程。落地点真东西。」
- 怎么证明行为没变：「我会重跑整套。用户能看到的东西只要变了就算 fail，哪怕你觉得'更好'。」
- 要不要先写 characterization 测试：「我喜欢这个做法——先把现有行为钉住再动手，能让我放心你没改坏。」
- 性能怎么验：「给我一个可复现的测量——基准脚本、before/after 数字。别口说无凭。」

## 验收标准（打分依据，硬性；裁判亲手复验）
A1 重构后**995 绿基线仍 100% 绿**（裁判用上面锁定命令重跑）。
A2 **行为零改变**：抽查 CLI 输出/退出码/参数语义/公开 API/插件接口，无用户可见变化。
A3 改动是**聚焦、可 review 的连贯范围**，非横扫 churn（裁判看 diff 判断）。
A4 改进**真实且说得清**：可维护性（复杂度/重复/模块缝，最好带指标）或性能（测量）。
A5 若声称性能改进：有**可复现测量**证明确实变快（裁判会尝试复现）。
A6 **无新增运行时依赖**（或有强理由且轻量）。
A7 public API / CLI / 插件接口**未变**。
A8 新增测试真实且通过；**无删测试/改松断言**骗绿（裁判 diff 审 tests/）。
A9 附**清晰改动说明**（改了什么/为什么更好/怎么验证），reviewer 可据此审。
A10 计划定稿后实现阶段**零人工澄清**（Loop 适配硬指标）。

## 关键陷阱区（"思维补全"评分着眼点）
- **行为保持是头号风险**：重构最容易悄悄改掉边缘行为（输出细节、编码、异常路径）。好工作流会先 characterize 现有行为（钉测试）再动，而非直接改。
- **范围纪律**：抵住"顺手把整块重写了"的冲动，选一个高价值、有边界的靶子。没有范围纪律的方案会在 A3 翻车。
- **"更好"要被定义/测量**：不能只说"更清晰/更快"，要有前后对比或指标。
- **不许弱化测试骗绿**：删测试、改松断言、把 assert 改宽——都是骗绿，A8 会抓。
- **先懂再改**：好工作流会强制真正读懂这块代码（它为什么这样写、有没有历史原因）再下手，而非表面重排。
- **性能优化的诚实**：微优化可能无实感甚至更慢；要用真实基准验证，别凭直觉。
