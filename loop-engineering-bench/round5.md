# Round 5 — S5 开源项目瘦身（去膨胀/死代码）+ 补测试（gallery-dl）

## 背景与目标（每轮报告共用）

**这是在评测什么。** 你想搞清楚一件事：当你只想"给需求 + 做验收"、把中间的想清楚需求→设计→拆任务→写代码→自测这一整段"loop"交给 AI agent 自主跑时，**哪种工作流（skill 组合）最靠谱**。所以我们让三套工作流在**同一道真实开发题**上正面对撞：

- **A = matt 的 skills**：`grilling`（把你盘问透）→ `to-spec`（写规格+ADR）→ `to-tickets`（拆成可执行工单）→ `implement`/`tdd`（按工单实现）。
- **B = 裸 brainstorm 基线**：不挂任何 skill，让 Opus 用它自己认为最好的方式对话、出规划、拆任务。这是对照组，用来量"skill 到底加了多少价值"。
- **C = superpowers 的 skills**：`brainstorming`（对话式想全设计）→ `writing-plans`（写分阶段 TDD 计划）→ `executing-plans`（按计划执行）。

**为什么这么设计。** 核心命题是"agentic coding 不是 vibe coding"——好的工作流应该在动手前**帮你把生产级的坑想全**（而不是热情满满地写出一个上线就炸的 demo），并且能**无人值守地从需求跑到可验收的成品**。所以除了常规的正确性/健壮性/测试/可维护/运维，我们专门加了一个"**思维补全**"维度，看它有没有帮非专家把该想的都想到。

**公平设置（每轮一致）。**
1. 三家拿**一字不差的同一段种子需求**起步、在**各自隔离的 git 仓库**里干活。
2. **规划用 Opus、写码用 Sonnet**，三家同配置。
3. 我（裁判）**全程扮演那个"只懂业务/只定目标、不懂实现"的用户**，agent 的所有提问**只从一份预先写死的需求档案作答**——同一个问题，三家得到**一字不差的同一个答案**；没问到的我不主动说。这样规划质量的差异完全来自工作流本身，而不是我给谁多喂了料。
4. 每家**规划软上限 90 分钟、实现硬上限 4 小时**，超时按现状记。
5. **我不写任何候选代码或规划**，只做裁判：**亲手跑它们的测试、亲手构造对抗输入、亲手复现性能声明**——绝不轻信自我报告。
6. 评分用 7 维加权：正确性与验收 23 / 健壮性 18 / 测试 13 / 可维护性 13 / 运维就绪 9 / Loop 适配 14 / 思维补全 10。

**每轮换一道不同场景的题**，看不同工作流在不同任务形态下的强弱，最后给总评 + 工作流选型建议。

## 本轮场景
在真实开源库 `mikf/gallery-dl`（媒体下载器，commit `86047cf`/v1.32.9，核心 ~13k 行，extractor ~61k 行本轮不碰）上做**瘦身（去膨胀/死代码）+ 补测试**。护栏=裁判亲手焊死的**离线绿基线 231 过 / 47 跳过**。

**这轮埋了一个关键陷阱**：`vulture` 扫出一堆"死代码"，但因为它排掉了 extractor/，就把 6.1 万行 extractor 消费的整个公共 API 误报成"未使用"。**照单全删会误删仍在用的代码、把基线跑红甚至运行时炸**。核心补测试靶是 `aes.py`——649 行纯 Python AES 实现、0% 覆盖、且因本 venv 无 Cryptodome 而是**当前活跃的 fallback 路径**。

## 结论先行
**排名：A（matt，9.39） > C（superpowers，9.14） > B（裸 brainstorm，9.12）**

**这是五轮里最接近、整体最高的一轮（全部 9.1+）。** 最重要的发现：**我埋的 vulture 假阳性陷阱，三家（含无 skill 的裸 brainstorm 基线）全部独立识破了**——都跨全包核实、都发现真死代码只有 ~11 行（一个 `DeprecatedConfigConstAction` 类）、都诚实地把这轮重构成"~80% 补测试 + ~20% 瘦身"，都用真 NIST 向量给 aes.py 补 KAT。没有一个照单删 vulture 输出。

判断力三家都过关，区分落在**执行的严谨与广度**：A 靠最彻底的 proof-of-death + 4 ADR + 扎实广度夺冠；C、B 几乎平手（0.02 分）——C 胜在最外科 + 一个"独立交叉验证"的严谨标杆，B 胜在最大广度（151 测试、aes 覆盖 96% 最高）。

三家的**变异测试全部通过**——我篡改 aes.py 的 S-box，三家的 aes 测试都立即变红，还原后全绿，**证明它们真在验证 AES 算得对、不是空跑**。三家 KAT 向量都是**真发布的 NIST 官方向量**（A/C 用 FIPS-197 Appendix C，B 用 SP 800-38A，不同附录同样官方）。三家瘦身都只删那**一个真死的类**（proof-of-death grep 证明零引用），aes.py 全部**只测不改**（vendored），现有测试全部**无删无改松**。

### 三家差异（证据带路径）
- **A**：**proof-of-death 最彻底**——不止 grep，还核查了 `action=`/`getattr`/`ACTIONS`-table/`__all__`/entry-point 所有动态接线路径（正是 vulture-FP 教训该有的怀疑），确认 `DeprecatedConfigConstAction` 真死才删；`add_url` 调查后判为"有意的公共 API 对称"**报告后保留不删**；4 个 ADR（proof-of-death 程序/测试优先/KAT 策略/vendored 不分叉）；诚实说明 test_results.py（网络 per-extractor 测试）排除理由。124 测试 4 模块。
- **B**：**广度最大**——151 个测试、4 模块全做（含 stretch actions）、aes 覆盖 96% 最高、exception 100%；KAT 向量 authoring 时对独立装的 pycryptodome 交叉核对。无 ADR。
- **C**：**最外科 + 严谨度标杆**——32 测试 3 模块（未做 actions），但发现**自己计划里的 GCM_TAG 向量验不过、用独立的 system cryptography 库（而非被测代码本身，刻意避免循环验证）交叉核对、复现密文修正 tag=`cc15abcc..`**（round5/C Task 4 commit）。这个"不拿被测代码给自己背书"的动作是本轮最锋利的严谨点。
